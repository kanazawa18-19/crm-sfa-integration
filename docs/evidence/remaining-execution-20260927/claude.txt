既定値がある場合：別のスプレッドシートや別のDBを黙って診断してしまいます。冒頭のコメントにある「同じ設定で数えるため」という意図に反し、診断結果そのものが信用できなくなります。

A-3 WARN：orphan が NG 判定に加わった（挙動の変更）

変更前の NG 判定は dup or diff で、diff = len(missing) でした。つまり、対応表に無い行（orphan）は一覧に出るだけで、終了コードには影響していませんでした。今回の変更で orphan が1件でもあれば終了コードが1になります。

シートに手入力の行や他ツール由来の行が存在し得る運用であれば、この診断は常に失敗することになります。意図した変更であれば、コミットメッセージか docstring に明記してください。意図していなければ、orphan は報告のみに戻すか、--fail-on-orphan のようなオプションに分けてください。

A-4 WARN：行番号照合が依存している前提

inspect_mapping_rows は enumerate(cells, start=2) の位置をそのままシートの行番号として扱っています。この計算が正しいのは、次の2点が成り立つ場合だけです。

cells の抽出部分（差分では省略）が、途中の空行を "" として保持していること。Sheets API の values は、空行を [] として返し、末尾の空行は返しません。[] を詰めて抽出していると、それ以降の行番号がすべて1つずつずれ、大量の誤った不一致と誤った修復候補を出してしまいます。
IdMapping.spreadsheet_row が int であること。DB から文字列で返ってくる場合、actual != [saved] は [3] != ["3"] となり、全件が不一致と判定されます。テストでは int を直接渡しているので、この問題は検出されません。

どちらも実装を確認したうえで、1についてはテストで [[“a”], [], [“b”]] 形式の API 応答を与えて検証することを勧めます。

B-1 BLOCKER（確認で解除可）：滞留分が statement_timeout 10秒を超えると永久に収束しない

今回の前提は、日報の処理が時間切れになり、これまで掃除まで到達していなかったことです。つまり WebhookEvent テーブルには、7日を超えた行が相当数たまっている可能性があります。

この状態で初回の DELETE が10秒を超えると、次のことが起きます。

文がキャンセルされ、ロールバックにより削除件数は0になります。
翌日も同じ量の滞留に新しい行が加わるので、また10秒を超えます。
保持期間7日を守るという目的が、いつまでも達成されません。

"receivedAt" にインデックスが無ければ、テーブル全体の走査が必要になり、この状況はさらに起こりやすくなります。

解除の条件は、次の2点を確認することです。

本番で SELECT count(*) FROM "WebhookEvent" WHERE "receivedAt" < now() - interval '7 days' を実行し、滞留件数を把握すること
"receivedAt" にインデックスがあること

件数が多い、または見積もれない場合は、次のどちらかで対応してください。

分割削除にする：DELETE … WHERE id IN (SELECT id … ORDER BY "receivedAt" LIMIT 5000) を、1回ごとに commit しながら、合計の時間予算内で繰り返します。途中で止まっても、それまでの削除は残ります。
リリース前に一度だけ手動で滞留分を掃除する：この場合も、その手順を記録してください。
B-2 WARN：失敗原因がログに一切残らない

接続文字列を漏らさないために exc_info=True を外した判断は正しいです。ただ、今回 lock_timeout と statement_timeout を追加したことで、掃除の失敗はこれまでより起きやすくなります。それなのに、ロック待ちによる失敗、時間切れ、接続不可のどれなのかを区別できません。

秘密情報を含まない次の2つだけでもログに残すことを勧めます。

例外のクラス名（type(e).__name__）
psycopg のエラーであれば e.sqlstate（ロック待ちは 55P03、キャンセルは 57014）

テストの test_cleanup_failure_preserves_report_and_hides_exception には、「クラス名は出力され、メッセージは出力されない」という確認を足すとよいです。

B-3 INFO：日報の時間予算を最大約20秒使う

掃除が先に走るため、最悪の場合は接続待ち10秒と文の実行10秒（ロック待ちの2秒はこの中に含まれます）を合わせた約20秒が、日報の300秒から差し引かれます。日報の時間切れ自体の修正は範囲外と明記されているので、今回の問題ではありません。ただ、日報の所要時間が上限に近い日には、この変更がきっかけで時間切れになり得ることを、関連する課題に書き残しておくとよいです。

B-4 INFO：処理の順序と SET LOCAL について（問題なし）
psycopg3 は既定で autocommit が無効なので、最初の execute でトランザクションが始まります。SET LOCAL はその中でだけ有効で、with conn を抜けるときの commit かロールバックで元に戻ります。コメントの意図どおりに動きます。
プラットフォーム側で処理が強制終了された場合（例外ではなく終了させられる場合）でも、掃除は先に commit 済みなので、保持期間は守られます。
{**run_report_batch(), **cleanup_result} で日報の結果に同じキーがあっても、掃除の件数で上書きされるだけなので、実害はありません。
B-5 INFO：ログとテスト
追加した logger.info("…掃除完了: deleted=%d") は、日報が時間切れになったときに件数を確認できる唯一の手段です。本番のログレベルが INFO を出力する設定になっているか確認してください。
この info ログが出ることを確認するテストもあると、将来ログを削除されたときに気づけます。
