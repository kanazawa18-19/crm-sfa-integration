# メール後の連絡先登録による履歴漏れの回収

2026-10-14追加実装。まだ本番未反映・未有効化。

## 原因と方針

今回復旧した5通は、メール到着より後に連絡先が登録されていた。GASの2時間重複走査では2時間を超える遅延登録を保証できない。旧日次同期も直近2日・先頭100件だけであり、連絡先の新規登録・メール変更を起点にした過去取込はなかった。

```
Notion正本を分割巡回 → メールの新設・変更を永続記録
                            ↓ 2日待機
固定した過去期間を10通ずつ取込 → 保存済みIDは除外 → 完了記録
```

GASを第一候補として検討したが、既存CRMのOAuth・連絡先正本読取・無通知の保存関数・DB監視をそのまま使える有界cronが最小構成になる。GASの自然観測を変更せず、遅延登録回収を独立した処理にする。

## 期間と副作用

- 自動ジョブの対象は、メール変更検知時刻を固定上限とする過去365日。既存 `scripts/backfill_gmail_history.py --days` の既定値を踏襲し、無限には遡らない。From/Toだけを照合し、SPAM/TRASHに加え、未送信のDRAFTSとチャットも除外する。
- 上限から2日経過するまで待機し、既存の通常同期・日次救済に先行しない。待機期間を設定値で短縮しない。
- 保存は既存 `db.insert_email_logs()` のみ。スコア・インシデント通知・Notion最終メール日時の更新・GmailIngestEffect・外部通知は呼ばない。過去取込が新着の通常通知を先取りするのを避けるため、実行時点から最低2日前で上限を固定する。
- `EmailLog.gmailMessageId` で処理済みを除外する。保存成功後に応答が失われても次回は既存IDとして終端し、今回復旧済み5通や以前の履歴を再保存しない。
- この履歴回収は遅延した業務登録への補完であり、当時の自然取込遅延を証明しない。

## 全入口の捕捉とbaseline

5分cronが連絡先正本を100件ずつ巡回する。Notionへの保存元を問わず、手入力・通常同期・問い合わせ・CSV等のメール値の変化を拾う。Webhookが来ない場合も同じ巡回で検出する。ページ単位の既知メールと変更世代UUIDを記録するため、観測できた `A→B→A` は別ジョブになる。巡回間に変更されて元に戻った値は、履歴APIがないため観測できない。

初回はNotionの分精度に合わせて開始cutoffを分の先頭へ切り下げて固定し、作成済み既存値をbaselineとして記録するだけで大量回収しない。

| 初回巡回で見つけたもの | 扱い |
|---|---|
| cutoffより前に作成・最終更新済み | baselineのみ |
| cutoff以降に新規作成 | 回収ジョブへ |
| 古いページだがcutoff以降に更新 | メール変更か他項目更新かを断定できないためcandidateとして参考件数に残す。自動回収・障害通知をしない |
| baseline後に既知メールが変更 | 新世代の回収ジョブへ |

Notionの1応答100件は20件ずつ1接続の一括SQLで保存する。既知値・ジョブ・ページ内残件を同じDBトランザクションで確定するため、180秒の時間予算で中断しても次回は残件から進み、同じ100件を繰り返さない。SQLは10秒のstatement timeoutを設定し、処理済みページ内位置だけを進める。Notionの1万件上限は作成時刻境界で続きを取得し、同時刻の上限停滞は未完了として監視する。失効cursorは同じ境界から再開する。

## 再開・保留・監視

Gmail側は180秒以内で期限済みジョブを順に処理し、各ジョブは1回最大10通に制限する。1件の取得失敗・共有鍵競合でも他ジョブへ進み、同じ実行で同じジョブを繰り返さない。検索IDと次ページtokenを先に永続化し、各通の保存後にだけ未処理IDを減らす。失敗は未処理分から再開し、失効tokenは同じ固定期間を最初から走査して既存IDを除外する。確定404は消失IDを私有DBに記録して残りの走査を続行するが、終端はdoneではなくblockedとし、取得不能の確認を残す。ページtoken失効のリセット回数も永続記録する。

処理前に連絡先が有効でメールが変わっておらず、同じメールの候補が正確に1件であることを確認する。取得中のメール変更も保存前に再確認する。候補重複・原本変更・連携なしは保留し、自動的に別連絡先へ付け替えない。統合済み旧IDと統合進行中も処理前に保留し、保存直前は既存のページ共有ロック内で旧ID/統合状態・原本を再確認する。統合先への自動付替えは行わない。

監視は `gmail_late_registration` の専用項目。本文・宛先・個別IDは出さず、候補・期限内待機・期限済み・保留の件数を分けて出す。active時に各ジョブ自身の進捗が30分止まった場合、失敗時、恒久保留時だけpendingとし、baselineの期限済み予約は参考件数にする。最古の未解消対象を示すハッシュを保持し、新しい保留の追加で警告年齢をリセットしない。巡回が30分進まない、巡回失敗が残る、DBを読めない場合はunknown。通常同期の共有鍵競合はジョブの再試行待ちとし、巡回失敗にしない。通常の2日待機は異常にしない。期限済み条件はジョブ検索のLIMITより前に適用し、待機100件で再開対象が隠れないようにする。監視には運転modeとbaseline_completeも出し、収集のみの状態と通常運転を区別する。監視通知は既存の継続再観測ロジックを使う。件数カウンターは確認済み処理の累計で、保存応答消失時の厳密な挿入数はEmailLogを読戻して確認する。

## 配備・限定実物検証・運転切替

1. 追加migrationを適用しコードを配備する。`GMAIL_LATE_REGISTRATION_ENABLED` が厳密に `true` でなければ、cronはDB/APIに触れずdisabledで返す。importにも処理開始の副作用はない。
2. `ENABLED=true`、`GMAIL_LATE_REGISTRATION_MODE=baseline` で初回巡回する。MODE省略もbaseline。基準値の収集と新規変更の予約だけ行い、通常ジョブのGmail取得・保存はしない。
3. `GmailContactDiscovery.data.initial=false` と `lastCompletedAt` で初回完走を確認する。ページ途中や上限停滞を完走扱いにしない。
4. 承認済み1〜5ページに限り `enqueue_selected(page_ids, after=..., before=..., client=..., apply=False)` で試算する。期間は明示し365日以内・2日以上前とする。`apply=True` 後、`run(job_ids=投入結果["ids"])` で投入したジョブIDだけを処理する。ID指定時はselected世代も条件とし、同じページの自動365日ジョブは選択しない。巡回や他ページのジョブは動かさない。同一対象・期間の再投入はdoneを含め無視する。
5. 初回実物は既保存メールを含む狭い区間とし、Gmail検索→既存ID除外→終端記録を確認する。既完了メールを再insertした実績には数えない。未保存対象がなければ、新ジョブ経由の本番insert枝は未検証と書く。隔離DBの実insert回帰と既存経路の5件復旧は別の証拠として扱う。
6. 初回完走・限定検証後にMODEをactiveへ変更する。自動ジョブは予約時の2日待機を満たしてから処理する。activeでもbaseline未完了なら通常ジョブは起動しない。自然観測14日と移管後72時間は別条件のまま。

cron URLは `/api/cron/gmail-late-registration`。既存のcron認証を使用し、運転状態の変更は環境変数経由に限定する。ジョブの保留理由を調べずにstateを戻したり、readyAtを過去に書き換えたりしない。

## 候補・保留の明示判断

`review_held_job(job_id, client=...)` は候補または保留1件を再読し、現在の連絡先メール・一意性・統合状態とジョブ内容を合わせたfingerprintを返す。原本変更を推測して自動的に再開しない。判断後は同関数に `action="retry"` または `"dismiss"`、`actor`、根拠の `reason`、試算した `expected_fingerprint` を渡す。worker共通鍵とページ共有鍵を取得し、同じ現物であることを再確認してから、判断者・根拠・時刻・元状態・消失IDをDBの監査履歴へ保存する。試算後の変化、一時API失敗、同時実行は適用せず再試算する。応答の `state` は適用後の状態（試算では現状態）、`prior_state` は判断前の状態を示す。`fingerprint` は判断時に照合した適用前の証跡であり、適用後の状態の指紋ではない。

retryは現メールが同一かつ一意・有効・統合対象外の場合だけ許可する。期間・readyAtは変えない。404の消失確認を再試行するときは消失IDだけを再確認する。dismissは「確認不要になった」という明示判断を残す終端で、完了したとは数えない。done・dismissed・pendingの再開は禁止し、古いworkerの保存も終端状態を上書きできない。SQLで直接stateを書き換えない。

候補には自動集計による更新も含まれ得るため、変更前メールの根拠を確認してからretryし、他項目更新だけと確認できたものはdismissする。担当者のGmail連携を後から追加した場合、その前から存在する全連絡先は自動で過去回収しない。対象と期間を別途判断して既存の明示過去取込手順へ渡す。
