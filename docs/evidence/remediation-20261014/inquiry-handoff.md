# 問い合わせ入口の保存と引継ぎ

Notion直接保存後に通常同期への明示引継ぎがなく、自己書込みの通知に依存する構造だった。対象18件は同じ連携による保存・未対応を確認したが、Notion配信履歴と本番の自己通知除外設定は未取得で、未配信理由は未証明。入口の4項目（名前・メールアドレス・携帯番号・取引先マスター）を明示的に渡す。

- 会社の完全一致が2件以上なら関連を付けない。連絡先のメール、または会社＋名前の複数候補も先頭を採用しない。
- Notion新規POST前に`HubCreationAttempt`へ`inquiry_notion`予約を確定する。結果不明の予約を自動再POSTしない。APIから確定IDを受け取ったものだけ記録する。
- `InquiryHandoff`に保存予定の4項目差分を先に記録する。保存後の通常同期失敗は、再送で空欄追記差分がなくてもこの記録から再開する。既存の非空欄は上書きしない。
- Zoho未対応で会社が未確定、またはNotionの明示「姓」欄がない場合は、新規作成せず`notion:<page_id>`の正規保留と理由を残す。姓名を推測分割しない。問い合わせ由来の会社未確定は後日の通常通知でも新規作成しない。
- 既存対応へ送る際も記録した差分だけを渡す。保存後に原本値が変わっていたら古い差分を配送せず確認待ちにする。
- 応答に`sync.state`と理由を返す。DB障害はHTTP500。監視の`registration_holds`は作成前保留・結果不明予約・問い合わせ引継ぎを通常の項目未完了とは別に集計し、読取失敗はunknown。
- 固定対象の復旧は`enqueue_existing_inquiry(page_id, properties, contact=..., wiring=..., additional_hold=...)`を使用する。現在値と根拠を確認した対象だけを渡す。同じ差分が完了済みなら再配送しない。

Web接客入口はNotion内限定のまま。今回変更しない。配備はDB migration → APIの順で行い、実データ復旧と読戻しは別の証跡に残す。

レビューでの追加対策：既存ページの空欄判定・保存は通常同期と同じページ単位の排他内で再読して行う。保存予定と問い合わせ由来の印は同じDBトランザクションで確定する。配送・新規作成もページ排他取得後に原本を再確認し、保存時から変わっていれば停止する。複数連絡先候補は入力識別子の保留へ載せ、候補を書き換えない。確定対応後の成功時は、この入口と同じ理由のZoho保留のみ終端にする。

監視APIの追加項目はGAS側も同時配備する。`registration_holds`は登録保留と引継ぎの件数（実レコードの重複なし件数ではない）、最初の登録時刻、最古の対象を識別するハッシュを返す。同じ対象の保留が次回観測でも残れば専用の警告とし、受信未着の説明に混ぜない。

Zoho保留の由来理由は`zohoHoldReason`として同期状態と別に保持する。同じ差分の再投入・新しい差分の保存・項目配送の一時保留を経ても由来を失わず、現在のZoho保留がその理由と一致し、対応IDが確定し、配送が成功した場合だけ終端にする。

外部レビュー対応：完了済みの保存先も、保存前と完了返却前にアーカイブ・ゴミ箱・統合旧IDを確認し、該当時は入力を保持したまま保留へ戻す。正本を推測して再作成しない。復旧関数はpageIdに一致する既存台帳をそのsourceKeyで再開する。曖昧候補の入力4値は`inputPayload`へ保持し、確認後は同じ入口へ再投入できる。同名候補を会社で一意に同定できない場合も作成を保留する。通常通知と問い合わせ入口は、会社一意・明示姓の新規作成条件を共有する。

## 手入力後の保留解消

会社・明示姓をNotionへ補完しただけでは、問い合わせの引継ぎ台帳は完了にならない。担当者が保存先の同一性と補完値を確認した後、対象ページIDと確認済みの4項目差分だけを`enqueue_existing_inquiry`へ渡す。関数は既存の未完了sourceKeyを再開し、確定ID・原本一致・配送成功・由来理由一致を確認して終端にする。完了済み行は異なる差分を渡しても再開しない。新たな変更は通常の入口から扱う。

返却stateだけでなく、対象のInquiryHandoffがdoneで、入口由来のHubCreationAttempt保留が解消し、別理由の保留が保持されていることを読戻す。結果不明予約や同定不足は、この手順でも自動作成・統合しない。保存先が404なら入力を保持してblockedとし、同じページを再作成しない。一時障害は永続保留を残してエラーを返す。
