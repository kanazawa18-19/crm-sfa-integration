レビュー結果（基準 9b258d4 との差分）

差分外のコード（HubCreationService の後続処理、Dispatcher からハブ作成への受け渡し、journal.dismiss_hold の状態遷移、record_sync_lock の実装）は見えていません。そのため、該当する指摘には「要確認」の前提を付けています。

区分	件数	主な領域
BLOCKER	1	問い合わせ保存先の固定化
WARN	12	保留の解除経路、監視の誤警告・互換性、GAS走査の恒久停止、証跡の欠落
INFO	6	遅延集計の既定値、スキーマ差分、テスト不足

――――――――――――――――
BLOCKER

B1. 完了済みの保存先ページを無検証で再利用している
場所：InquirySession.saved_page と handler の if saved: 分岐
条件：同じメールで以前に問い合わせがあり、その連絡先が後から Notion 上でアーカイブ・ゴミ箱移動・重複統合（片方の削除）された場合です。
実害：saved_page は InquiryHandoff の状態が done でも pageId を返すため、_exact_ids による「アーカイブ除外・一意性確認」を通らずに旧ページへ書き込みます。結果は二通りです。
・更新差分がある場合：アーカイブ済みページの更新が Notion に拒否され、毎回 500 になります。以後、そのメールからの問い合わせは恒久的に保存されません。
・差分が空の場合：stage が早期 return し、deliver は done を返します。200 応答で削除済みページの ID が返り、問い合わせは失われます。
どちらの場合も InquiryHandoff は done、または例外でロールバックされるため、registration_holds に現れず監視で検知できません。旧実装は毎回メールで再検索していたため、この経路は退行です。
修正案：saved_page が保存先を固定するのは、作成予約が reserved/created のまま InquiryHandoff が done になっていない「途中再開」の場合に限定してください。done 後の新しい問い合わせは毎回 _resolve_existing_contact で解決し、pageId が変わる場合は stage の「保存先が競合」を新しい行として扱う設計にしてください。途中再開であっても、get_raw_page で archived/in_trash を確認し、該当すれば保留にする必要があります。

WARN

W1. 復旧関数のキーが入口と異なり、元の保留が残り続ける
場所：enqueue_existing_inquiry（キーは inquiry-recovery:<page>）
条件：入口で会社未確定や姓未入力により blocked になり、人手で修正した後に復旧関数を 1 回だけ実行した場合です。
結果：
・元の InquiryHandoff[inquiry:<hash>] は blocked のまま残ります。
・復旧行の zohoHoldReason は NULL のため、zoho_hold.reason == row.zohoHoldReason が成立しません。入口が残した Zoho 保留（notion:<page>, zoho, blocked）は resolve されません。
・registration_holds は pending を継続し、恒久的な誤警告になります。テストは復旧関数を 2 回呼び、1 回目で自分の理由を記録しているため、この経路を検出できていません。
修正案：復旧関数は pageId で既存の InquiryHandoff 行を探し、その sourceKey で処理してください。あるいは、入口行の zohoHoldReason を引き継いでください。

W2. 曖昧保留で問い合わせ内容が CRM のどこにも残らない
場所：InquirySession.ambiguous → stage(None, {})
結果：保存されるのはハッシュ化されたキーと理由だけで、会社・名前・メール・電話は保存されません。handler は 200 を返すため、lead-researcher 側は完了扱いになります。監視には「誰の問い合わせか」が分からない保留が 1 件（HubCreationAttempt と合わせて 2 件）残り、運用者は対応できず解除もできません。
修正案：保留行に入力 4 項目を保存してください（他の行は既に電話・メールを保存しているため、方針上の差はありません）。あわせて、手動解除または再投入の手段を用意してください。

W3. 通常同期のハブ作成ガードに「姓」の条件がない
場所：HubCreationService の inquiry 判定（取引先関連の件数だけを確認）
条件：会社が一意に解決した問い合わせで新規作成された連絡先です。create_props に 姓 は含まれません。
結果：deliver は姓の欠落で保留にしますが、作成直後に届く Notion の通常 Webhook はガードを通過します。require_notion_fields が 姓 を必須にしていなければ、名前から姓を推定して Zoho に新規作成される可能性があります。
修正案：ガード条件を deliver と共通の関数にまとめ、「取引先が 1 件、かつ姓の明示入力あり」の両方を判定してください。テストにも、姓のないケースと会社が一意のケースの組み合わせを追加してください。

W4. ‘source_changed_after_handoff’ の伝播先が未検証
場所：HubCreationService.handle の戻り値 → Dispatcher → deliver
懸念：deliver が保留と判定するのは result.skipped or has_partial_skips の場合だけです。ハブ作成がこの文字列を返したときに Dispatcher が skipped/partial に変換しなければ、Zoho が作成されていないのに done となり、inquiry_handoff の保留も解除されます。
修正案：Dispatcher での変換を明示し、deliver → 実 Dispatcher → HubCreationService を通す結合テストを 1 本追加してください。

W5. 原本照合の値表現が 3 経路で異なる
場所：deliver（contact.get_page）、Dispatcher（get_record）、HubCreationService（_creation_properties）
懸念：関係 ID のハイフン有無、タイトルの文字列とリストの違い、空値（None と ‘’）などが経路ごとに異なると、変更がなくても常に「保存後に変更」または source_changed と判定されます。保留が解除されず、恒久的な警告になります。テストはすべてフェイクで、同じ表現を前提にしています。
修正案：比較前に共通の正規化関数を通してください。実クライアントの応答例を使った固定テストを追加してください。

W6. registration_holds の監視が、正常な作成中を unknown と判定する
場所：registration_health の 'unknown' if counts.get('reserved')
結果：通常の作成処理（reserve → create → finish）や inquiry_notion の作成中に毎時監視が重なると、unknown になり誤警告が出ます。
修正案：reserved は一定時間（例：10 分）以上経過したものだけ unknown にしてください。
あわせて要確認：journal.dismiss_hold が行を削除せず、created 以外の状態（dismissed など）を残す実装の場合、state<>'created' の集計に完了済みの引継ぎが永続的に含まれます。

W7. 監視の後方互換性がない
場所：webhook_health.py は registration_holds を常に追加しますが、旧 GAS の validate は OPTIONAL_KEYS に unfinished_sync しか持っていません。
結果：サーバーを先にデプロイすると、旧 GAS が「診断項目が不正です」で応答全体を拒否します。毎時監視が全項目停止し、目的にある「既存の毎時監視と互換」を満たしません。
修正案：GAS を先にデプロイする手順を明記してください。または、サーバー側で項目追加をフラグやクエリパラメータで段階的に有効化してください。

W8. GAS 走査が 4xx 拒否で恒久停止し、自動回復しない
場所：ingest.js の終端・開始の送信と observation.validate/record
条件：
・ページ送り中の Gmail 側の変動（ラベル変更や移動など）で同じ ID が別ページに再出現すると、len(set(ids)) != count で complete が恒久的に 400 になります。terminalPending のまま毎回同じ拒否を受け、成功位置が進みません。
・長期停止で before - after > 31日 になると、started が毎回 400 になります。
結果：DRY_RUN 中は観測が止まるだけですが、本番取込みに切り替えた後は新着の取り込みも止まります。自動回復するのは 404 の経路だけです。
修正案：
・サーバー側で ID を重複除外して件数を数え、重複を evidence に記録してください。
・決定的な 4xx（内容の競合、範囲不正、件数不一致）を受けたら、GAS が走査を放棄し、カーソルを削除して新しい走査に移り、警告を出すようにしてください。
・長い範囲は 31 日以内に分割してください。

W9. 確定 404 のメール ID が DB の証跡に残らない
場所：ingest.js の read()（MISSING_MESSAGE_IDS はスクリプトプロパティにのみ保存）
結果：要件の「メール ID 欠落」を DB で追跡できません。比較スクリプトでは、該当メールが crm_not_seen_by_gas として理由なく現れます。プロパティは容量上限 1000 件で例外を出し続けるだけです。
修正案：消失を記録するフェーズ（例：phase ‘missing’）を追加して DB に記録し、比較スクリプトで区別してください。

W10. 旧ログが自然観測として数えられる
場所：compare_gmail_gas_ingest.py の entry.get('observationKind', 'natural')
結果：旧 GAS のコンソールログ（過去に実施した遡及走査を含みうる JSONL）を入力すると、自然観測として採用されます。要件の「過去バックフィルを自然観測に数えない」に反します。
修正案：natural として扱うのは observationKind と scanId を持つ行だけにし、欠けている行は除外件数として出力してください。

W11. 名前によるフォールバックで重複が作成される
場所：_resolve_existing_contact の名前経路
条件：メールなしの問い合わせで、同名の既存連絡先の取引先関連が空の場合です（過去に会社未確定で作られた問い合わせ連絡先が典型です）。もう一つは、会社が未確定で同名候補が存在する場合です。
結果：いずれも新規作成されます。目的の「曖昧な候補では新規作成しない」に対して、同名候補を曖昧として扱っていません。
修正案：同名候補が 1 件以上あり、会社で確定できない場合は ambiguous として保留にしてください。

W12. 外部処理中に DB トランザクションと行ロックを保持している
場所：observation.record（process() を FOR UPDATE のトランザクション内で実行）
結果：10 通分の Notion 照会や本番取込みの処理中、トランザクションを開いたままになります。idle_in_transaction などのタイムアウト設定があると、副作用の完了後に記録だけが失敗します。本番取込みでは、再送時に再処理されます（メール単位で冪等なら実害は限定的です）。
修正案：「処理中」を予約するフェーズを別トランザクションで確定し、処理後に結果を記録する 2 段構成を検討してください。少なくとも、DB のタイムアウト設定との整合を確認してください。

INFO

I1. 比較スクリプトの遅延集計は、--latency-start を省略すると end が既定値になり、遅延サンプルが常に 0 件になります。自然観測では、指定を必須にするか未指定時にエラーにするほうが誤読を防げます。初回走査（成功位置なしで 2 日分を遡る）は kind が natural になるため、開始日時の指定は必須の運用になります。

I2. Prisma の @default(now()) とマイグレーションの clock_timestamp() が一致しないため、migrate diff でドリフトとして検出されます。コードは常に receivedAt を渡しているので、どちらかに揃えて問題ありません。

I3. 作成直後の Notion Webhook との競合について。create_page_once から stage(page) で由来の印を書き込むまでの間に通常の Webhook が届くと、inquiry ガードは効きません。現状は取引先マスターの必須チェックで止まる見込みですが、W3 と合わせて、ハブ作成側が inquiry_notion の作成記録（externalId）でも由来を判定できるようにすると確実です。

I4. 既存連絡先への「空欄なら埋める」判定は Notion の値だけで行っています。Zoho 側に値があっても Notion が空なら上書きされます。2026-08-14 に受容済みのリスクですが、今回の「既存値の上書き」の確認範囲に含まれるため記載します。

I5. Notion の email equals フィルタが大文字小文字を区別する場合、取得後の小文字比較では補えず、大文字小文字だけが異なるメールで重複が作成されます。実 API での挙動を確認してください。

I6. 404 の判定に \b404\b を使う文字列照合は、プロキシ由来など Gmail 以外の 404 も確定消失として扱う可能性があります。error.code だけで判定するほうが安全です。

確認して問題なしと判断した点

・応答紛失時の再送：送信対象の ID 群をカーソル上で固定し、走査 ID・連番・要求ハッシュで同一性を保証し、同時再送は開始行のロックで直列化しています。成立しています。
・成功位置の更新：終端の保存が成功するまで成功位置を進めない設計と、終端だけを再送する経路は正しく動作します。
・同一候補への並行問い合わせ：共有ページロック内で現在値を読み直す方式で、空欄埋めの競合を防げています。
・作成結果が不明な Notion 作成：再作成せずに止める挙動を確認しました。
・自分が残した Zoho 保留だけを解除する条件（理由の一致）は意図どおりです。ただし W1 の経路を除きます。

この変更で整うのは証跡を記録する仕組みまでです。14 日観測とその合格後の 72 時間並走は未実施のため、移管成功の根拠にはなりません。この点は前提どおりです。優先度は B1、W1、W8、W7 の順で対応することを推奨します。
