結論として、未解決の BLOCKER はありません。採否表の根拠は概ね妥当です。残る懸念は運用上の停滞と誤警告に関する WARN 4 件で、ほかに確認事項が 2 点あります。Gmail の 14 日観測と 72 時間並走は未経過であり、今回の結果を移管成功の根拠にしない点は前提どおりです。

確認事項（コードを確認すれば済むもの）

戻り値の扱い：「SkipTrackingDispatcher は hub_creation_complete 以外を skipped にする」という説明では、作成が不要な既存連絡先で返る None の扱いが読み取れません。None も skipped になる場合、対応表が揃った既存連絡先への問い合わせ配送が常に blocked になります。None はそのまま通すことをコードかテストで確認してください。
変換関数の同一性：service.py は parse_notion_property_value を notion_webhook から import し、lead_inquiry_webhook と notion_client は clients.notion_client 側を使っています。両者が同じ関数オブジェクト（再エクスポート）であることを確認できれば、W5 の不採用根拠は確定します。

残る WARN（いずれも重大な実害ではなく、停滞または誤警告）

W-a. 保存先が取得できない場合に毎回 500 になる
場所：check_page の例外経路
条件：ゴミ箱の保持期間が過ぎて完全削除されたり、統合の権限が外れたりして、get_raw_page が 404 などで失敗する場合です。
結果：保留と inputPayload は残るので気づくことはできます。ただし、同じメールからの問い合わせは以後すべて 500 になり、送信元の再送も失敗し続けます。
修正案：404 は「確定した消失」として、アーカイブ済みと同じく blocked で 200 を返してください。例外として扱うのは一時的な障害だけにします。

W-b. 消失通知の再送で内容が食い違うと走査が止まる
場所：ingest.js の read() と observation の eventId（scan:missing:連番）
条件：missing の保存が失敗した後、再実行までの間に同じページ内のより前のメールも削除されると、同じ連番で別の ID を送ることになります。
結果：内容の競合として 400 になり、カーソルが破棄されないまま毎回同じ 400 が続きます。発生頻度は低いものの、自動では回復しません。
修正案：eventId を消失 ID ごとにする（scan:missing:<id>）か、固定した ID 群の中で消失した ID をまとめて送ってください。

W-c. 手動で解消した後も監視の警告が残る
条件：会社や姓が欠けていて保留になった後、担当者が Notion 上で入力を補った場合です。
結果：通常通知の経路で Zoho は作成されますが、InquiryHandoff の行と inquiry_handoff の保留は blocked のまま残ります。復旧関数を実行するまで、registration_holds が警告を出し続けます。
修正案：手順書に「補完後に enqueue_existing_inquiry を実行する」と明記してください。または、HubCreationService が作成を完了した時点で、該当する問い合わせの保留を照合して解除するようにしてください。

W-d. 復旧関数が完了済みの行も再び開く
場所：enqueue_existing_inquiry
内容：同じ pageId に紐づくすべての行に、渡した properties を stage します。そのため、done の行も pending に戻って再配送されます。配送は冪等なので実害はありませんが、意図した動作かどうかを確認してください。done の行を対象から外すほうが安全です。

INFO
・remember_payload は同じキーで再度問い合わせがあると inputPayload を上書きします。同じ人から保留中の問い合わせが複数届いた場合、以前の入力は残りません。履歴が必要なら追記型にしてください。
・W11 の採用により、よくある姓名の問い合わせは同名の候補が 1 件あるだけで保留になります。運用での確認件数の増加を見込んでおいてください。
