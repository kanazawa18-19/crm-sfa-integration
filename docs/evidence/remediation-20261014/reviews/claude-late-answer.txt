結論として、BLOCKER はありません。重複保存や既存値の上書きにつながる経路は見当たりませんでした。保存は ON CONFLICT による一意制約の範囲に閉じており、副作用のない insert_email_logs だけを使い、保存直前に共有ロック内で原本を再確認しています。ただし、運用開始直後から監視が恒常的に警告状態になる構造と、下書きの誤取込みがあります。有効化前に WARN の 1〜4 を直すことを推奨します。本番では未検証という前提で評価しています。

WARN

1. 下書き・チャットが検索から除外されていない
場所：query_for（`-in:spam -in:trash` のみ）
条件：担当者のメールボックスに、連絡先宛ての未送信の下書きが 365 日以内に残っている場合です。
結果：下書きも From が担当者・To が連絡先なので、classify_message は outbound と判定し、送信済みメールとして EmailLog に恒久保存されます。返信ラグなどの集計が汚れます。GAS 側は `-in:drafts -in:chats` を付けているので、経路間で扱いが食い違っています。
最小修正：`-in:drafts -in:chats` を追加し、検索条件を固定するテストを足してください。既存の backfill_gmail_history.py も同じ検索条件なら同時に直してください。

2. 初回巡回中に自社システムが書き込むと、解除できない blocked ジョブが大量に生じる
場所：observe_batch の baseline_unknown
条件：初回巡回は 5 分ごとに 100 件ずつ進むため、連絡先が数千件あると完走まで数時間かかります。その間に、Gmail 同期による最終メール日時の更新、通常同期による反映、同期メモの書き込みなどで last_edited_time が更新されたページは、すべて「担当者数 × 1 件」の blocked ジョブになります。
結果：
・メール変更の有無が不明な候補が、運用初日から数十〜数百件たまります。
・解除手順が文書化されておらず、「state を戻さない」という方針もあるため、残り続けます。
・health は blocked をすべて件数に含めるため、registration 系と同じく警告が固定されます。
最小修正：この候補は blocked ではなく別の状態（例：candidate）として記録し、health では警告ではなく参考件数として出してください。確認して不要と判断したものを監査付きで終了させる関数と手順もあわせて用意してください。

3. blocked の出口がなく、監視の指紋が新しい保留を隠す
場所：health の fingerprint（最古の 1 件の ID だけを使う）、process_job の各 blocked 経路
条件：統合の進行中（一時的な状態）、担当者の連携解除、Notion の 404、候補重複などで blocked になった場合です。
結果：
・統合中という一時的な理由でも永続的に blocked になり、自動で再開しません。
・最古の blocked が残っている限り指紋が変わらないため、後から増えた blocked や処理の停滞は「同じ警告」とみなされ、24 時間ごとの再通知に埋もれます。
最小修正：
・指紋を「未完了ジョブ ID の集合のハッシュ」に変え、新しい保留が出れば再通知されるようにしてください。
・統合中など一時的な理由は pending のまま reason だけを記録して再試行にし、恒久的な理由とは状態を分けてください。
・blocked を確認して終了・再開する公式の手順（関数）を用意してください。

4. 処理量が 1 回の起動につき 1 ジョブ 1 ページ（10 通）しかなく、通常の滞留が警告になる
場所：run の `processed=1; break`
条件：CSV で数百件の連絡先を取り込む、担当者が複数いる、1 連絡先あたりのメールが多い、のいずれかに当てはまる場合です。例えば 300 件 × 担当者 3 名なら 900 ジョブで、最短でも 900 回の起動、約 75 時間かかります。
結果：
・回収が大幅に遅れます。
・health は「待機期間を過ぎた未完了」を pending として出し、最古のジョブが 48 分以上残れば警告になります。正常に処理が進んでいても警告されます。
・baseline 運転のまま 2 日以上過ぎた場合も、待機期間を過ぎたジョブがたまり、同じく警告になります。
最小修正：
・deadline に達するまでジョブを順に処理するループにしてください。
・health は処理が進んでいるかどうか（最終進捗時刻）で判定してください。滞留件数だけで pending にしないようにします。
・baseline 運転中は、待機期間を過ぎたジョブを参考情報として出してください。

INFO

・Notion の時刻は分単位です。created_time と last_edited_time は分単位に切り捨てられるため、cutoff と同じ分に作成・編集されたページは baseline 扱いになり、回収対象から漏れます。cutoff を分の先頭に切り捨ててから記録してください。
・メール検索の大文字小文字：一意性の確認は小文字化したメールで Notion の equals フィルタを使っています。Notion 側が大文字小文字を区別する場合、大文字を含むメールで登録された連絡先は候補 0 件と判定され、恒久的に blocked になります。実 API での挙動を確認してください。
・連携が失効した担当者：refresh_token が失効すると（invalid_grant）、毎回例外になり error が立ち続けます。監視には現れますが、ジョブ単位で「担当者連携の再認証が必要」と記録して blocked にするほうが原因を特定しやすくなります。
・欠落 ID の重複記録：保存後の応答が失われて再試行すると、404 になった ID が missing に二重に追加されます。追加前に重複を確認してください。
・後から連携した担当者：巡回時点の担当者でしかジョブを作らないため、後から連携した担当者の過去メールは対象外です。既存の backfill 手順で扱うことを文書に追記してください。
・関数の実行時間：deadline は 180 秒です。このルートの最大実行時間を 200 秒以上に設定していることを確認してください。
・テストの不足：record_guard の実ロックと、run の運転モード分岐（baseline・active・ID 指定）を DB で通す試験がありません。fixture で両方を差し替えているためです。

確認して問題なしと判断した点
・既定で無効：環境変数が厳密に true でない限り、DB にも外部 API にも触れません。
・巡回の途中再開：Notion の応答を固定し、20 件ずつ原子的に確定してページ内の続きから再開します。失効した cursor は同じ境界から再開します。
・Gmail 取込の再開：ID を先に固定し、1 通ずつ保存してから進めます。保存済みの ID は再取得も再保存もしません。
・保存直前の確認：共有ロック内で旧 ID・統合状態・原本を再確認しており、統合先への自動付け替えもしません。
・限定投入：世代 selected と ID を指定することで、同じページの自動ジョブを巻き込みません。
・待機条件：期限済みの条件を LIMIT より前に適用しています。
・監視出力：本文・宛先・個別 ID を出していません。
・GAS 側：domain.js は 9 項目の応答に対応済みです。
