判定：BLOCKERが1件、WARNが5件あります。BLOCKERは担当者対応の既存同期（更新）経路で、新規登録用に設けた「代替担当者」と「任意欄は空欄」の規則が、既存レコードの更新にもそのまま適用されてしまう問題です。

区分	箇所	到達経路と欠陥	修正案
BLOCKER	owner_payload（kintone_sync と zoho_sync の通常更新）	通常同期で、Notionの担当メンバーが対応表にない1名（例：対応表への登録前の新入社員A）の場合を考えます。kintone側では、_to_kintone_payload が required=True で呼ぶため代替本人が選ばれ、kintoneに正しく入っている既存の営業担当者が代替本人で上書きされます。Zoho側では、required が既定の False なので owner_to_external が None を返し、payload に {'Owner': None} が入ります。Ownerは必須なので、その更新は拒否されて同じイベントの他項目も送られないか、Ownerが消えます。さらにkintoneの全項目通知で代替本人が戻ってくると、Notionの担当メンバーも[A]から[代替本人]に置き換わります。「推測割当を行わない」に反します	代替本人と空欄化は新規登録（ZohoCreationAdapter/KintoneCreationAdapter）の必須欄だけに限定する。通常の更新では、対応が取れない場合は常に UNRESOLVED として当該欄を送らず、unsupported として報告する
WARN-1	zoho_webhook の Owner受信	Notionの担当メンバーが[A, B]の場合、送信時は複数なので保留され、ZohoのOwnerはAのままです。この状態でZoho側がOwnerをCに変えると、通知で Notion が[C]になり、Bが消えます。送信側の「単一欄へ縮約しない」規則と対になっていません	Notion側が複数担当の場合、単一Ownerの受信は保留する（サイトコントローラーの代表値の扱いと同じ考え方）
WARN-2	sync_review の writer.plan（担当メンバーの削除承認）	Notionで担当メンバーを空欄にして最終承認すると、Zohoへの書込みは Owner=None で必ず失敗し、申請は failed で止まります。kintone側は代替本人が書き込まれます。画面は「他のツールのこの項目も空欄になります」と表示するので、実際の結果と一致しません	Owner等の必須担当者欄は削除承認の対象外とする（supported=False で保留）。または代替を行うことを画面で明示し、Zohoも同じ規則にする
WARN-3	hub_creation service（アクションのrollup）	creation_rollup が None（has_more や未対応型）の場合も、properties に既にある担当営業・提案サービスは残ります。汎用の変換がrollupの一部だけを入れていると、kintoneの '担当営業' not in properties の検査を通過し、未確定の値で登録されます	None の場合は properties.pop(name, None) で消し、必須不足として保留させる
WARN-4	重複確認の上限と常時保留	kintoneの案件は店舗名が同じなら無条件に保留になるため、既存施設の契約延長や追加提案の案件は必ず保留されます。Zohoの連絡先は一覧を2000件まで照合し、それを超えると全件保留になります。どちらも解除画面が別実装であるため、登録経路として事実上止まります	実際のZoho連絡先件数と、同名案件の比率を実測する。反映前に解除手段を用意するか、該当経路を無効にしておく
WARN-5	反映順序の強制がない	完了予定日・作成日・新規・既存種別・リードソース1・商品カテゴリー・先方担当者・姓・名の受信先は、Notionにまだ存在しません。製品コードを先に配備すると、Zohoで完了予定日が変わるたびに存在しないプロパティへの書込みになり、案件更新が失敗します。以前は契約日 / 予想契約日に入っていた値も、そちらには入らなくなります	起動時か書込み前に、専用欄の存在を確認する。存在しなければ、その欄の写像を無効にして旧挙動を維持する
INFO-1	zoho_webhook	resolved_notes と unresolved_note の import が差分に見当たりません。無い場合、Ownerを含むZoho通知がすべて NameError になります	import の有無と、Owner経路のテストを確認する
INFO-2	受信ラベル「作成日時」	Zohoの標準Created_Timeの日本語ラベルは通常「作成日時」なので、スキップされる Created_Time と重なり、field42 の受信が効いていない可能性があります	field42 の実ラベルを確認する
INFO-3	sheet_properties	複数選択の「A, B」のような区切り文字列は、1つの値として選択肢外と判定されて保留されます	既存のシート入力の形式との互換性を確認する
INFO-4	prepare_creation_fields	通常の列追加に ensure_sync_key_column を使っています	同期キー列としての副作用（位置や保護など）がないことを確認する

問題ないと確認した点は次のとおりです。

連絡先の姓・名は、フルネームから分割せず専用欄の値だけを使っています。
Zohoのlookupは対応表のIDだけで解決し、関連が複数ある場合は保留します。
複数選択は、1要素でも選択肢外なら全体を保留します。
Zohoの完了予定日と契約日を別欄に分けており、既存値の一括変更もしていません。
必須項目はAPIから都度取得し、不足していれば保留します。
schema追加スクリプトは、表示したhashと一致する場合に不足欄だけを追加し、既存欄の型や関連先が異なれば停止します。
