3. 共有メール・CC受信における実施者（actor）の取り違えと誤判定

該当箇所: src/email_review/domain.py 27行目（participants）、src/email_review/service.py 107行目（process）

問題点:

participants の送信（outbound）判定が any(address.lower() == owner.lower() for _, address in sender) となっており、owner 1名のアドレスしか確認していません。自社の同僚が顧客へ送信したメール（自社送信・担当者CC）を受信した場合、送信元が owner と異なるため 「受信（inbound）」と誤判定 されます。その結果、自社同僚の本文から「相手の署名」として自社名が抽出され、誤紐付けの原因になります。

共有メールや同一メールを複数人で受信した場合、先に取り込んだ担当者のメールアドレスが row["owner"] に固定されます。その後、別の営業担当者がSlackや管理画面で手動確定（confirm）しても、process 内では actor_id = self.gateway.actor(row["owner"]) となっており、実際に操作した担当者ではなく最初に取り込んだ row["owner"] のNotionアカウントで記録が作成 されます。

修正案:

送信判定は owner 単体ではなく、差出人のドメインが internal_domains に含まれるかどうかで判定してください。

記録作成の実施者は、手動確定の場合は row.get("actor")（または操作時の認証ユーザー）を優先し、自動確定の場合のみ row["owner"] を用いるよう分岐してください。

4. find_action の厳密一致失敗による結果不明（unknown）レコードの永久固定化

該当箇所: src/email_review/gateway.py 115行目〜127行目（find_action）、src/email_review/service.py 130行目〜140行目（reconcile）、src/email_review/domain.py 96行目（decide）

問題点:

find_action 内の any(current.get(key) != value for key, value in expected.items()) で全プロパティの完全一致を要求しています。しかし、Notion APIから再取得した値（ISO日時の秒・タイムゾーン表記、リレーション配列の形式など）と送信時の辞書表現にわずかでも差異があると常に不一致と判定され、find_action が None を返します。

reconcile で find_action が None を返すと state="unknown" のまま更新され、「再登録は行いません」と記録されます。

さらに domain.decide では state == "unknown" の行に対して action != "reconcile" の操作（手動での再照合や強制確定）を Conflict で拒絶しているため、一度 unknown に落ちて既存記録が見つからなかったレコードは一切の操作を受け付けず、永久にデッドロック（文鎮化） します。

修正案:

find_action はタイトルに含まれる一意の #mail-{row['id'][:12]} を主キーとして存在確認を行い、プロパティの全件完全一致比較に依存しないようにしてください。

reconcile で該当レコードが存在しないことが確認できた場合、管理者が手動で「再照合（resume）」または「対象外（exclude）」に遷移させられるエスケープハッチを domain.decide に設けてください。

WARN（潜在的障害・設計改善が必要な項目）
1. record_lock におけるセッションレベル・アドバイザリロックの解放漏れ

該当箇所: src/email_review/gateway.py 21行目〜30行目

問題点:

pg_try_advisory_lock はセッションレベルのロックです。finally 節で pg_advisory_unlock を明示的に呼んでおらず、conn.close() のみに依存しています。

_connect_direct() の内部実装がコネクションプールを使用している場合、close() は物理切断ではなくプールへの返却となり、セッション上にロックが残留します。結果として、同じレコードに対する以後の同期処理が永続的に RecordSyncBusy で失敗し続けます。

修正案:

finally 節で必ず SELECT pg_advisory_unlock(%s) を実行するか、トランザクションスコープの pg_try_advisory_xact_lock を使用してください。

問題点:

4. BFF / Dashboard における Origin / Sec-Fetch-Site 判定によるリクエスト遮断

該当箇所: dashboard/app/api/email-review/route.ts 13行目〜17行目

問題点:

if (!sameOrigin || site === "cross-site" || site === "same-site") において、new URL(request.url).origin を使用しています。リバースプロキシ環境（Next.js がコンテナ内でポート3000等で稼働している構成）では request.url が http://localhost:3000 となり、ブラウザから送信された headers.origin（例: [https://crm.example.com](https://crm.example.com)）と不一致になって正規のリクエストが403で拒絶されます。

修正案:

プロキシ環境を考慮し、x-forwarded-host / x-forwarded-proto を反映させたオリジン比較を行うか、標準的なCSRFトークン検証方式に改修してください。

5. スレッド一括更新（capture）におけるデッドロックの可能性

該当箇所: src/email_review/repository.py 69行目〜73行目

問題点:

thread_id に属する EmailReview を一括で state='new' に更新するクエリ（UPDATE "EmailReview" ... WHERE id IN (...)）で、更新行のソート（ロック取得順序の固定）が行われていません。

修正案:

更新対象のIDリストをあらかじめ昇順ソートして取得してから順次ロック・更新するか、一括更新の競合例外をリトライする処理を入れてください。
