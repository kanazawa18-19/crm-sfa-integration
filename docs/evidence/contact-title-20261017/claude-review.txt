総評として、本番反映の前に BLOCKER 2件の対応が必要です。どちらも「対象フラグの状態は変わらない」という前提に依存しています。その前提が崩れると、装飾済みタイトルが外部に流出するか、外部の氏名が消去されます。それ以外の経路（純氏名の読み替え、Webhookでの表示タイトル変更の遮断、新旧混在時のOR検索）は、概ね意図どおりに組まれています。

BLOCKER

ID	ファイル	指摘	理由・推奨対応
B1	src/sync_engine/webhook_handlers/notion_webhook.py、contact_title.py	対象フラグを true→false に戻すと、生タイトルが外部の氏名として送られる	ids=[‘managed’] かつ checkbox=false の場合、canonical_properties は生のプロパティを返します。さらにフィルタ条件 name == NAME and MANAGED in properties が成立するため、「名前」＝「氏名（会社／メール／電話）」が外向きに配送されます。以後も get_page・照合・姓名補完バッチがこのページを旧連絡先として扱うため、装飾タイトルが氏名として流れ続けます。ネイティブAutomationがタイトルを先に、フラグを後に設定する場合も、同じ中間状態が発生します。対応案は次のとおりです。(1) フラグを片方向の遷移に限定する。'managed' が変更IDに含まれ、かつ false の場合は配送せず保留にする。(2) 「フラグfalse・氏名（連携用）が非空・タイトル≠氏名（連携用）」の組み合わせを不整合とみなし、fail closed にする。
B2	同上	既存連絡先のフラグを false→true に変えると、外部の氏名が空値で上書きされる	既存連絡先は氏名（連携用）が空です。この状態でフラグが手動、またはビュー条件の誤りでONになると、canonical_properties は NAME=None を返します。ids=[‘managed’] で配送されるため、外部の実在する氏名が消去されます。「空にされた氏名を復活させない」という意図は、純氏名を明示的に変更した場合に限るべきで、フラグ遷移とは区別する必要があります。対応案は、「フラグがtrueに遷移し、純氏名が空」の場合は NAME を配送せず保留にすることです。既存テストの ([‘managed’], {NAME: '検証 太郎'}) は正常系として残してください。
