## 独立レビュー

動物3体（sec・quality・QA）の最終判定はBLOCKER 0、WARN 0。書き手は1人、レビュー担当はコード変更なし。

修正した主な指摘:

1. Notion書込後、シート配送失敗で案件関連の起票まで到達しない → Notion成立直後に起票。
2. 関連応答が不正でも空配列として上書きできる → 関連型・ID・ページ分割を厳格検証。
3. 案件失注/差替えで未配送義務が消える → 追加計画と配送義務を別表へ分離。
4. 逆関連の反映遅延で旧値を配送して完了する → PATCH前に期待相手IDを保存、観測するまで完了しない。
5. 8回配送保留後もペアが再試行される → 同一transactionで関係ペアも保留し、新規計画へ継承。
6. `not_applicable` の意味が不正確 → `no_delivery_this_run` へ変更。

## 他社モデル

Claude Opus 5.5・中、Gemini思考モードの専用チャットで実施。API不使用。宛先・資料hash・全文照合はmanifest、回答原文は同ディレクトリ。原文のサイドバー・他の会話名は除外した。

両者の逆関連遅延の指摘を独立再現し修正。Claudeの通常同期失敗への波及も修正。追補レビューは両者BLOCKERなし。最後の小差分で資料から `@staticmethod` を抜粋し忘れたためGeminiがself欠落を指摘したが、実ファイル44行には存在し、実PGでも成功。資料不足として訂正を送った。

採否の補足:

- Geminiのlist[str]がAPI不正という指摘は共通Notion変換ラッパーを見落としたもの。実際はrelation/id形式に変換される。
- 保留中でも既発生の未配送を進めるSQLのORは意図した条件。評価の保留判定とは分けている。
- `unconfirmed` の対象行消失を0として正常化する案は不採用。共通キュー例外に変換して失敗を伝播する。通常の並行処理は案件ロックで排他し、手動DELETEは行わない。
- schemaの追加2列は最終Prismaにも存在。migrationは本番未適用の状態で改訂し、使い捨てDBで検証した。
- 既存関連集合は試行ごとに再取得するため、1回の人手削除が永久に古い集合との比較を続けるという指摘は当たらない。
- 連続編集で8回の未確認に早く達する可能性は、データを失わず保留する制約として受容・仕様書に明記。運用担当が原因確認後resume。保留の管理画面通知・操作は別の未実装項目。
- 無変更時の再照合・接続回数・大規模ペアの遅延、外部API呼出中の時間超過、人手編集とAPI書込の競合は残る制約。高頻度大量処理の実負荷試験は未検証。
