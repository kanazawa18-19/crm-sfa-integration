B1　dismiss_hold の存在と例外保護

確認したこと：journal.py の差分にも周辺コードにも dismiss_hold がありません。
再現条件：Zoho由来の新規作成で対応表の保存に成功すると、journal.dismiss_hold が呼ばれます。未定義なら AttributeError、定義済みでも一時的なDB障害で例外になります。
影響：例外で500応答になり、Zohoが再送します。再送時は対応表があるので通常更新に入ります。その結果、対応表成立後に予定していた案件起票・通知・シート行作成・メモが永久に実行されません。重複作成はありません。
最小修正：定義を追加します。新規作成側の呼出しも、通常更新側と同じく例外を握る形にします。

python
if journal is not None:
    try:
        journal.dismiss_hold(source_key, "mapping:notion")
    except Exception:
        logger.warning("作成保留表示の解消を次回へ延期しました source=%s", source_key)

B2　create_page_once の再送

再現条件：Notionクライアントがタイムアウトや5xxで自動再試行する設定です。1回目のPOSTが実際には成功し、応答だけが失われた場合に起きます。
影響：同じ呼出しの中で2回POSTされ、目的1（再POSTの防止）が台帳の外で破られます。
最小修正：create_page_once ではPOSTの再試行を無効にします。模擬試験で「タイムアウト時にHTTP層のPOSTが1回だけ」であることを確認してください。

W1　作成成功後の台帳確定失敗

再現条件：create_once がIDを返した直後に、Postgresの切断などで journal.finish が失敗します。
影響：同じ except に入って「作成結果不明」と扱われ、手元にあるIDが通知にもログにも残りません。人は同名候補から探すことになり、目的2に反します。予約は reserved のまま残るので、W5の全体停止も続きます。
最小修正：try を分けて、IDを必ず残します。

W2　復旧経路の行き止まりが見えない

再現条件は三つあります。
(a) 人が重複と判断して作成ページをアーカイブした後に、Zohoから更新が来る。
(b) get_raw_page が404や通信エラーで例外を出す。
(c) new_record_created_page_mapping_conflict になる。
影響：
(a)(c) は保留行も通知も作らずスキップします。created 予約は監視の集計対象外なので、以後の更新が誰にも見えないまま捨てられます。
(b) は例外が上まで伝わり、500と再送を繰り返します。
最小修正：
available の呼出しを try で囲み、例外は「確認不能」として返します。
三つのいずれでも journal.hold(source_key, "mapping:notion", db_key, "作成済みページ <ID> が利用不可または対応表と競合") を残し、通知します。

W5　未確定予約によるDB全体の停止

再現条件：Zoho→Notionの作成結果が不明で、予約が reserved のまま残っています（人の確認まで残る仕様です）。その間に、同じ db_key で人が作ったNotionページがZohoへの新規作成に入ります。

W6　Notion→Zohoの結果不明による折返し（既存リスク）

前提：journal.conflicts() が確定IDだけで照合しているなら、次のことが起きます。
再現条件：ハブのNotion→Zoho作成で結果が不明になり、target='zoho' が reserved のまま externalId なしで残ります。ロック解放後に、Zohoの新規作成通知が届きます。

最小修正：new_record_guard に、同じ dbKey で target='zoho'・state='reserved'・externalId IS NULL の行があれば保留にする判定を加えます。W5の関数と同じ形で、W5と同じ絞り込みを入れます。

I1 から I4

I1：確実な4xx（作成されていない）も reserved のまま保留されます。方針どおりですが、確認後に reserved を blocked へ戻して再予約できるようにする運用操作が見当たりません。hold() は WHERE state='blocked' のときしか更新しないので、dismiss_hold が状態を別の値に変える実装だと、2回目の保留が黙って無視されます。削除で実装するか、ここも試験で確認してください。
I2：split(":", 3) は要素が足りないと ValueError で落ちます。try で囲み、落ちた場合は「登録元 <source>」と表示してください。pending_details が reserved を含むかどうかも確認してください。
I3：作成時に原本キー（source_key またはその fingerprint）をページのプロパティに書き込んでください。結果不明や W1 のときに、DBを完全一致で照会でき、名前で推測せずに済みます。
I4：通常更新のたびに dismiss_hold を発行します。件数が多い場合は、保留行があるときだけ実行するよう軽量化を検討してください。
追加すべき模擬試験
POSTの応答が消えた後、同じ原本IDの通知が再び来ても、POSTは合計1回のまま（B2）。
finish 失敗時に、通知とログに page_id が含まれ、対応表を登録しない（W1）。
対応表の保存成功・応答消失 → 次回の通常更新で一致を確認して保留が解消される。不一致なら保留が更新される（W3）。
