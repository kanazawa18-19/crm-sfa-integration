静的レビューの結果、BLOCKERが1件あります。統合が保留中のあいだ、その営業担当のGmail取込全体が止まり、保留が長引くとメールが恒久的に失われる経路です。

EmailLogの移管そのもの（1トランザクション内での照合・ロック・更新・再読込、応答が途切れた後の再開、第三者変更の検出、旧計画の保留）は、データ喪失の観点で問題を確認していません。

BLOCKER

B1 統合保留が担当者のGmail取込全体を止める
根拠：
・contact_record_guard は、統合保留中の連絡先に対して RecordSyncBusy を送出します。テスト「統合保留中は保存も最終日時更新もしない」でも、この挙動が前提になっています。
・_process_message_ref_or_skip が握りつぶすのは404だけです。そのため例外は sync_rep_incremental の外まで伝播し、historyId は進みません。
・sync_rep（日次同期と、Pushからのフルスキャン退避）も同様に、その時点で残りの処理を打ち切ります。
影響：
1. 統合が人の確認待ちで保留されているあいだ、その担当者の他の顧客宛てメールもすべて取り込まれません。インシデント通知（high）と最終メール日時も遅れます。Pushが来るたびに同じメッセージで失敗し続けます。
2. 保留がGmailの履歴保持期間を超えると HistoryIdExpiredError になり、直近2日分のフルスキャンに切り替わります。その結果、停止した時点から「現在−2日」までに届いていた未記録のメールは、再取得されないまま失われます。日次同期も2日分しか見ないため補えません。
3. 8月の404障害（Push処理が170回連続で失敗）と同じ「先頭の1件が後続全体を止める」構造に戻っています。
修正案：
・統合保留による停止（長期になりうるもの）と、鍵の一時的な競合（数秒で解けるもの）を別の例外に分けてください。
・統合保留の場合は、メッセージIDと担当者を保留キュー（例：GmailIngestDeferred）に永続化してから後続の処理を続け、historyId も進めます。
・保留キューは、finish_with_aliases の完了時や統合の取消時に再投入し、加えて定期処理でも再投入します。
・保留キューの最古の滞留時間を健全性チェックに加えてください。
・GAS経路（atomic_insert）でも、同じ例外が担当者単位の停止にならないことを確認してください。
・「統合保留の連絡先を含む履歴でも、後続のメールが記録され、historyId が進む」ことを確かめる回帰テストを追加してください。

WARN

W1 外部呼出し中もレコードの鍵を保持している
根拠：contact_record_guard の with ブロック内で、次の処理をすべて実行しています。
・score_email
・EmailLog の保存
・notify_managers_immediate
・Notion の update_page
・notify_web_engagement_tool（例外の隔離なし）
影響：鍵を持つ時間が外部APIの遅延に左右されます。その間、同じ連絡先へのNotion webhook同期や統合の実行が RecordSyncBusy になります。また notify_web_engagement_tool の例外で処理全体が失敗扱いになり、B1と同じ停止経路に入ります。
修正案：鍵の中では EmailLog の保存と最終メール日時の更新だけを行い、通知は鍵を外した後に実行してください。atomic 経路はすでに claim で二重送信を防いでいるため、移動しても安全です。

W2 メール証跡ハッシュの脆さ
根拠：_evidence は SELECT * で取得した全列を json.dumps(default=str) でハッシュ化しています。
影響：
・EmailLog に列を追加するマイグレーション（既定値付き）を行うと、その時点で承認済みや保留中の統合がすべて「比較後に統合元のメールが…変更」で保留になります。
・timestamptz の文字列表現は接続のTimeZone設定に依存します。比較時と実行時の接続設定が異なると、内容は同じでもハッシュが一致しません。
・digestedAt 以外にも後から更新される列（照合状態など）があれば、同じく保留になります。
修正案：ハッシュ対象の列を明示した一覧に固定し、日時は UTC の isoformat に正規化してから計算してください。

W3 ガードを通らない書込みと、移管されない参照
根拠：
・移管対象は EmailLog.contactPageId だけです。
・過去分の一括取込（scripts/backfill_gmail_history.py）は、docstring 上 classify_message とローカル辞書で直接保存するため、contact_record_guard と別名解決を通りません。
影響：
・統合完了後に、統合前に作った辞書で過去分を取り込むと、アーカイブ済みの統合元IDにメールが付き、正本から見えなくなります。
・メール照合（email_review の保存内容）など、contactPageId を持つ他の表があれば、統合後もアーカイブ済みのIDを指したままになります。
修正案：
・EmailLog への全書込み経路が、別名解決とガードを通ることを確認してください。過去分取込は、保存直前に resolve_alias を適用し、統合中の連絡先は保留にします。
・スキーマ全体で contactPageId 相当の列を洗い出し、統合手順に含めるか、統合を保留する条件に加えてください。

W4 kintone反映の案内と既存変換の食い違い
根拠：補足では既存変換は「連絡済み」等の4値に対応とあります。一方、project_form は「連絡済みのみ対応」と表示し、preview_view は「連絡済み」以外なら「kintoneの営業ステータスは変更されません」と表示します。
影響：残り3値に変更した場合、実際には kintone も更新されるのに「変更されません」と案内されます。保存前の確認画面で誤った情報を出すことになります。
修正案：案内と判定を、変換表（4値）から生成してください。表にない値の場合は kintone が未反映（partial）になることを明示します。

W5 メール証跡の件数上限
根拠：統合元の全メールについて id・sentAt・hash を、次の4か所に重複して保存しています。
・snapshot.emailHistory.rows
・手順の rows
・before
・desired
件数の上限はありません。
影響：メールの多い連絡先では journal の行が肥大化し、保存や比較画面の表示、digest 計算の負荷が上がります。
修正案：本文の100ブロック制限と同様に件数の上限を設け、超える場合は保留にしてください。手順側は件数とハッシュの要約だけを保持し、詳細は snapshot を参照する形にもできます。

INFO

I1 sentAt が NULL の行があると、str(None) が 'None' になり、latest_date で「最終メール日時を確認できません」として保留されます。安全側の挙動ですが、str() の前に None を判定してください。

I2 比較から実行までの間に統合元へ新しいメールが届くと、実行時に保留になり、比較のやり直しが必要です。require_record_available が「承認済み・未実行」の段階から保存を止めるかどうかによって、やり取りの多い顧客の統合が完了しにくくなる可能性があります（B1の対処と合わせて検討してください）。

I3 統合でスレッドが1つの連絡先にまとまると、未返信リマインドの判定対象が変わります。EmailReminderLog で二重送信は防げますが、古いスレッドが新たに「未返信」と判定されないか、判定に期間の条件があるか確認してください。

I4 最終メール日時は、Gmail保存側では秒単位で書き込み、統合側では分単位に揃えて比較しています。Notion上の最終メール日時と EmailLog の値を等値で比較している箇所（通知済み判定など）が他にあれば、同じく分単位に揃えてください。

I5 不足しているテスト：
・B1（統合保留中も後続メールが記録され、historyId が進むこと）
・GAS経路（atomic_insert）で統合保留にあたった場合
・接続のTimeZone設定が異なる場合のハッシュ一致
・日時の追加試験（実施中とのことなので、分単位に丸めた境界値（:59 から :00 への繰り上がりなし）も含めてください）
