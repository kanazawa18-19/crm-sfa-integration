BLOCKER

B1 created 後の再開が計画前の指紋に縛られている
根拠：apply は予約の状態によらず snapshot を取り直し、digest(current) != plan[‘hash’] なら保留します。一方、preview は予約があると「元の計画で再開してください」と拒否します。snapshot には次が含まれます。
・Zoho 親の実物全体（Modified_Time や Last_Activity_Time など、関連活動の追加だけで変わる項目を含む）
・元アクションの値と本文
・「元アクションの関連が空欄」という条件
POST 前の照合としては正しい設計ですが、POST 後の再開にも同じ条件を課しています。
影響：
・Notion ページの作成・finish が済んだ後、対応表の保存か最終確認（W2）で止まると、再開時には Zoho 親の活動日時などが変わっていることが多く、「計画後に…変わりました」で保留になります。
・新しい計画は preview が拒否するため作れず、正規の手順では完了できません。取込ページは対応表がないまま残り、通知ガードによって通常処理の対象にもなりません。アクションの関連承認にも進めません。
・test_mapping_failure_resumes_known_id_only は snapshot を固定値の Mock にしているため、この経路を検出できていません。
修正案：
・POST 前の照合（計画の全指紋）と、POST 後の再開条件を分けてください。
・attempt が created の場合は全指紋を比較せず、次の不変条件だけを確認します。
・計画ファイルの改ざん有無（hash と snapshot の一致）
・予約の identityHash と externalId
・verify_imported（DB、アーカイブ、確認番号、計画項目、既存の対応）
・Zoho 親が同じIDで実在し、統合履歴がないこと
・同じ外部IDの対応が、取込ページ以外に存在しないこと
・対応表を保存した後は、通常同期によって取込ページの項目が変わりえます。そのため対応表が保存済みで一意なら、項目の一致は求めずに完了扱いにします。
・回帰テストとして「created 後に Zoho 親の Modified_Time が変わっても、対応表を保存して完了する」ケースを、snapshot を実物の経路にしたうえで追加してください。

WARN

W1 ID未確定の予約中は、Notion取引先の新規登録が全件止まる
根拠：existing is None のときは include_unidentified=True で照会するため、reserved が1件でもあれば、無関係な未登録の client_master ページもすべて ‘relation_parent_import_pending’ になります。この結果は Notion のメモにも保留表にも記録されません。また reserved は設計上、人が調べるまで解除されません。
影響：タイムアウトや、予約後のローカル例外（I2）で reserved が残ると、その間に営業が作成した新しい取引先は Zoho・kintone に登録されません。次の編集か週次点検まで誰も気づきません。
修正案：
・保留の対象を、計画の取引先名と一致するページ、または予約時刻以降に作成され確認番号を持つページに絞ってください。
・reserved が一定時間を超えて残る場合は、健全性チェックか運用DMで通知します。
・保留した理由をページのメモに残してください。

W2 対応表保存直後の一意性確認が Notion 検索に依存している
根拠：保存後の確認 self.mappings(external_id) は、Notion の対応表DBを検索（_query_all）しています。作成直後のページは、検索結果に反映されるまで時間がかかる場合があります。
影響：実際には保存済みでも「保存後の外部ID対応が一意ではありません」で保留になり、B1の再開経路に入ります。
修正案：保存直後は store.get(imported) による直接読取で確認してください。重複の検出は、短い再試行を挟んで行うか、次回の再開時に回します。

W3 Zoho側ガードは取込完了後も True を返し続ける
根拠：pending_hub_creation は、Zoho イベントに対して予約が reserved か created である限り True を返します。Notion 側のような「対応表が成立していれば通す」条件がありません。
影響：pending_hub_creation が新規レコード判定（対応表なし）でしか使われないなら問題ありません。対応表がある通常更新でも参照される経路があれば、この親の Zoho 側の変更が恒久的に同期されなくなります。
修正案：呼出し箇所を確認し、「取込後、対応表のある Zoho 更新が通常どおり配送される」テストを1件追加してください。

W4 kintone 側の同じ顧客
根拠：取込後の対応表には zoho_id しかありません。文書でも、欠損している kintone は自動作成しない方針です。
影響：kintone に同じ顧客が既にあり、未対応のままだと、kintone の通知が未知レコードとして Notion の自動作成に進み、親ページが二重になりえます（自動作成側に同名照合がない場合）。
修正案：適用前に kintone 側の該当顧客の有無を確認し、あれば対応表へ手動で紐付ける手順を運用文書に加えてください。
