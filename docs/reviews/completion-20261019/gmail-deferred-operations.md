# 統合待ちメールの保全と再開

連絡先統合の保留で通常Gmail同期が止まる問題を修正した。統合鍵を取得できないメールは、照合済み連絡先・担当者・Gmail ID・取得済み項目と原文（base64url MIME）をDBへ保存する。原文取得またはDB保存が失敗した場合は履歴位置を進めない。保存済みなら他メールを続行する。GAS側は既存の `effect_failed` として再試行対象を維持する。

- 配備前に `20261019000000_gmail_deferred_message` を適用する。ここでは本番未実施。
- 既存5分cron `gmail-late-registration` から再処理する。1回最大10連絡先、1連絡先1件、45秒の開始予算、各メールのHTTP予算10秒。DB接続・SQLにも既存接続上限と5秒SQL上限がある。全体の厳密な45秒打切りではない。
- 待機・失敗は5分から最大30分間隔へ回す。別連絡先を続け、本文を期限で捨てない。
- 保存は既存の原子的挿入・通知試行印を使い、保存後の最終日時更新から再開できる。処理完了直後に停止しても重複通知しない。これは既存の「通知を試みたら再送しない」方針で、通知配送そのものの保証ではない。
- 完了時は抽出本文が非空なら本文を消し、IDと完了日時の受領記録を残す。抽出本文が空なら原文MIMEを監査・将来の全文回収用に保持する。再配送は行わず、EmailReviewへ原文を複写しない。同じキューの再投入では初回本文と作成時刻を変更しない。
- ヘルスチェック `gmail_gas_observation` に保留件数・30分超件数・最古作成時刻・最終試行時刻を追加した。30分超はwarningとする。Gmail移管の14日＋72時間の待機条件は変えない。
- 原文は顧客情報を含むため、通常アプリと同じDB権限下に保存し、レスポンス・ログへ出さない。

今回、旧手動 `scripts/backfill_gmail_history.py` は実行しない。同CLIは共通統合鍵と新キューを通らないため、稼働中の連絡先統合と並行利用しない。通常経路の非原子的保存後にNotion更新だけ失敗したケースの既存再開問題、および通知処理を統合鍵の外へ移す変更は今回の対象外。新キューの再開は原子的保存経路を使う。
