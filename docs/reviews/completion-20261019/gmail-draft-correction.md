# 下書き活動の固定訂正

`scripts/correct_gmail_draft_activities.py` は、Gmail 履歴で同じ会話の下書き4版と最終送信1通を結び付けられる固定5受付だけの運用処理。顧客値・ID・完全な変更前データは私有入力/計画に置く。通常の候補判定・一般統合の管理外関連条件は緩めない。

`reserve --input <私有spec> --output <私有予約結果> --actor <管理者> --expected-hash <specのdigest>` は、配備済みの通常操作ガードを使って固定5件を先行停止する。本文や外部対応は変更しない。処理中workerのある受付は全件予約せず、SQLトランザクションを戻して待つ。

`preview --input <私有spec> --output <私有plan> --actor <管理者>` は読取のみ。`apply` は同じ計画を入力し、独立レビュー済み `--expected-hash` を要求する。順序はガード本番配備 → 固定spec hash予約 → 新しい計画生成 → 実読レビュー → apply。予約前の旧planは適用できない。新規の外部活動を作成する処理はない。

## 固定する根拠

- 各受付の所有者、Gmail ID、thread ID、共通メール識別値、活動IDを照合。履歴の追加/削除イベントの message ID と thread ID も直接照合し、下書き4版の順序と後続 SENT を確認する。
- 本文・タイトル以外の書込可能項目は5活動で同一を要求する。日付、親、先方担当者、種別等を別物へ変換しない。
- 正本は外部3先が既に揃う下書き活動の器。最終送信の内容を移し、正本の外部IDを保持する。元の最終送信活動には外部IDがない場合だけ扱う。
- 管理外の関連は、固定5ページすべてで空配列かつ続きなしを実読した定義だけ例外とする。非空へ変化したら停止する。通常の本文ブロックと親の逆関連は共通統合で保持する。
- 比較後に活動・連絡先・関連する親/子の共通鍵を取得し直して原本と参照を再照合する。実行時も同じ全対象の鍵を保持する。

## 実行と再開

`先行予約 → 比較 → 受付停止 → 4統合 → 正本訂正 → 旧外部取消 → SENT受付移管 → 下書きEmailLog除外 → 全実読 → SENT正本だけ解除`

訂正マーカーは送信証拠のあるSENTにも適用する。判断の全操作・evaluate/process/reconcile・Notion通常通知・共通新規作成の入口/ページの鍵内を拒否し、長い中断中も保持する。最終検証前にSENTを解放しない。解除はSQLで一括し、4旧ページと4下書き受付の停止印は残す。専用統合は通常画面からの再開・中止も拒否する。

段階は既存 `SyncOperationHistory` に計画hashとともに予約する。最初の予約に完全な計画/変更前データを保存する。Notion統合は既存 `RecordMergeJob` の予約・本文追加・再読・別名確定を使用する。結果不明の本文追加を再送しない。複数統合で同じ親を扱うため、後続の参照配列と本文は前の統合結果を引き継いで計画する。

外部処理も既知IDごとに予約し、通信断後は現在値を再読する。予約前から消えている実物は成功扱いにしない。添付/コメント/関連ノートは空を要求し、変更があれば保持して停止する。

- kintone: 正本の本文のみ訂正、旧2活動は全項目・型・コメントを退避した上でIDと版を指定して取消。永久削除なので、旧IDの別名・追跡可能な原本退避が成立してから実行する。
- Zoho: 正本のタイトル/本文/日時を `trigger: []` と更新時刻条件で訂正。旧3活動は `wf_trigger=false` で削除し、既知IDが通常取得に現れないことを確認する。ゴミ箱からの復元操作はこの処理に含めない。
- Sheet: 行を削除/詰めず、既存の同期キーを実読して旧3行の削除フラグだけ変更する。正本行は同じ行のタイトル/本文/日時を訂正する。
- 受付移管: 同一SQLトランザクションで旧正本の一意活動IDを解放してSENT受付へ移す。4下書きは除外理由・元活動IDを残す。本文・Message-ID・所有者を入れ替えない。
- EmailLog: 4下書きの完全行を退避してから集計対象から除外する。Reminder参照が生じたら全件保持。実在SENT行は通知処理が更新するdigestedAtだけ比較から外し、本文・日時・ID・contactPageId等を保持する。下書きも同じ比較条件とし、削除時のdigestedAtを含む最新の全行を削除と同じSQLトランザクションで追加退避する。

## 実測と制限

対象ZohoカスタムDBは通常GET/v8/fields指定でも Modified_Time を返さなかった。COQLの既知ID読取では取得できたため、前後COQLの時刻一致を確認して実物と版を結び付ける。

Zoho DELETE に `If-Unmodified-Since` の原子的な版条件保証は公式仕様上確認できない。ヘッダーを付けても、直前の完全実読と削除の間に外部画面から変更される小さな窓は残る。共通鍵はこの連携の同時処理を排他するもので、外部UIの編集まで止めない。SheetもAPIの条件付き更新がなく同じ制限がある。削除前の完全退避と結果不明時の実読を必須とし、版付き原子取消を保証したとは記録しない。

固定5以外の再配送や、過去回収CLIの実行は行わない。トリガー・GAS観測起点を変更しない。私有計画には個人情報を含むため他社レビューへ添付しない。

適用前の派生値読取では、対象の連絡先1件について、下書き4行を除いても最大メール日時が不変、Notion最終メール日時も同じ分単位で一致した。4下書きのインシデントスコア/優先度はすべてNULL。実値は `draft-correction-derived-readback.json` に保存した。これは適用前の読取であり、適用後に再照合する。

旧Sheetの同期キーは保持する。dispatcher は元キーと別名解決後の正本IDが違うイベントを `merged_source_archived` で終了する。結合試験で旧行の削除フラグ通知が正本を変更しないことを確認した。同期キーを空にして追跡経路を失わせない。

この固定5件のアクション日は実読で同一であるため、不変条件を維持する。kintone活動に同じタイトル/アクション日を書き込む対応欄はなく、本文だけを訂正し他の既存欄を保持する。適用中は対象Sheetの並べ替え・行挿入を行わない。完全退避を保存するSyncOperationHistoryは管理者の運用経路から扱い、私有証拠を一般画面/外部レビューへ公開しない。

通常のaction_id索引と訂正旧ページ配列のGIN索引を併用する。`20261019030000_email_review_correction_guard` をDB先行で適用してからAPIを配備する。ローカルPostgreSQLのEXPLAINで両索引を使うBitmapOr経路を確認した（小さな合成表で索引経路を検証するためenable_seqscanをOFFにした。実データの速度実測とは区別する）。

## Zoho訂正の読戻し差への限定対応

適用途中で安全停止したZoho正本は、保存された実差で期待本文862文字に対し実物861文字、`期待本文 == 実物本文 + LF`、実物末尾LFなしを確認した。さらにLast_Activity_Timeは実物Modified_Timeと同値へ更新されていた。

同じplan/hashを保持し、Zohoに限って「本文欄の末尾LFがちょうど1個除かれた場合」と「実物Modified_Timeと同値のLast_Activity_Time」を比較時だけ許容する。複数LF・CRLF・空本文・途中の改行・別項目/親/タイトルの差は許容しない。書込前のbefore完全一致と版条件は変更しない。既成功kintone/予約済みZohoの同計画再開で再PUTしないことを試験した。独立読戻しスクリプトも送り先を明示して同じ限定比較を使用する。
