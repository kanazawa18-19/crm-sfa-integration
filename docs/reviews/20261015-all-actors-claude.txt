結論：BLOCKERはありません。WARNは3件です。そのうちW1は、設定不備が保留にならず別の挙動へ黙って変わる経路なので、マージ前の修正を推奨します。管理者アカウントによる代替、複数担当の一部だけをアカウント欄に残す処理、作成者からの推測の3点は、いずれも今回の差分で発生しないことを確認しました。

ID	区分	根拠箇所	要旨
W1	WARN	action_kintone.py action_actor_rows の by_id = {row['notion_id']: row ...}	入力IDだけ正規化し、設定側のnotion_idは正規化していない
W2	WARN	action_kintone.py action_actor_rows 原本別設定分岐、docs 「未確認ユーザー」→「氏名を確認できないユーザー」	原本別設定の担当者が、対応設定に未登録でも通るようになった
W3	WARN	adapters.py plan の except節、action_kintone.py の保留文言	再実行では解消しない取得失敗に、正しい解消手順が示されない
I1〜I7	INFO	下記	堅牢化・テスト補強

W1 設定側IDの正規化漏れで、保留すべき設定不備が「アカウント欄空欄」に化ける
入力の担当営業IDは str(UUID(...)) で正規化されています。一方、by_id のキーは CRM_USER_MAPPING_JSON の値そのままです。設定のnotion_idがハイフンなし・大文字などの非正規形だと、登録済みの管理者も未登録扱いになり、{'notion_id': identifier} として処理されます。
変更前は、この状態は「確認済み対応設定がありません」で保留されていました。変更後は、Notionから氏名を取得し、対応者を空欄、コメントに実名という経路で作成が成功します。管理者本人の記録からアカウントが黙って外れ、設定不備も表面化しません。「verified対応設定が不正なら保留」に反します。
修正案：by_id を作るときに各行のnotion_idも UUID で正規化し、変換できない行があれば CreationHeld('担当者の確認済み対応設定のユーザーIDが不正です') にする。テストは、非正規形の設定IDで保留になるケースを1件追加してください。他DBの owner_to_external は生値で照合しているため、今回は owner_directory 側を変えず、アクション内で閉じる対応が影響範囲として妥当です。

W2 原本別承認設定の挙動が変わっている
変更前は、CRM_ACTION_ACTORS_JSON の notion_user_id も対応設定に登録されている必要がありました（未登録なら保留）。変更後は未登録でもNotion照会で通ります（test_new_override_actor_still_requires_original_creator がこれを前提にしています）。作成者照合は維持されているため推測にはなりません。ただし、依頼文の「原本別承認設定は従来のまま」とは差があります。
意図どおりであれば、docsの原本別設定の段落に「原本別設定で指定した担当者も、対応設定への事前登録なしでNotion照会の対象になる」と明記してください。意図外であれば、原本別設定の分岐で得たIDについて、directory未登録なら従来どおり保留してください。

W3 再実行では解消しない取得失敗に、解消手順が合っていない
保留文言は「氏名・連携権限を確認し、解消後に再実行」です。しかし、ゲストや退職などで削除されたメンバーは、GET /users/{id} で取得できない可能性があります（実API検証で要確認）。この場合、権限を直して再実行しても解消せず、対応設定に display_name 付きの行を登録するのが唯一の解消手段です。
修正案：両方の保留文言に「Notionで取得できない担当者は、CRM_USER_MAPPING_JSONに表示名を登録してから再実行」を追加する。設定の表示名は優先されるため、コード上はこの手順で解消できます。429/5xxのような一時障害も同じ文言で保留になりますが、自動再試行を追加しない方針どおりなので問題ありません。

INFO

I1 adapters.py で creation_context() と action_actor_rows が2回評価されています（action_profile_ids と action_actors で各1回）。評価の間で内容が変わっても保留側に倒れるため安全ですが、1回の評価結果を両方に渡すと判定根拠が一致します。

I2 1回の同期で同じ新担当者のアクションが多数あると、同じユーザーへのGETを件数分繰り返します。HTTP予算の消費や429による一括保留を避けたい場合は、アダプター内で成功結果だけを実行単位でキャッシュする案があります。再試行の追加ではないので方針には反しませんが、今回の範囲外として見送っても構いません。

I3 氏名の検証は \n・\r・【】 だけです。\u2028・\u2029・\x85・\x0b、NULなどの制御文字は通ります。kintoneや往復経路で改行に変換されると、以後 _comment_parts が「枠破損」で更新を止めます。len(name.splitlines()) != 1 or not name.isprintable() の判定を追加すると確実です。前後の空白をstripするかどうかもあわせて決めておくとよいです。

I4 display_name が 0・False・[] など文字列以外の偽値だと「未設定」と扱われ、Notionの氏名で上書きされます。厳密にするなら、キーが存在して文字列でない場合は設定不正として保留にしてください。

I5 「氏名を取得する接続がありません」の保留文言には、対象IDと解消手順がありません。配線漏れの検出用なので重要度は低いですが、他の保留文言と揃えると運用時に判断しやすくなります。

I6 production_wiring.py は notion_clients['action'].get_user を構築時に評価しています。notion_clients['action'] がラッパー型などで get_user を持たない場合、Zohoを含む作成サービス全体の構築が失敗します。本番の型が HttpNotionClient であることを確認するか、getattr(..., 'get_user', None) にして、存在しなければI5の保留に落としてください。

・アカウントありで表示名なしの登録者と、新担当者の混在時に、登録者側もGETされ、アカウント欄が空になること
・全員にアカウントがある場合に resolver が呼ばれないこと（calls == []）
・HttpBudgetExceeded が保留に変換されず再送出されること
・notion_clients に action がない配線

・ゲスト
・削除済みメンバー
