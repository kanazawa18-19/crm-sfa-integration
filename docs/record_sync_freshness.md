# 古いWebhookによる巻き戻り防止

2026-09-08。対象は同期ディスパッチャとシート行再試行（outbox）。本番への適用・本番操作は未実施。

## 変更前と変更後

以前はmappingの最終同期時刻を読む瞬間だけ古さを判定していた。別ワーカーが先に新しい値を書いた後でも、先に判定を通った古い処理が後から上書きできた。シート行再試行にも、Notion取得と行追加の間に同じ競合があった。

現在は同一DB・Notionキーの同期を1件ずつ処理する。

```
専用ロック取得 → mapping再読込 → 古さ判定 → 現在値取得・判定
 → 受理時刻の永続保存 → 外部書込 → 完了時刻保存 → mapping時刻保存
 → 接続終了・ロック解放
```

`RecordSyncWatermark` の受理時刻（acceptedAt）は外部書込の直前に先行保存する。外部書込後に完了時刻の保存が失敗しても、それより古いイベントは拒否する。未完了の同時刻イベントは再送可能。完了時刻（completedAt）とmappingの最終同期時刻のうち新しい方以下は、従来どおり `stale_event` とする。Notion APIの読み取りが古い値を返しても、Postgresに残した時刻が判断の下限になる。時刻は小数秒6桁を保存する。

ロックはPostgresのセッション単位で保持する。受理時刻保存の確定後も外部書込完了まで解放しない。専用namespaceは `record_sync`、既存のシート行作成ロックより常に外側で取得する。競合は `RecordSyncBusy` を送出し、Webhookの既存エラー経路でHTTP500・再送にする。outboxの競合は試行回数を消費せず差し戻す。

outboxはNotion取得から行追加・行番号保存まで同じロックを保持する。手動復旧の棚卸しで行番号を記録するときも同じロックを取得する。新規ページ作成は従来のmapping登録を先に済ませ、その後の行追加だけ同じロックで保護する。登録後に新しい同期が先行した場合、古い作成時プロパティを捨ててoutboxへ渡す。ロック取得失敗も既存の行作成失敗通知・再試行へ渡す。

## 配備条件

- `20260908000000_add_record_sync_watermark` の追加マイグレーションを先に適用する。既存データの削除・書き換えはない。
- `DATABASE_URL_UNPOOLED` に直接接続を設定する。未設定・既知の `-pooler` ホストは例外にして処理を止める。独自の接続プール名は自動判定できないため、運用者が直接接続を確認する。
- テーブル未配備・DB接続不可・受理時刻保存不可の場合、既知レコードの外部更新を開始しない。
- このテーブルは再送に対する記録なので自動削除しない。将来削除するときは古い再送を受け付ける期間を別途決める。

## 保証の範囲と残る制約

- 本番のプロセス間排他はPostgresを使用する。SQLite実装だけは同一store個体・単一プロセスのテスト用ロックを使う。同一SQLiteファイルを別storeや別プロセスで開く使い方は保証しない。
- ロックに参加しない手動編集・バックフィル・別システムの書込は対象外。Notion webhook後段のカレンダー同期等にも適用していない。
- 外部書込とPostgresは同一トランザクションにならない。書込後に失敗した同時刻イベントの再送は外部書込を繰り返す可能性がある。接続断でロックを失った実行中リクエストの停止や、外部APIの読み取り整合性は保証しない。
- 時刻は従来どおりレコード単位で比較する。別項目の古い差分・同時刻の別イベント・ツール間の時計ずれを項目単位で解決する変更ではない。部分的な書込スキップ時にも完了時刻を進める既存仕様は維持する。
- 新規ページ自体の二重作成排他は今回の対象外。mapping登録前の既存の作成・補償経路は維持する。登録後のロック失敗でoutboxにも積めなかった場合は既存通知経路に従い手動復旧が必要。
