# シートの行を作れなかったレコードの再試行（outbox）

2026-09-07 作成。実装は `src/sync_engine/spreadsheet_outbox.py`（積む側）と
`src/sync_engine/spreadsheet_outbox_drain.py`（作り直す側）。

> **名前について。** いわゆる transactional outbox パターン（主DBの書き込みと同一
> トランザクションでイベントを書き、配送を保証する仕組み）**ではない**。外部API
> （Sheets）への書き込みが失敗したあとに積む、**再試行キュー**。積むこと自体が
> 失敗しうる。配送保証があると思って読まないこと。

## 何を直したのか

同期エンジンは「スプレッドシートの行を作れなかった」ときも Webhook に **2xx** を返す。
Notion ページと ID マッピングは既にできているので、500 を返してリトライさせると
**重複ページを作りかねない経路**を叩き直すことになるためで、この判断自体は変えていない。

問題は、そのあとの拾い方が**全部人任せ**だったこと。

```
   2026-09-03 まで                        2026-09-07 から
   ─────────────────────────────────      ─────────────────────────────────
   Slackへ通知              人が読む       ★キューに積む
   verify_spreadsheet_…     人が流す       ★日次のcronが作り直す
   backfill_spreadsheet_…   人が流す       （どちらも今までどおり使える）
   次の更新イベント          いつ来るか不定
   ─────────────────────────────────      ─────────────────────────────────
   Slackを見落とし、そのレコードが          放っておいても、翌日には行ができる
   二度と編集されなければ**永久に欠ける**
```

ChatGPT が BLOCKER、Gemini が独立に WARN として指摘していた穴（2026-09-03）。

## 仕組み

```
   ① 失敗                                          ② 積む
   ┌──────────────────────────────┐              ┌────────────────────┐
   │ Dispatcher                    │              │ SpreadsheetOutbox  │
   │  新規作成でシートに書けない    │──────────▶│  dbKey             │
   │  更新でNotionが読めない        │              │  notionKey         │
   │  行作成ロックが取れない        │              │  status / attempts │
   │  書き込みが例外で落ちた        │              │  nextAttemptAt     │
   └──────────────────────────────┘              └────────────────────┘
              │ Webhookは2xxのまま                          │
              ▼                                              │ ③ 日次cron
        Slackへ通知（積めたかで文面が変わる）                  ▼
                                              ┌──────────────────────────┐
                                              │ /api/cron/               │
                                              │   spreadsheet-outbox-    │
                                              │   drain（毎日 02:00 JST）│
                                              └──────────────────────────┘
                                                            │
                                    Notionを読み直す ──▶ 行を追記 ──▶ done
```

### 値は持たない。持つのは「どのレコードか」だけ

失敗時のスナップショットを貯めて後から流すと、**その間に入った新しい値を古い値で
巻き戻す**（`_append_spreadsheet_row_for_created_record()` の `append_only` と同じ事故）。
マスターは Notion なので、作り直す瞬間に Notion を読めばこの事故が原理的に起きない。

**この割り切りの帰結**：このキューが直せるのは「行がまるごと無い」状態だけ。
「行はあるが1列だけ書けなかった」は対象外で、そちらは従来どおりイベントの再送（500）と
次の更新イベントで直る。`_enqueue_missing_spreadsheet_row()` が
`mapping.spreadsheet_row is not None` のときに積まないのはこのため。

### 積む条件

| 経路 | reason | いつ |
|---|---|---|
| 新規レコード作成 | `new_record_row_write_failed` | 追記が例外で落ちた |
| 〃 | `new_record_row_write_skipped` | ロックが取れない・ターゲットが見送った |
| 〃 | `new_record_row_properties_unavailable` | スキーマが引けず項目を決められない |
| 更新 | `update_notion_fetch_failed` | 全項目の取り直しで Notion が読めない |
| 更新 | `update_notion_page_missing` | Notion ページが読めない（None） |
| 更新 | `update_schema_unavailable` | スキーマが引けない |
| 更新 | `update_row_write_skipped` | 行を作るつもりで作れなかった |
| 更新 | `update_row_write_error` | 書き込みが例外で落ちた（**500 は今までどおり返す**） |

**積まない**のは次の2つ。

- **行が既にあるレコード**（上記のとおり、このキューでは直せない）
- **シートへ書ける項目が1つも無いとき**（作り直しても Notion を読み直すだけで、
  その Notion ページはミリ秒前に同じ値で作ったばかり。積めば毎回同じ判断で
  解決され、キューが実体のない件数で埋まる）

### 何を「解決」と呼ぶか

```
   行を作れた                          done
   もう行があった                      done（別のワーカー・次のイベントが先に作った）
   IDマッピングがもう無い               done（レコードごと消えた。作る先が無い）
   Notionページがもう無い               done（同上）
   シートへ書ける項目が1つも無い         done（作っても同期キーだけの行になる）
   Notionが読めない・書き込みが落ちた    もう一度（8回で failed）
   シート・Notionが構成できていない      もう一度（8回で failed。**差し戻しにしない**）
   別のワーカーが作成中・時間予算切れ     差し戻し（試したうちに入れない）
   行の新規作成が許可されていないDB      取り出さない（pending のまま置く）
```

**`status` とは別に `resolution` を持つ**（どう決着したか）。`done` の件数だけだと
「行を作れた（`created`）」と「そもそも作る必要が無かった（`not_applicable`）」が混ざり、
**この仕組みが実際に効いているのかを後から数えられない**ため。
値は `created` / `already_present` / `not_applicable` / `gave_up` /
`recovered_manually` の5つで、診断の `by_resolution` に出る。

**差し戻し（試したうちに入れない）が許されるのは、放っておけば数分で解けるものだけ。**
混み合いを数えると、`SPREADSHEET_ROW_CREATION_*` を一時的に切っただけで全件が
`failed` へ落ちる。逆に**シートのタブや Notion の認証が未設定のような恒常的な失敗を
差し戻すと、試行回数の上限に永遠に到達せず、Slack も鳴らず、診断も緑のまま静かに
滞留し続ける**（2026-09-07、シロクマと Gemini が独立に指摘）。前者は差し戻し、
後者は失敗として数える。

`failed` は**消さない**。人が対処するために残す。`done` は 30 日で掃除する。

### 諦めた行の棚卸し（消えない赤信号を作らない）

`failed` の案内は「`backfill_spreadsheet_rows.py` で作り直してください」だが、
**そのスクリプトはこのキューを一切触らない**。案内どおりに直しても `failed` が残り、
診断が永久に赤くなる——**消えない赤信号は誤報と同じだけ有害**で、
「誤報を鳴らし続けると本物の通知も無視される」（CLAUDE.md）を自分で起こしてしまう。

そこで日次のcronが最後に `failed` を最大50件見に行き、**行がもうできていれば
静かに閉じる**（`resolution=recovered_manually`）。**確かめるだけで、書き込みはしない。**
自動での再試行はしない（8回試して駄目だったものなので）。

未対処のまま残る `failed` は、毎日この確認で Sheets を1件1リクエスト読むことになる
（＝ポーリング）。50件が上限なので Quota には影響しない範囲だが、
**放置し続けると毎日そのぶん読み続ける**ことは意図した動作として書いておく。

## 運用

```
   状態を見る   GET /api/diagnostics/integrations?only=spreadsheet_outbox
                → failed が1件でもあれば status=failed（対処が要る）
                → pending の最も古いものが3日以上残っていても status=failed
                   （日次で拾えるはずのものが残る＝詰まり。下記）
                → それ以外は ok。pending の件数と内訳だけ返す

   手で流す     GET /api/cron/spreadsheet-outbox-drain（CRON_SECRET が要る）

   諦めた分     scripts/backfill_spreadsheet_rows.py --db-key <db> --apply
```

`failed` になったレコードは Slack へも上がる（`notify_update_skipped`、
reason=`spreadsheet_row_outbox_gave_up`）。**打ち切りを黙って握らない**ため。
cron のレスポンスにも、その回に諦めたものが出たら `needs_attention: true` が入る。

### 「静かな滞留」を異常として拾う

シートのタブや Notion クライアントが**丸ごと構成できていない**とき、作り直しは
「差し戻し」を通る。これは正しい（混み合っただけで `failed` へ落とさないため）が、
構成ミスのような恒常的な失敗でも同じ経路なので、**試行回数の上限に永遠に到達せず、
Slack も鳴らず、診断も緑のまま**になる。

日次で拾えるはずのものが3日残っていたら、それは待ちではなく詰まり。
`probe_spreadsheet_outbox()` は `pending` の最も古い積み込みからの日数を見て、
3日以上なら `failed` を返す。

### 上限

| | 値 | 理由 |
|---|---|---|
| 1回の処理件数 | 200 | Sheets の書き込み Quota（100リクエスト/100秒）に張り付かせない |
| 時間予算 | 240秒 | Vercel の `maxDuration` は 300 秒。超えると途中で殺される |
| 試行回数 | 8回 | 日次 cron でおよそ1週間ぶん |

滞留が残っていることは診断の `pending` 件数に出る。1回で片付けようとしない。

## 残っている限界（正直に書く）

1. **本番Postgresで一度もSQLを流していない。** テストは `psycopg` を差し替えた
   Fake で、プレースホルダの数までは機械的に見ているが、型解決までは見ていない。
   デプロイ前にステージングで `claim_due()` / `enqueue_row_creation()` /
   `record_failure()` を一度は実行すること（2026-09-07、シロクマ指摘）。
2. **キューに積むところが失敗したら、そこは元のまま。**
   DB が落ちていれば積めない。そのとき Slack の文面は
   「再試行キューにも積めませんでした。**自動では復旧しません**」に変わるので、
   黙って落ちることはない（`_handle_new_record_row_not_created()`）。
3. **「行はあるが1列だけ書けなかった」は直せない。** 上記のとおり。
4. **cron は日次**なので、最悪およそ24時間は行ができない。
   Vercel Hobby の cron は1時間のゆらぎがあり、これ以上細かくしても意味が薄い。
   もっと早く埋めたいときは `/api/cron/spreadsheet-outbox-drain` を手で叩く。
5. **本番での実地検証は未了。** マイグレーション適用とデプロイの後、
   実際に1件失敗させて（あるいは既存の取りこぼしを積んで）翌日の cron で
   行ができることを確認する必要がある。
