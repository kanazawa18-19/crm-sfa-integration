# 限定4job試験ツールのローカル実装・独立検証

2026-09-10 主機CX。着手基準 `a00286c`、従来製品基準 `695f850`。
要件は [追加試験計画](sync_capacity_additional_trial_plan.md)。
本書は実装・ローカル検証の記録であり、実サービス試験の結果ではない。

## 今回の範囲

固定scope `trial-retry-deadline-1`、4job、12独立プロセス、共有3枠の試験を用意する。
既存の12job試験の合格条件を変更せず、限定試験として別に判定する。

```text
ローカルで開始条件・予約・異常系を検証
                  │
                  ▼
公式emulatorで12プロセス・保存状態を照合
                  │
                  ▼
独立レビュー・記録 ──▶ 今回の停止位置
```

元台帳の読書き、短期認証の取得・更新、実サービス再照会、使用済scope再実行、
台帳リセット・増枠・期限延長、本番配備は対象外。試験には使い捨て台帳を使う。
元の累計値は既存文書の記録であり、今回の実測値とは扱わない。

## 実装・検証結果

固定コマンド `retry-deadline` / `retry-observe` と専用scopeを追加した。
任意件数・任意scopeの指定機能は追加していない。既存コマンドから新scopeを使う経路も拒否する。
開始権と観測権は各1回。認証失敗・中断でも開始記録を保持し、予約を返却しない。
台帳の内枠と従来累計は同じ排他更新で検査・更新する。

成功診断は子PIDごとに、各操作の競合発生場所・試行経過ms・再試行回数・最終結果を記録する。
SDK本文・認証情報を含めず、失敗側も検証済みの固定診断だけを終了記録へ残す。
自然な初回3秒超の競合後成功がなければ `retry_observation=not_observed` とする。
runnerの保存照合結果を台帳へ保持し、observerは同じjob ID・状態・所有者・枠・試行回数と比較する。
比較元のrunner結果が欠測なら `state=observed` / `runner_result_unavailable` として合格にしない。

### ローカル公式Firestoreでの独立照合

架空のUUID付きdemo project、匿名認証、`127.0.0.1:8787` の公式emulatorだけを使用した。
12実子で3取得・9満枠終了、4job=processing3/pending1、job/owner/slot/attempts一致、
全12PID不在を独立確認した。observerも実GuardedAPIで同じ4件を読み、書込み増分0を確認した。

| ローカル試験の予約増分 | runner | observer |
|---|---:|---:|
| RPC | 58 | 2 |
| read | 290 | 102 |
| write | 15 | 0 |
| runtime秒 | 660 | 60 |

新規文書名は5件。上記はローカル試験の安全側予約であり、実サービス使用量・請求量ではない。
実サービスでも58RPCで済むという推定には使わない。

| 独立検証 | 結果 |
|---|---|
| 通常環境の全pytest | 3,151成功・12skip、20.16秒 |
| 公式emulatorの既存試験 | 10成功 |
| 新規試験suiteのemulator指定実行 | 27成功（全体試験と重複する単体試験を含む） |
| 独立追加検証 | 異常・並列境界・事後観測11成功、取得全体30秒境界3成功 |
| 最終停止確認 | 試験プロセス0、emulatorの8787番待受終了 |

全pytestの12skipはemulator専用11件と既存のcommit非該当stream条件1件。
emulator専用11件は別実行で成功した。上のsuiteを合算して異なる試験件数とは表現しない。
全pytestにemulator環境変数を付けた試行は、既存の非接続SDK試験1件が
「通常projectでのemulator利用禁止」により失敗したため、通常suiteとemulator試験を分けて再確認した。

QAの残WARN：Python 3.14の並列境界試験で、複数スレッド下のforkに関する非推奨警告12件。
今回の実行では停止・不整合は起きていない。実試験runnerは独立subprocess起動で、
このforkは合成台帳の並列境界テスト専用。警告の解消は残課題とする。

初回3.181秒の競合後成功は仮想時計による再現であり、emulatorでも3秒超競合は未観測。
独立証跡は `/private/tmp/crm-capacity-qa/independent_result.json` と
`final-pytest-no-emulator.log`。一時ファイルが失われても再開できるよう、数値と限界を本書に記録した。

開始前に照合する移行履歴のSHA-256（内容一致を確認する値）は、元台帳を今回
開いていないため `EXPECTED_HISTORY_SHA256 = None` のままとする。
未設定では認証取得前に拒否する。テストは使い捨て台帳の合成値だけを注入する。
実操作前には承認されたローカル照合を行い、既存記録との一致を確認した上で固定値を設定する。
現在の台帳から自動的に採用した値を、過去の履歴との一致証明にはしない。

### レビューで確認する境界

- 履歴は「辞書として読める」だけで一致とはしない。開始後の変更検出と、
  開始前から異なっていた履歴の検出を分ける。
- observerの内部整合だけで「同じ結果」としない。今回のrunnerが残した
  job ID・owner・slotと比較する。runnerが失敗した場合の観測成功は試験合格へ昇格しない。
- 製品が保存成功を確定した後の時間切れは、保存を取り消したことにしない。
  限定試験の時間条件を満たしたかは試験側で別に判定する。
- 初稿のemulator試験は仮想時計がSDKの実時計まで変更して失敗した。
  時計を試験ポリシーだけに分離して修正後に成功した。実際の元期限を緩めた修正ではない。
- 固定された過去の日付・区画に依存する試験案は見送った。
  合成時計と試験ごとのdemo区画を使い、期限後も過去データと衝突せず回帰確認できる。

独立SEC・品質の最終確認はそれぞれBLOCKER 0 / WARN 0。
SECの新規対象29件は成功（emulator1件除外）。品質は読み取りレビューでありテスト実行ではない。

## 残る実操作と保証の限界

実操作には、元台帳のローカル照合・必要な短期認証更新・未使用scopeの固定試験1回・
事後観測1回を含む具体的な指示が別途必要。本イシューでは実行しない。
元台帳が記録から変わっていれば自動補正せず、再計画する。

公式emulatorでの成功は、実Firestoreの遅延・IAM・永続性を保証しない。
自然な初回3秒超の競合が観測されなければ「対象事象未観測」とする。
4job試験の成功を従来12job×5回の達成に数えず、本番容量保証・復旧・復元・
実流量の評価は別課題として残す。

## 2026-09-10 実操作前の履歴照合準備（元台帳未読）

基準 `b5fd0f603ff3e666e19c7d3e86e2ddb03f9f3721` をfetch後のorigin/mainと照合した。
今回は保存済みJSONだけを読み、固定指紋の比較元を確定した。元台帳照合・設定・実試験は未実施。

`docs/sync_capacity*.json` を再帰走査し、`target_migration`、
`upper_bound_transition`、`created_at` の3項目を全て持つ辞書を実際に数えると5件だった。
`retry_policy.history()` / `fingerprint()` と同じ3項目の抽出と
`json.dumps(value, sort_keys=True).encode()` のSHA-256で、全5件が同じ値となった。

| 保存済み証跡 | JSON内の位置 | 件数 |
|---|---|---:|
| `sync_capacity_stage_inventory.json` | `ledger_after_transition` | 1 |
| `sync_capacity_stage_concurrency_results.json` | `runs[0].before` / `runs[0].after` / `inspection.before` / `inspection.after` | 4 |

過去証跡から得た比較値：
`4204b2410ed91536e73aae7d71a9d2056aa512d65d2d8d9cf8c02ef0a8381d98`

これは保存履歴5件の一致であって、独立した5回の試験や現在の元台帳との一致ではない。
台帳ファイル全体のSHA-256とも異なる。数値の整数/小数表現やJSONの区切りを変更すると
指紋が変わるため、設定前の照合も実装と同じ形式を使う。

```text
保存済み5件の履歴一致（今回確認）
              │
              ▼
元台帳の読取り照合（具体指示後）
              │ 一致＋累計・停止条件も一致
              ▼
固定指紋設定・独立検証 ──▶ 限定実操作の指示範囲を確認
```

次工程では、元台帳を変更せず上記3項目を比較し、さらにRPC1483、read4438、
write423、delete0、runtime5785、SQL接続5/文24、重複なし文書名90件、
使用済scope1～6、新scopeの開始記録なし、stage2、元期限・停止条件を確認する。
累計が合っていても履歴指紋が違えば停止する。記録の欠落・相違は自動修復しない。
現在の台帳の値で比較元を上書きせず、既存証跡との差分を調べて再計画する。

`EXPECTED_HISTORY_SHA256` は `None` のまま。準備確認のためにrunnerを起動しない。
開始権は認証前に消費されるため、動作確認目的の起動でも一度限りの権利を失いうる。
元台帳照合と設定だけの指示を、認証更新や実RPC実行の指示へ拡張しない。

文書のみの追記。保存JSONの抽出件数・指紋一致・実装の抽出/直列化形式を確認した。
製品コード・元台帳・認証情報は変更せず、製品テストと他社再レビューは再実施していない。
