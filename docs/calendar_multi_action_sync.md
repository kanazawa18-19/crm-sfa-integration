# 案件に紐づく複数TODO・カレンダー予定

2026-11-25。ローカル実装・独立検証済み。本番未反映。Notion/Googleへの新規書込みは未実施。

## 目的

```text
Notion案件
  ├─ 資料送付 2026-11-26 → 案件に紐づくTODO → 11/26の終日予定
  ├─ 電話確認 2026-11-28 → 案件に紐づくTODO → 11/28の終日予定
  └─ 見積準備（日付なし）→ 案件に紐づくTODO → 予定は保留
```

既存TODO DBを使い、各TODOの「🤝 案件管理」で元案件を関連付ける。業務のkintone・スプレッドシート同期は対象外。

## 入力と識別

- 「次回アクション」が空欄でなければ優先し、空欄なら「AI推奨アクション」を使う。
- 複数アクションは箇条書きなどの明示された項目境界で分ける。自由文から勝手に作業数を推測しない。
- 複数タスクでは各項目に書かれた完全な年月日を期限として使う。案件全体の「AI推奨アクション日」1つを全タスクへ配らない。
- 箇条書きは1項目でも本文の日付を使用し、複数から1項目に減っても取得元を変えない。箇条書きでない単一文章の日付は従来の「AI推奨アクション日」を使用する。日付がないTODOも作り、カレンダーだけ保留する。
- 年の省略・「明日」などの相対日付は推測しない。同じ項目に複数候補日がある場合、実行日の日本時間で今日以降の最短日、全て過去なら最新日を選ぶ。日を跨ぐ再通知では選択日が変わる場合がある。
- `[id:quote]`などの明示IDがあれば案件ID＋そのIDで識別する。IDがなければ日付を除いた本文から識別する。
- 並び替え・日付変更では同じTODO/予定を更新する。日付直後の曜日括弧も識別から除く。明示IDなしの本文変更は別タスクになる。以前のTODO/予定を自動削除しない。
- 同じ内容の別タスクには異なる明示IDを付ける。識別子衝突を推測で統合しない。

入力例：

```text
- [id:send-material] 資料を送付する 2026-11-26
- [id:call] 電話で確認する 2026-11-28
- [id:quote] 見積を作成する
```

## 保護するもの

- 新規TODOの状態は「未着手」。手で変更した状態や管理項目を自動で戻さない。
- TODOを作ってから対応する予定を登録する。予定登録の失敗時にTODOを作り直さない。
- Notionの作成応答が不明な場合は、再送による重複を避け、作成予約を残して照合待ちにする。確定エラーを含め自動で予約を解放せず、手動確認が必要な場合がある。
- カレンダー送信前にも予約を保存する。送信結果不明の場合、遅れて古い更新が届く可能性を考慮し、そのタスクのTODO・予定の次回更新も照合まで止める。
- TODOから予定の応答確認まで同じタスクを直列化する。案件内の再開位置も保存し、時間不足で未着手のタスクは次の再通知で続きから処理する。定期的な再送ジョブは今回追加しない。
- 旧方式の「案件につき1予定」と新方式のタスク別予定が衝突する場合、推測移行・削除せず保留する。
- 日付・本文の空欄化、案件やTODOの削除、担当者変更に伴う旧予定の削除・移管は自動実行しない。
- Google予定の直接編集は保護対象ではない。同期対象の件名・日付・説明は案件の内容で更新される。
- TODOの更新前後を読取り照合する。ただしNotionには条件付き更新がないため、直前読取りと書込みの間の人編集を完全に排除できない。

## 有効化

`PROJECT_ACTION_TODO_ENABLED=true` で新しい処理を有効にする。既定はOFFで従来の単一予定経路を維持する。ON時はCalendarの設定がなくてもTODOを処理し、予定のみ保留する。Notion認証と既存DB・予約表を使い、新しい表の追加は不要。

## 本番化前の確認

受信側APIとCRM側を合わせて公開し、既存のDB利用上限を解消してから実接続の確認が必要。今回のローカル試験を実APIへの登録成功と扱わない。

## 切替と保留の復旧

1. 旧経路からの案件処理を止め、実行中の処理が終わるのを待つ。旧方式と新方式が同時に「予定なし」を確認して作成する競合を避ける。
2. 受信側を対応版にし、その後CRM側の新機能を有効化する。本番公開は別途本人指示後。
3. 既存案件単位予定があれば一覧・内容を確認して移行方針を決める。自動で転用・削除しない。
4. 日付不足は当該項目に完全年月日を入力して案件を再通知。担当・Google未接続は該当設定を直してから再通知する。
5. 作成結果不明・更新結果不明は、外部の保存結果と予約台帳を照合するまで予約を消さない。通常の再実行で再POSTしない。
6. 人編集・完了による保留は、その状態を尊重する。保留解消目的で未着手へ自動で戻さない。

有効化は全案件の一括生成ではない。既存の案件変更通知が起点であり、過去案件の一括生成は別作業。

担当メンバーが複数の場合、Notion TODOには全員を設定し、Google予定は従来どおり先頭1名の連携先へ登録する。顧客を参加者として招待しない。

## 原本の版と検証結果

原本の更新時刻を外部書込み前に保存し、取得済みでも古い情報は反映しない。同時刻で内容が違う場合や更新時刻が不明な場合は保留する。同時刻・同内容は続きから再開できる。

独立QA566件（ローカル558・実PostgreSQL8）成功、スキップ0。MA46件・型検査成功。架空3タスクのプレビューはTODO3件・予定2件（日付なし1件）。内部SEC/品質/QAとGemini/Claudeの指摘採否は `reviews/calendar-multi-action-20261125/`。実API保存は未検証。

「再通知」は定期自動実行ではない。運用者が既存Webhook受付へ同じ案件の通知を再投入する操作を指す。対象5項目を変更すると別の入力として先頭から照合する。原本の内容を再開目的だけで変更しない。結果不明予約の手動照合・解除は別の確認作業であり、通常再通知では解除されない。
