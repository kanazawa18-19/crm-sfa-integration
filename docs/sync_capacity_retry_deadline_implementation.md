# 同期容量の総期限共有と競合再試行

2026-09-10 主機CX。設計は `sync_capacity_retry_deadline_design.md`。
本書はローカル実装・検証を記録する。実サービスの競合解消・応答時間の保証ではない。

## 変更の目的

初回の確定競合が3秒を超えると、総処理時間に余裕があっても再試行されなかった。
処理全体の絶対期限を共有し、次の試行に必要な時間が残る場合だけ最新値で再試行する。
保存結果不明の通信失敗は再送しない。成功応答を受け取った保存は期限超過で取り消さない。

```text
受付・worker開始 ──▶ 絶対期限
                       ├── 待機・query・候補全体
                       ├── scope/job読取り・比較保存
                       └── 試験ガード・追加読取り・台帳待機
                                 │
                      確定競合＋次試行予算あり
                                 ▼
                        新batchで最新値を読む
```

## 時間配分の根拠

| 場所 | 設定値 | 根拠・意味 |
|---|---:|---|
| ストア操作・HTTP保存 | 30秒 | 未実測の既定。呼出し元期限を注入できる |
| worker全体 | 300秒 | 既存outboxの300秒実行枠を基準に配分 |
| 業務開始に必要な残時間 | 240秒＋終了保存分 | 既存outboxの業務予算240秒との整合 |
| 終了保存の予約 | 10秒 | 業務に使わせない保存用の時間 |
| claim | 最大30秒 | 業務と保存の予約を差し引き、取得だけで使い切らない |
| RPC開始最低予算 | 0.05秒 | 未実測・注入可能な開始許可条件 |
| 1試行開始最低予算 | 0.3秒 | 読取り2・保存1・ガード追加読取り等3の計6RPC最低予算 |

RPCの上限10秒と開始最低予算は別である。各通信は残時間でtimeoutを短縮し、
1試行を開始できたことは完了までの所要時間を保証しない。

独立SECが、初稿のworker固定45秒では既存240秒のoutboxと矛盾し、
仮想41秒の成功でもfinishが0回になる問題を検出した。既存業務予算に整合させる修正を採用。
単に「長い処理は未対応」と文書化する案は、既存動作の後退を残すため見送った。

## 配備前に確認する制限

- 秒数は測定結果ではなく、注入可能な設定値。Webhook提供元や実配備の制約に
  合致するかは未検証。本番配備の承認・容量保証にはしない。
- 同期業務や動作中のSDK呼出しを強制中断する仕組みではない。期限とRPCのtimeoutにより
  新規処理の開始を制限する。業務が想定時間を超え、終了保存に必要な時間がなければ枠を保持する。
- 読取り側のSDK自動再送も無効にする。読取りの一時的通信失敗を成功に見せず呼出し元へ返す。
- 旧V1診断の3秒判定は変更しない。V2は総期限・試行予算・8回上限・不確定連鎖を区別する。
- 使用済scopeの再実行、台帳リセット・増枠、認証更新、実サービス再照会は行わない。
  前回記録の残517RPC・文書名残10を引き継ぐ。今回の実測値ではない。

独立11件は `tests/sync_capacity/test_retry_deadline.py` に移植した。
初回3.181秒競合、2回連続競合後成功、最大8回、新batch/再読取り、再試行時満枠、
queryから複数候補の期限共有、ガード追加読取り、短timeout、予約後期限到達、

これらは実SDK・モックRPC・仮想時計、および公式ローカルemulatorによる試験である。
emulatorは停止済み。実サービスの競合遅延・IAM・永続性の保証ではない。

### Gemini Proの採否

受領指摘はB1/W1/I1。独立SECで一次コードとローカル実動作を照合した。

| 指摘 | 採否・根拠 |
|---|---|
| B1 ロック取得直後の期限例外で永久ロック漏れ | 不採用。呼出し元with openが例外でcloseする。ローカル一時ファイルで当該例外後、別プロセスがロックを即取得することを独立検証 |
| W1 stream finallyのusing_deadlineは重複なので削除 | 不採用。生成器の実行はcallのwith終了後。実GuardedAPI＋モック通信でcall後は期限なし、finally内は期限あり、終了後なしを確認。削除すると台帳の期限が消える |
| I1 呼出し元とbudgetedの二重設定 | 変更不要。最短期限と厳しいminimumを合成するため、期限延長・条件緩和はない |

### Claude Opus 5・中の採否

受領指摘はB3/W6。INFOは本文の箇条書きを数えて6項目（回答冒頭は5と表記）。
差分にないコードを仮定した指摘を含むため、独立SEC・品質と一次コードを照合した。

| 指摘 | 採否・根拠 |
|---|---|
| B1 HTTP保存前の期限不足がsave_unconfirmed | ログ分類改善を採用。save_not_startedを追加。ただしoutcomeはログだけでHTTPは503のため「再送対象外になりデータ欠落」は誤認 |
| B2 V1 atomicをV2接頭辞で再出力するとinvalid | 採用。現製品はV2生成のみだが、受理するV1形状の再出力も接頭辞を整合させる |
| B3 期限例外が競合例外捕捉に入る | 不採用。実コードはexcept conflictsであり、仮定されたexcept Exceptionではない。phaseは送信済み保証ではなく処理段階 |
| W1 初期化前の期限不足がneeds_attentionになる | 状態に関する仮定は誤りで既にretry。ただし未開始を区別するログ改善を採用 |
| W2 finish未開始を結果不明と記録 | 未開始ログ分類を採用。枠解放・業務再実行案は不採用。既に業務の副作用が発生しているため枠を保持する |
| W3 計測用monotonic引数と期限時計が別 | 見送り。計測引数は既存の用途で、期限はmodule時計を差し替え仮想検証済み。新たな時計ドメインの混在を導入しない |
| W4 残予算不足をValueErrorにすべき | 不採用。残時間減少は設定不正とは限らず、期限例外で開始前停止するのが意図どおり |
| W5 GuardedAPIの各callで期限リセット | 現経路に対して不採用。storeの親期限と最短合成し、追加read/台帳まで共有。単独callはその操作の期限を確立。0/負timeoutを下限へ拡大する案も、短timeout非拡大要件に反するため不採用 |
| W6 台帳lock待機の指数backoff | 見送り。10ms sleepがあり、負荷問題は未実測。期限付き待機は検証済み |
| INFO6項目 | 変更不要。期限検証、standalone batchの期限、理由の優先順位、budgetedの非None保証、固定error_code、import順。いずれも完了を妨げない |

別途、親が短い期限を指定したdrain_oneで、開始判定だけ長い既定期限を参照する点を
独立品質が仮想再現した。入口でeffective_deadlineを合成し全段階に適用する修正と
回帰3件を追加。通常run_workerは同じ明示期限のため当該条件に非該当だが、注入契約を満たすため修正した。
