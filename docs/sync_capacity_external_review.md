## Claude：BLOCKER 4、WARN 10の採否

| ID | 指摘 | 一次コードとの照合・判断 |
|---|---|---|
| B-1 | 同じ内容の後日の編集が永久に重複扱い | 通常のGASは `gas/onEdit.js` で毎回 `editedAt` を生成し、Kintoneは更新日時が必須。一般化した欠落の主張は非該当。ただしNotionの通知ID・時刻が両方欠けた入力は再現できるため、受付UUIDで別要求として保全する防御を採用 |
| B-2 | outboxの生産頻度以上にdrainできず要求が滞留 | 容量確認の指摘は採用。現行outboxは `vercel.json` で日次1回、両方毎分という再現条件は現設定ではない。古い要求優先なので後着outboxが先着Webhookを追い越し続ける意味の飢餓でもない。流入量にoutbox自身・初期化再試行を含める配備条件を明記する |
| B-3 | 共通scope文書が処理量の制約 | 集中点がある指摘は採用。ただしエミュレーターの失敗48/60を本番の1文書書込み限界と断定できない。実測では読取りロックから書込みへの切替が約2秒で失敗した。両文書の更新時刻を前提にした原子保存でロック待ちを避ける。実Firestoreでの持続処理量測定は引き続き配備条件 |
| B-4 | 強制終了で枠を失い手動復旧が必要 | 可用性の制約として採用。強制終了が日常的という実測は無い。時間超過だけで旧処理・DB処理の停止を証明できないため、期限による自動解放は不採用。処理時間とプラットフォーム上限の適合、保持枠監視、全処理停止後の復旧所要時間を配備前に確認する |
| W-1 | 決定的な候補・slot選択と競合分類 | ランダム化・再試行増加だけでは改善が安定せず不採用。保存方式の変更を優先する。確実な競合と応答不明を同じ意味の成功とは扱わない |
| W-2 | 受信記録の例外で業務処理を保留してしまう | 非該当。`record_webhook_receipt()` 自身がDB例外を捕捉し、業務処理は続行する |
| W-3 | 初期化失敗を無期限に再試行 | 制約として採用。60秒後へ戻すため先着の正常pendingを追い越し続けないが、再試行は処理量を消費する。初期化失敗は共有設定の一時障害を含むため、一律回数で大量の要求を手動復旧へ送る変更は見送る。滞留・再試行の監視と流量計算が必要 |
| W-4 | 理由無し `skipped: true` が完了になる | 現経路では非該当。4ハンドラのboolean skipはDispatcherの戻り値で、`ObservedDispatcher` が空・不明reasonを保全対象にする。Dispatcher前の早期終了は理由文字列を返す |
| W-5 | 保存用データの過大入力を503にする | 採用。生bodyは既に413だが、保存用ヘッダー追加後の大きさも413に分類する。その他の要求構築エラーは400にする |
| W-6 | cron認証の位置引数への依存 | 引数名を明示する小修正を採用 |
| W-7 | Dispatcherの属性委譲不足 | 非該当。全4ハンドラの参照は `dispatch()` のみ。不要な全属性委譲は追加しない |
| W-8 | 同じ通知IDで配送メタデータが変わると409 | 採用。Notionの `attempt_number` を重複照合から除外し、実データの違いは引き続き409にする。「最初の保存失敗・後続409で全消失」は非該当で、409時は既存jobが保全されている |
| W-9 | 要求ごとのFirestore client生成 | 性能確認項目として保持。環境切替を跨ぐclient共有は今回追加しない。実環境ではclient生成・認証・通信を含む入口/worker全体の所要時間を測る |
| W-10 | CLI `drain` が手動復旧説明に無い | 説明追加を採用。既存CLIは有効フラグを検査済み。実業務書込みを伴うコマンドとして明記する |

Notionの配送フィールドは[公式イベント仕様](https://developers.notion.com/reference/webhooks-events-delivery)と照合した。生bodyへの署名検証後に重複照合用データだけを正規化し、業務データまで無条件に同一扱いする緩和はしない。

## 保存方式の比較

| 比較 | 隔離エミュレーターでの観測 |
|---|---|
| 元実装の最終計測 | 12プロセス×5回：取得12、競合例外48、上限超過0 |
| 候補・slotランダム化 | 12呼出中3取得・9失敗する回を再現。共通scopeの競合は残る |
| SDK内部8回再試行 | 12×5：取得13、満枠27、例外20、上限超過0。失敗回は最長16.56秒で、待ち時間が増大 |
| 更新時刻条件付き原子保存のclaim試作 | 12×3：取得9、満枠27、例外0、上限超過0、最大2.283秒。scopeだけ／jobだけが先行変更された2ケースで両方とも書き換わらないことを確認 |

SDKの再試行は元transaction IDで順番を保持するが、エミュレーターでは約2秒のロック待ち失敗が8回続くケースが残った。試作結果だけを製品の最終検証とは扱わない。

[Firestore Commit](https://docs.cloud.google.com/firestore/docs/reference/rest/v1/projects.databases.documents/commit) は一組の書込みを原子的に実行する。[エミュレーターの制約](https://firebase.google.com/docs/emulator-suite/connect_firestore)では本番のtransaction動作を完全には再現しないことが明記されている。そのため本番性能・IAM・永続性の確認は別途必要。
