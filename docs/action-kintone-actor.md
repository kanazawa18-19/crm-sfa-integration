# kintoneアクションの実担当者と未確定サービス

案件なしのアクションも保持する。kintoneアカウントのない担当者を、管理者など別人のアカウントへ置き換えない。対象はアクションだけで、案件管理など他DBの既存担当者対応は変更しない。

2026-10-15本人方針：この扱いは今回の担当者に限定せず、今後の全担当者へ適用する。kintoneは本人の1アカウントのみという運用前提で、確認済み対応にない人へアカウントを割り当てない。アカウントが増えた場合は対応設定を更新する。

## 作成時の判断

1. Notionの「担当営業」の集計が確定していれば、そのユーザーIDを実担当者の根拠にする。
2. 集計が確定空配列の場合だけ、承認済みの原本別設定を使用する。原本別設定がない場合は、本人承認済みの作成者ID一覧 `self_actor_creators` に含まれる人だけ、作成者本人を担当者とする。未承認の作成者へ一般化しない。
3. 実担当者全員に有効なkintone対応がある場合は、対応者欄へ設定する。
4. アカウントがない人を含む場合は対応者欄を明示的に空配列で送り、全員の実名をコメントの専用枠へ保存する。一部の担当者だけ残すことも、管理者へ代替することもしない。
5. 提案サービスの集計が確定空配列の場合は、外部の既存選択肢「未確定」を使う。集計未完了・選択肢未存在の場合は保留する。

対応者欄がまだ必須の場合は作成を保留する。コメントの補足を入れても、利用者が書いた履歴本文は保持する。

## 設定

実ユーザーID・氏名・対象原本IDは環境設定に置く。コードやこの資料には書かない。

`CRM_USER_MAPPING_JSON` の確認済みユーザー行に `display_name` を追加する。`kintone_code` は現在有効なアカウントだけに設定する。確認済みの表示名は設定値を使う。未登録の担当者や表示名が未設定の担当者は、原本で確定したNotionユーザーIDを `GET /users/{id}` で照会し、人間のユーザー・同一ID・有効な表示名を確認してコメントへ保存する。担当者ごとの事前登録は不要。取得不能・bot・別ID・空の氏名なら保留し、対象IDと対処方法を理由へ記録する。氏名・連携権限を直した後に対象原本の同期を再実行する（この保留に自動再試行は追加していない）。退職・ゲスト等でAPI取得不能な場合は、原本から氏名と担当者の同一性を確認したうえで確認済み表示名を設定し、対象原本の同期を再実行する。推測名で埋めない。アクション内では設定側のUUIDも正規化し、正規化後の重複や不正IDは保留する。他DBの対応設定処理は変えない。既存 `fallback_notion_id` はこのアクション作成では使わない。

`CRM_ACTION_ACTORS_JSON` の構造:

```json
{
  "verified": true,
  "records": {
    "承認済みの原本ページUUID": {
      "notion_user_id": "実担当者のNotionユーザーUUID",
      "expected_created_by": "原本で確認した作成者UUID"
    }
  }
}
```

キーはUUIDとして正規化し、不正なキー・正規化後の重複は保留する。対象外ページ、作成者が変わったページ、氏名を確認できないユーザーは保留する。新規対象を追加するときも、原本・業務上の実担当者を確認してから登録する。原本別設定は「担当営業が空欄の例外」に必要であり、担当営業が確定している新担当者の氏名取得には不要。原本別設定で確認済みの担当者も、ユーザー対応への事前登録なしでNotion氏名照会を利用できる。作成者照合の条件は変えない。設定自体をリポジトリへ保存しない。

## メモの往復

コメント末尾の `【CRM同期:実担当者】` から `【/CRM同期:実担当者】` はシステム管理枠。通常同期では最新コメントと版番号を取得し、本文だけ置き換えてこの枠を保持する。取得項目不足・版競合・枠の重複や破損は書き込まず保留する。文字数上限で切り捨てない。

kintoneから戻るコメントは管理枠を分離し、利用者本文だけをNotionの履歴メモへ送る。枠が不正なら、その項目を同期しない。メモの往復で担当者補足が本文へ混入したり、何度も増えたりしない。通常の本文編集から実担当者の枠を差し替えることは許可しない。

担当営業・提案サービスは既存の読み取り専用集計欄のまま。今回の変更は作成時の担当者決定と、以降の本文更新による補足消失の防止であり、集計変更による担当者の自動再割当を追加するものではない。

## 対象限定の復旧

通常の作成サービスを使う。既存のZoho IDがある対象は、その送り先の計画・作成より前にスキップする。kintoneの不足分だけを作成する。既存reserved/created予約は解除しない。対象外の保留を一括再送しない。

検証には、原本限定の承認照合、管理者への誤割当防止、未完了集計の保留、本文の往復、競合時の無書込み、既存Zohoへの再送防止を含む。実サービスでの復旧・結果確認は別途行う。

## 外部レビューの採否

- **管理枠のCRLF対応を採用**。枠内はLFまたはCRLFで統一された形式を受け付ける。本文全体の改行は正規化せず、本文と管理枠の区切りも保持する。枠内だけ改行形式が混在するものや、末尾以外の枠は保留する。
- **対応者の必須チェックがないという指摘は不採用**。作成payload構築後に既存の `missing_required_reason` が全必須項目を判定する。対応者が必須のままなら空配列で作成されないことをテストで確認した。
- **通常同期の二重GETという指摘は不採用**。今回の履歴コメント保護はactionだけ、既存の選択肢メモ保護はprojectだけで相互排他。同一処理で両方の読取りは発生しない。
- **作成者コンテキストが次のレコードへ残るという指摘は不採用**。`candidate_context` はcontext managerの `finally` でリセットする。原本ごとの値を永続的な共通変数へ保存していない。

### コメントの読取経路

| 経路 | 管理枠の扱い |
|---|---|
| kintone Webhook、取りこぼし再送・棚卸し | `KINTONE_FIELD_TRANSFORMS` の本文分離を共有する。 |
| 外部新規取込 `new_record_builder`、同期確認 `sync_review` | 同じ変換表を使うため本文だけを比較・入力する。 |
| kintone作成前の候補照合 | 両方のコメントを本文へ分離して比較する。枠の有無や改行形式だけで既存履歴を別物にしない。壊れた枠は保留。送信payloadの枠は維持する。 |
| 旧CSV移行 `transform_kintone_action` | CSVの「コメント」も本文分離する。不正な枠は例外として止め、原本へ流さない。過去処理の再実行は行わない。 |
| Notion→kintone通常更新 | 最新コメントの枠を保持し、版番号を指定して本文を更新する。 |

## 作成者本人を担当者とする承認（2026-10-16）

本人が特定の作成者について「作成したなら担当も本人」と確定した場合、`CRM_ACTION_ACTORS_JSON` の `self_actor_creators` にそのNotionユーザーUUIDを設定する。`verified: true` が必須。担当営業が確定空配列の場合だけ有効で、既存の明示担当営業や未完了集計を上書きしない。原本別設定が存在する場合はそちらを優先し、作成者不一致をこの一覧で救済しない。UUIDは正規化して比較する。氏名・kintoneアカウント不在の扱いは上記と同じ。個別原本の追加設定なしで今後の新規作成にも適用する。

運用設定には今回本人が確認した作成者1名だけを追加し、全作成者への自動適用はしない。過去の完了済みレコードは再作成しない。施設・関連先の未確定は担当者の承認と別に保留する。
