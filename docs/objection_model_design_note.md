## 材料はある（2026-09-03 実測）

`ProjectMirror`（案件管理DBのPostgresミラー）27,749件のうち、自由記述の充足率。

| 項目 | 件数 | 充足率 |
|---|---|---|
| 失注理由 | 1,784 | 6.4% |
| メモ | 1,876 | 6.8% |
| 次回アクション | 2,006 | 7.2% |
| ネックポイント | 446 | 1.6% |
| テキスト | 30 | 0.1% |

充足率は低いが、**件数としては1,784件の失注理由がある。** 断りの型を取り出すには十分。

### 失注理由の上位（実データ）

```
   現状必要性がない        43        本社管理                26
   連絡取れず             38        不要                    16
   時期見送り             32        進展なし                13
   時期尚早               32        本社決裁                10
   エリア支配人との商談が                間に合っている            9
   できるまで進まない       26        上申の結果、導入しない      9
```

読むと、断りは大きく3種類しかない。

```
   ┌─ 必要性 ────  「今のままで足りている」「必要性がない」「間に合っている」
   ├─ タイミング ─  「時期尚早」「時期見送り」
   └─ 決裁 ──────  「本社管理」「本社決裁」「エリア支配人と話せない」
```

**「決裁」型が想像以上に多い。** 現場は乗り気でも本社で止まる。
これは商品説明の問題ではなく**進め方の問題**で、回答モデルの作り分けが要る。

## 設計案

```
   ① 集計   提案サービス（商品）× 顧客種別 で 失注理由・ネックポイントを束ねる
              → Postgres だけで完結。API呼び出しゼロ
   ② 分類   束ねた自由記述を「必要性 / タイミング / 決裁 / 価格 / 競合 / その他」へ
              → claude-haiku-4-5（定型の分類。大量ループの1件処理）
   ③ 生成   商品ごとに「想定質問」「想定ネガティブ」「回答モデル」を書き起こす
              → claude-sonnet-5（文章の質が要る）
   ④ 保存   生成結果をDBに保存し、画面は保存済みを読むだけにする
              → 画面表示のたびにAPIを呼ばない。再生成は明示操作か週次
   ⑤ 表示   商品ページ／案件詳細に「この商品でよく出る断りと返し方」として出す
```

### モデルの使い分け

金沢さんのモデル階層ルール（軽い作業はHaiku、下流に効く判断はSonnet以上）に沿う。
分類は定型なのでHaiku、回答モデルの文章はSonnet。**惰性でOpusを使わない。**

### 出典を必ず添える

生成した想定ネガティブには、**元になった案件件数と実際の文言**を並べる。

```
   ✗ 「価格が高いと言われがちです」
   ○ 「決裁で止まる（該当34件）。実際の記録:『本社管理』『上申の結果、導入しない』
       …… 現場ではなく決裁者に当てる導線が要る」
```

根拠の無い一般論は営業の役に立たない。**必ず実データの件数と原文を出す。**
