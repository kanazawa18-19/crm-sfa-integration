# 項目の空欄削除を確認する

Notion・シート・外部CRMから空欄になった項目は、通常の値変更と分けて `SyncFieldReview` へ保存する。元レコード自体を削除する機能ではない。管理画面 `/sync-review` はDBの `User.isManager` がtrueの利用者だけに表示し、実行APIでも再確認する。

## 判断と配送

- 1回目確認 → 最終承認 → 既存送り先の対象項目だけを消去する。最初のボタンでは配送しない。
- 却下は案件・項目ごとに、読み取れた元値への復元／項目全体の同期を保留して元ツールの空欄を維持、から選ぶ。復元先は空欄化した元ツールだけ。全ツールの同項目を保留する間も他の項目は処理する。
- 保留元へ値を再入力したことを実値で確認したら、未配送の保留を終了する。途中配送済みは自動解除しない。
- 通常変換が空欄を抑止していた外部項目も `SyncEvent.clear_requests` で承認経路に渡す。不正値・未取得を空欄に変換しない。

## 確認範囲と再開

通常同期と同じレコードロックを使用する。送り先ID、対象欄の値、代表欄に付随する全選択保存枠を承認時の記録と比較し、違えば消去しない。対象項目が対応未確認・読取不能なら保留する。既存の他項目・メモ本文・別選択項目の保存枠を維持する。Notionの対象関連は全件取得する。

配送直前に予定値をDB保存し、送り先ごとに読戻す。処理が途中終了した場合は、配送待ち・復元待ち・失敗から再開できる。実値が予定値である場合だけ配送済みと扱う。値が変わって再開できない場合は、旧snapshotを判断履歴へ保存して現在値で最初から再確認できる。

Zoho/kintoneは取得した版を条件に更新する。Notion/Sheetsには同等の原子的な条件更新が無いため、書込み直前の読取と自システム内のロックで保護するが、利用者の手動編集とAPI書込が同時に起きるごく短い隙間までは保証しない。シートは既存の同期キー検査と行のロックを共有する。

## 台帳・画面

マネージャー判断の実行者・操作・版・時刻・その時点の値を履歴に保持する。処理待ちと、処理済み/空欄維持は別一覧で各50件のページ切替。判断履歴は各項目から確認できる。未対応の外部項目やAPI必須欄の制約は承認で無視せず、理由を表示して保留する。

`20260928050000_sync_field_review` migrationが先に必要。実DBテストは `SYNC_REVIEW_TEST_DATABASE_URL` で明示した localhost の `crm_field_review_test` のみを受け付ける。試験用schemaを毎回作って撤去し、本番URLへは接続しない。

kintoneは全項目通知のため、初回に見えた空欄だけでは削除申請を作らない。
レコードごとの直前観測値を`SyncSourceObservation`へ保存し、既知の非空欄から空欄への変更だけを申請する。
初回の空欄や他ツール比較で発見した空欄は他ツールへ配送しない。既存値の観測前に消された項目は自動起票できない。
空欄維持を選んだ後も履歴画面から現在値で判断をやり直せる。空欄のままなら二段階承認へ戻り、その操作だけでは削除しない。
