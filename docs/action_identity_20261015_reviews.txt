【W1】plan冒頭の actionComparison 削除と defer() の組み合わせで、照合のしおりが消える

該当箇所: adapters.py の ZohoCreationAdapter.plan と duplicate_scan.py の defer / scan_input_hash

再現条件:

Zohoのアクションが2000件を超え、分割照合が複数回の実行にまたがって進んでいる。journal の行は inputHash=H1（actionComparison を含むハッシュ）、たとえば phase=full, last_id=8000 の状態。
次の実行で、plan() 冒頭の context.pop('actionComparison') の後、/settings/fields か /settings/layouts の取得中に http_budget(60) を超える（429 待機などで発生しうる）。
except HttpBudgetExceeded から defer() が呼ばれる。この時点の context には actionComparison がないため、fingerprint は H0 になり H1 と一致しない。
その結果、checkpoint = {'phase':'full','last_id':'0',...} で行が上書きされ、last_id=8000 までの進捗が失われる。次の check() でも H1≠H0 なので、また先頭からやり直しになる。

もう一つの影響として、行が state='held'（6回進まず、通信失敗3回など、手動での再通知が必要な状態）でも、ハッシュが一致しないため早期 return されず、pending に上書きされます。手動再通知を必須にする仕組みを、メタデータ取得の時間切れだけで素通りできてしまいます。

差分前は defer と check が同じ digest(context) を使っていたため、この問題は起きていませんでした。既存テスト test_old_action_checkpoint_..._defer_first と test_changed_external_mapping_..._defer_first は、比較条件がない状態で既存の行がある組み合わせを通っていません。

修正案: 比較条件が未確定の時点での defer は、既存の行に触れないようにします。

【W2】原本の再通知が、後発の重複ページに阻まれる

該当箇所: service.py の _check_creation_duplicates（Notion経路では毎回実行される）

再現条件:

Notionでアクション A を作成する。Zohoへの作成は成功し、kintoneは担当者対応が未設定のため target 単位で保留になる。
誰かが A と同じ内容の B を作成する。B は Notion 照合で A を見つけ、source 単位で保留になる。ここまでは仕様どおりです。
管理者が kintone の担当者対応を設定し、A を再通知する。
A の Notion 照合が self_id=A で B を見つけるため、A 自身も source 単位で保留される。その結果、A の kintone 作成は B をアーカイブするまで進みません。

アクションの場合、以前は「タイトルが同じ」という条件だったため、このケースはほとんど起きませんでした。内容一致に変えたことで、発生しやすくなっています。

修正案（どちらか、または両方）:

自分の source_key に created または reserved の attempt が1件でもあれば、その原本は既に作成を開始済みとみなし、Notion照合を省略する。
一致した候補が自分より後に作られたもの（created_time が新しい、または同時刻で ID が大きい）であれば、保留しない。後発の側だけを止めます。

【W3】同日・同内容の正当な複数接触に解除手段がない（業務判断が必要）

再現条件: 同じ取引先に同じ日、テレアポを2回かけて2回とも不在だったケースです。種別、メモ「担当者不在」、先方担当者がすべて同じで、案件はなし。タイトルは「1回目」と「2回目」で異なります。

2回目は Notion 照合で保留されます。この保留は CreationHeld を直接送出していて、hold_duplicate を経由しないため、管理画面の候補に出ず、見送り操作ができません。
仮に Notion 照合を通過しても、Zoho と kintone では1回目の created 予約と同じ fingerprint になります。そのため reserve が一意制約で False になり、恒久的に保留されます。Zoho の候補を管理画面で見送っても解除されません。

「同内容の別原本は保守的に保留する」という仕様には沿っています。ただ、架電履歴では日常的に起きるパターンなので、利用者はメモの文言を変えて回避するしかない状態です。

修正案（業務判断のうえで選択）:

管理者が「別の接触として承認」した原本だけ、fingerprint に承認IDを加えて一意制約から外す（監査ログに記録する）。
または、運用ルールとして「同日の再接触はメモに時刻や回数を書く」ことをシートとNotionの入力説明に明記し、保留メッセージにも書き方を案内する。

【W4】シート経路の入力形式（実データでの確認が必要）

シート経路では、title_value の直後に _creation_fingerprint → identity が呼ばれるようになりました。sheet_properties の戻り値が次のいずれかに当たる場合、シート登録のアクションは全件保留になります。

取引先がUUIDではなく顧客名やラベルになっている（テストでも ‘client’ から UUID に書き換えています）
アクション日が 2026/10/13 や 10/13 の形式（action_day は ISO 形式しか受け付けません）

テストはすべて合成の ISO 値と UUID です。本番シートの実際の値で sheet_properties の出力を確認してください。必要であれば、action_day で / 区切りを受け付けるか、sheet_properties 側でISO形式に正規化してください。

【W5】Notion候補を全項目解析している

候補ごとに _creation_properties を呼んでいるため、照合に使わない全項目の parse_notion_property_value と、担当営業・提案サービスの creation_rollup まで実行されます。無関係な過去のアクション1件でこれらが例外を出すと（照合キー以外の項目の型変更、ロールアップの異常値など）、その取引先の新規アクションがすべて保留されるか、汎用例外として扱われます。

修正案: 候補には validate_notion_identity と照合に使う6項目だけの抽出を行う軽量関数を使ってください。原本と候補で同じ抽出規則を使うという方針は、その関数を共通化すれば維持できます。
