## 不足先の安全な調査手順

1. `scripts/inventory_unmapped_hub_records.py` を読取実行。6DBの完走結果を使用する。非対応の保存先（連絡先のkintone等）は不足としない。重複対応・原本不在は回復候補にしない。
2. `python scripts/triage_missing_targets.py <DBの一覧.json> <新しい分類.json>`。取得開始から6時間以内の新規走査だけを読み、DBも読取専用。--resumeの一覧、取得開始時刻のない旧形式、時刻の逆転は拒否する。出力は本人だけが読める新規ファイル。本文・名前・理由自由文は含まない。
3. `creation_result_unknown` は成否調査まで再POST禁止。`mapping_restore_requires_readback` は作成済みIDの実物と同一性照合が先。`registration_intent_unconfirmed` は既存外部原本の取込み等を新規作成と取り違えない。
4. `input_or_identity_review_required` は原本の必須項目・親関連・重複候補を実読して判断。自由文のキーワードだけで自動解除しない。シート行移動は元一覧の `sheet_review_rows` も照合する。
5. 根拠が揃った特定IDだけ `scripts/recover_missing_target.py <新計画.json> --db-key ... --id ... --target ...` で計画を作る。適用は既存CLIの `--apply` に分離し、原本ハッシュと既存予約の確認を維持する。

自動スケジュール・全件一括再作成・成否不明の予約解除は追加していない。既存CLIとの全体実通信はDB復旧待ち。

## 本文保存期間

`python scripts/report_email_body_retention.py --days <比較日数>`。接続変数の既定は `DATABASE_URL_UNPOOLED`、`.env`の自動読込はしない。
状態・更新時刻別の件数/本文UTF-8バイト数だけを返す。日数に既定値を持たせず、比較結果を削除承認としない。
受付のupdatedAtで区切るため、メール受信日からの保持期間とは異なる。DB解放容量の予測でもない。
pending/held/結果不明、根拠として参照される受信メール、訂正照合に必要な送信メールを一律削除しない。
削除を実装する場合は本文・snippet・判断履歴の抜粋・候補根拠・配送済み本文を分け、参照と再取得の挙動を決める必要がある。

## 容量監視の接続準備

`python -m src.sync_capacity observe` の結果を保存し、次のCLIで通知用JSONへ変換する。

```text
python scripts/check_capacity_observation.py <観測.json>
  --last-worker-success <成功または正常idleの実測epoch秒>
  --freshness-seconds <許容途絶秒>
  --waiting-seconds <許容待機秒>
  --processing-seconds <許容処理秒>
```

実行時は1行にする。異常時は終了コード2。worker成功時刻が未取得なら省略し、欠測として通知候補にする。
開始/終了時刻の矛盾・未来・欠測は正常とせず、観測後の経過も滞留時間に加える。処理中の時刻はclaim時のupdated_atを使う。
このCLIはファイル入力だけで、Slack送信・原本更新・再送・ロック解放はしない。処理中の長時間経過だけで重複実行を開始しない。
観測の走査費用は文書数に比例するため、毎分全走査は設定しない。定期収集停止を検知する外側の監視も必要。

## 定期回収集約の設計判断

現状の設定は14本、1日1,043起動。うち5分2本/10分3本が1,008起動。これは設定の計算で実DB消費ではない。

| 処理 | 現在の上限/独立性 | 集約前に必要な条件 |
|---|---|---|
| 新規登録照合 | 240秒のHTTP予算、最大5件 | 残時間を外から渡し、巡回位置を保持 |
| シート未配送 | 240秒の時間予算 | 他処理と共有する上限、未処理を次回へ |
| 日報再開 | 永続的な収集/送達状態、start_today=False | 未送信のみ再開、結果不明の送達を再送しない |
| Slack/メール照合 | Slack各処理最大10、メール最大5 | 件数だけでなく全体時間の上限と公平な順番 |
| Gmail遅延 | 遅延180秒＋耐久保留45秒 | 通常Gmail排他・カーソル・二つの独立回収を維持 |

単一HTTPへそのまま直列に入れると300秒を超え、後半の回収を失う。入口だけまとめても個別DB接続は減らない。
推奨設計は、永続的な次回順番＋各処理の残時間引数＋失敗隔離。ロック専用の直接接続を他処理と共有しない。
採用条件は、現行の最大遅延以内、到着量以上の処理量、各処理が定期的に選ばれること、停止/再起動時のカーソル保持。
DB復旧後にキュー別到着件数・滞留・1件/1回の時間・DB接続数を測って予算を決める。測定なしの一律15分化・無料枠内保証は採用しない。
本番スケジュールは変更していない。共有時間予算を全回収へ導入する実装と実負荷検証は未完了。
