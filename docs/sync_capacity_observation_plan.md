## 継続観測の仕様

観測窓は**連続7日間以上、通常営業日と日次outboxを含む期間**を候補とする。
繁忙日の代表性がなければ延長する。今回開始した事実ではなく、次回の収集条件。
開始・終了をUTCで保存しJSTも併記する。途中の配備切替をrevision別に分ける。

```text
送信元の試行 → 配備先の到達 → 新規受理 → worker試行 → 完了
   再送含む      認証失敗含む    重複除外     retry含む
                   ↓                         ↓
             欠測を別記する             時間・接続数を計測
```

| 収集元 | 対象・必要項目 | 集計と不足の扱い |
|---|---|---|
| Vercel / Cloud Run | `/api/webhooks/`のnotion・kintone・zoho・spreadsheet、2種drain。時刻、path、status、配備先、要求ID、HTTP時間 | 日別、経路別、固定UTC1分/5分窓の件数。保持期間・全ページ・標本抽出の有無を確認できない窓は欠測 |
| 送信元の既存配送記録 | 配送ID、試行時刻、結果（本文・認証値不要） | 初回と配送再送を分ける。到達ログだけから再送数を推定しない。未取得の送信元は不明 |
| queue（配備後のみ） | 新規受理、重複、保存失敗、source、job_id、owner、状態、試行数、時刻 | 新規jobとworker再試行を別計数。現時点はDBなしで未計測 |
| worker（隔離試験で先行） | claim開始、取得、初期化終了、業務終了、保存確認。単調増加時計の経過秒 | 初期化・業務・結果保存を分離。正常/失敗別にn・p50・p95・最大。未完了を0秒にしない |
| Neon | 総接続、対象同期、他用途、待機接続、観測時刻 | 通常枠を再照合。既存指標を優先。SQL採取が必要ならread-only・短いtimeout・本文非取得。標本間ピークは未観測 |

固定窓ピークは境界を跨ぐバーストを過小評価しうる。時刻精度が十分なら
移動60秒/300秒窓も併記する。ログのページ上限に到達したら期間分割か全ページ取得。
欠落・時刻不正・取得失敗を0件に置換しない。
同じログの再取得は配備先＋要求ID（Cloud LoggingはinsertId等）で重複を除く。
配送再送は別のHTTP要求として残す。

## 容量を決める計算と未決事項

`S ≤ floor((B − O − R) / C)` を候補枠数の上限とする。
Bは再照合した通常DB枠、Oは他用途（待機接続含む）の予算、Rは管理・変動余裕、
Cは同期1枠が使う最大同時接続。過去値106本と仮定3本だけでSを確定しない。

1call最大1jobなので、起動頻度だけでも処理数は制約される。
`λ × E[T] < S` は必要な目安だが十分条件ではない。
λは新規job＋初期化retry試行の毎秒数、Tは試行ごとの枠保持秒。
配送再送のうち重複排除された要求を新規jobへ二重加算しない。
outbox1job内の行数はjob数と別に記録し、所要時間に反映する。

起動回数ではなく**実際の終端到達数と正常completed数を分けて**比較する。
needs_attentionで待機列が減っただけなら同期成功としない。
持続流入を処理でき、バースト後に最古待機時間が減ることを確認して枠数・頻度を決める。
定期起動の第一候補は共通ルールどおりGAS。認証の保管先、呼出しの重複、失敗通知、
実行時間と必要頻度の適合を隔離試験で確認してから採用する。登録は未実施。
