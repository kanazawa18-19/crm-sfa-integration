## 今回の変更

`scripts/verify_spreadsheet_backfill.py` を修正した。

- 同期キー列はヘッダから読み取るだけ。列が無い・複数ある場合は停止し、列を作らない。
- 同一シート内の行番号衝突と、保存された番号と実際の同期キー位置のずれを検出する。
- 不足、対応表のない行、シートの重複、対応表の重複、行番号衝突・不一致は終了コード1。
- `--skip-id-mapping` で行番号を省略した正常な行は、未記録件数として表示する。
- `--no-mapping` は対応表に接続せず、シートの同期キー重複だけを検査したと明示する。
- `--report-json` は全対象と一意な実位置の修復候補をローカルに保存する。既存ファイルは上書きしない。保存先が既存または親フォルダが無い場合は、認証読込前に終了コード2で停止する。
- 重複行の内容は未比較なので、先頭を残して削除するという旧案内を廃止した。

`scripts/audit_id_mapping_collisions.py` は別DB間の同番号を調べる旧調査用。
別シートの同じ行番号は正常でも発生する。今回の同一シート内衝突には、上記verifyを使う。

## 本番操作の指示後に行うこと

1. 対象シート・対応表の現在値を読み取り、診断を保存する。

   ```sh
   .venv/bin/python scripts/verify_spreadsheet_backfill.py \
     --db-keys client_master \
     --report-json /private/tmp/crm-sheet-integrity-before.json
   ```

2. `missing_keys` は同期キーが見つからない対象。必ずNotionの現物とキー未入力の既存行を確認する。
   空のキーを持つ行が既存レコードなら、新規追記すると重複する可能性がある。
3. `row_collisions` と `row_mismatches` を照合する。`candidate_row` は実位置が一意な時だけ返す。
   これは実行可能な修復計画ではない。対応表のページ重複、kintone/Zoho ID競合、同時更新、
   更新先行番号を別レコードが保持しているケースを確認してから対象を確定する。
4. 本番の書き込み前に、対象一覧、変更前後、バックアップ、同期処理との競合回避を用意する。
   過去の全件バックフィルを、そのまま現在の同期稼働中に実行しない。
   行番号だけを一括消す案、対応表の丸ごとupsert、先頭以外の重複行を一律削除する案は採らない。
5. 指示された対象だけを修復し、別ファイルへ再診断して不足・衝突・不一致の実件数を照合する。
   本番のデータ修復完了は、この到達確認まで済んでから判断する。

## 検査範囲と限界

- A列末尾位置はA列の長さからヘッダを除いた値であり、実データ件数ではない。
- 比較は取得時点の同期キーと対応表だけ。全列の値の一致、Notionページの生存は検査しない。
- 複数APIの読み取りは一括の確定時点を持たない。同時に行を並べ替えると候補も変わる。
- 元の取得処理が漏らしたレコードは判定できない。「不整合0」は取得範囲内の判定である。
- JSONは全レコードIDを含む。Git管理外のローカルへ置き、外部レビュー本文には含めない。
