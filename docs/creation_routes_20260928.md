# 外部登録の9経路と専用入力

Notion・新規登録シートからZoho6種類／kintone3種類への登録計画を作る。
APIの必須項目を再取得し、不足・未対応・重複候補・作成結果不明は既存の登録保留台帳に残す。
不足する業務値を推測で補わない。外部POSTは予約済みの1回だけで、応答不明を自動再送しない。

## 専用欄

| DB | 追加欄 |
|---|---|
| 連絡先 | 姓、名（タイトルのフルネームを自動分割しない） |
| 案件 | 完了予定日、契約予定日、作成日、新規・既存種別、リードソース1 |
| 商品 | 商品カテゴリー、先方担当者（連絡先への関連） |

Zoho完了予定日（Closing_Date）、kintone契約予定日（日付）、既存契約日／予想契約日は別欄として保持する。
過去の既存値を一括修正しない。会社名（母体）は本人回答Q047に従い取引先名と同じ値を作成時に送る。
商品・連絡先・案件・アクションのlookupは関連するNotionページの対応表にあるZoho IDを使い、複数候補を1件へ縮めない。

シートの複数選択・関連・担当者はJSON配列、または1件の値を受け取る。関連・担当者の文字列はNotion UUIDのみで、名前から推測しない。
アクションの担当営業・提案サービスはNotionの完了済みrollupを読み、未完了や非対応型は必須不足として保留する。

## 担当者

`CRM_USER_MAPPING_JSON`に確認済み対応を設定する。形式は下記（架空値）。実IDをGitに保存しない。

```json
{"verified": true, "fallback_notion_id": "確認済み本人のNotion ID", "users": [{"notion_id": "Notion ID", "zoho_id": "Zoho ID", "kintone_code": "kintoneログイン名", "enabled": true}]}
```

設定未確認・無効ユーザー・複数担当を単一Ownerへ縮約する必要がある場合は保留する。
確認済み対応表に個別対応が無い場合、任意欄は空欄、必須欄は設定で確認した本人を代替とする。
担当者の照合は名前の似ている人への推測割当を行わない。現在の実設定は未投入であり、動作確認済みとはしない。

## 反映前の準備

`scripts/prepare_creation_fields.py`は既定で追加予定のschemaを表示するだけ。
`--inspect`で既存Notion型とシート見出しを確認し、`--apply --expected-hash <表示hash>`で不足欄だけを追加する。
既存欄の改名・型変更・値変更をしない。実schemaを追加し、担当者対応を確認してから製品コードを反映する。

## 検証と残り

9経路の登録計画は合成APIデータで検証する。実書込みはQ058の別途承認範囲を超えて実施していない。
重複候補の手動比較・統合・見送り画面は別実装が必要であり、既存の保留は自動解除しない。
本番schema反映、実ユーザー対応の設定、9経路全部の実配送は未検証。

## 2026-09-29の実確認

担当者対応を実設定し、Zoho6種類・kintone3種類で限定実配送・読戻し・再通知同IDを確認した。詳細と検証範囲は [実稼働復旧の証跡](evidence/completion-20260929.md)。上の未投入・未検証は当初時点の記録。

案件はv8のFields/Layout/Pipelineで必須項目を取得し、既定パイプラインが一意で、営業ステータスが所属する場合だけそのPipelineとLayout IDを送る。案件の登録POSTもv8を使用する。既定が複数なら営業上の所属を推測せず保留する。通常更新などの既存API版は維持する。

Zohoのリードソースは表示名と内部値が異なるため、受信対応から逆引して往復変換し、作成時は実設定の表示名・内部値の組も照合する。kintoneの案件・アクションは参照元取引先アプリのトークンを併用する。作成と返信はDB・送り先共通の鍵で排他し、応答不明の予約がある間はそのDB・送り先の新規受信を再試行する。確定済みIDの返信は先に識別し、既存更新は継続する。

大規模な本番COQL照合は本人再認証・権限追加待ち。今回の限定Zoho実試験は、正式Get Records全件照合＋直前差分確認を使った操作であり、COQL経路の確認済みとはしない。
