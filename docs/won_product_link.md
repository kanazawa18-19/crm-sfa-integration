# 受注案件の商品・取引先関連

2026-09-28 本人指定。既存の確定7ステータス＋口頭受注で、案件「サービス・商品」の各商品に案件「取引先マスター」の全IDを追記する。分析のステータス分類は変えない。名前から推測せず、既存関連を保持し、失注・解約・空欄から削除しない。

## 通常同期と関連の読取

Notion発は他ツールへの読取・書込より先に起票する。外部発はNotion書込成功直後に起票し、後続の案件シート配送・メモ・通知が失敗してもキューを保持する。Notion書込が失敗した場合は起票しない。外部発の新規作成は対応表の完了時刻を先に確定しない。新規作成はNotionと対応表が成立した直後、後続の通知・シート配送・メモより先に起票する。新規シート登録も登録履歴のNotion IDから同じ処理へ渡す。対象外ステータスは案件の関連を全件取得せず、新たな関連追加は行わない。商品・取引先が後付けされたときも最新案件から再評価する。

`get_raw_page_with_relations` で必要な関連だけプロパティ取得APIのページ分割を最後まで読む。更新する関連について、プロパティの存在・型・relation配列・非空の文字列ID・boolのhas_moreを検証する。ページ分割応答のresults・要素型・カーソルも検証し、不正な応答を空欄として上書きしない。通常のページ取得の通信量は変えない。

商品と各取引先は通常同期と共通のレコードロックを取得する。Notionの双方向関連を利用し、取引先の「サービス・商品」へ商品IDを追加する。商品の取引先が100件を超えても商品側への配列置換を避けられる。取引先側の商品数が100件に達していて新しい商品を追加する必要がある場合は変更せず保留する。[Notion公式の配列上限](https://developers.notion.com/reference/request-limits)。

## 案件の状態が変わっても配送を失わない

保存するのはID（配送で含まれるべき相手IDを含む）と処理状態で、その他の業務値は都度読み直す。

1. `ProjectProductLinkTask`：案件評価の起票、再試行日時、原因と対象ID。
2. `ProjectProductLinkPair`：案件の商品ID×取引先ID。未処理・処理済み・保留を保持する。未処理分は実行時の最新案件から再評価し、失注・空欄・差替えで不要になったペアは実行しない。
3. `ProjectProductLinkDelivery`：商品・取引先それぞれの配送義務。NotionのPATCHより**前**に両側を同じトランザクションで確定する。案件が後に失注・空欄・商品差替え・削除されても消さない。配送義務には期待する相手IDを保持し、Notionの最新関連に存在することを確認するまで配送完了にしない。

追加ペアの処理と配送消化は別段階。追加評価や一部対象が失敗・保留でも、発生済みの他の配送を続ける。配送は対象の最新Notion値を読み、商品・取引先のシートへ直接反映して成功した対象だけ消化する。Notionの逆参照反映が遅れている場合、追加前の旧値を配送して義務を消すことはない。期待IDを8回確認できなければ `DELIVERY_NOT_VISIBLE` で対象保留とし、同じ対象に関わる未完了の追加ペアも同一トランザクションで保留する。保留中対象への新規ペアも自動実行せず、resumeでペア・配送の両方を再開する。無関係な対象の配送は継続する。確認回数はcronだけでなく案件編集からの呼出も含むため、短時間の連続編集でも8回未確認となり保留する場合がある。安全側に配送義務を保持する制約として受容し、原因確認後に運用担当がresumeする（管理画面からの再開操作は別の残件）。PATCHの結果が不明・失敗のまま案件が失注した場合も、未成立の期待IDを推測して削除せず保留する。原因確認後の明示的なresumeで再確認する。botのWebhookには依存しない。Zoho/kintoneにはこれら関連の対応項目がないため版取得・書込をせず、結果の `skipped_tools` に残す。

1回につき追加は最大5ペア、配送は最大10対象、時間は20秒を目安に次の処理への着手を止める。実行中の外部API呼出は中断できないので厳密な20秒以内の終了保証ではない。済ペアと配送済み対象を保存し、再試行で毎回先頭からやり直さない。時間・件数上限で残った分はキューに保持し、次回候補日時を1分後に進めて他案件にも順番を回す。未処理・配送義務・恒久保留がなくなったときだけ親タスクを消す。

## 再試行・保留・再開

専用cron `/api/cron/project-product-links` は毎時30分、最大3案件を処理する。案件ロック内で再確認・計画更新・処理・消化を行い、Webhookと競合させない。日報とは独立。失敗があればHTTP500と件数、残作業は `deferred`、外部未対応は `unsupported_relations` に計上する。`no_delivery_this_run` はその回に配送結果がない件数で、業務上の対象外件数ではない。キュー保存・読取失敗は専用例外で通常同期にも伝播させ、正常完了にしない。一方、原因と再処理義務が永続化された関連エラー・ロック競合は案件本体の成功を取り消さず、完了時刻を進めて関連キューに任せる。Notion本体へ届かなかった外部変更の復旧はこのキューの対象外。

- 一時失敗：`NOTION_READ_FAILED`（通信/5xx等）、`NOTION_WRITE_FAILED`、`INVERSE_NOT_VISIBLE`、`DELIVERY_NOT_VISIBLE`（8回未満）、`DELIVERY_FAILED`、`RECORD_BUSY`。15分から倍増、最大24時間の間隔で再試行する。キューは消さない。
- 恒久保留：`RELATION_LIMIT_100`、`PAGE_ARCHIVED`、`PAGE_NOT_FOUND`、`MAPPING_MISSING`、`DATABASE_MISMATCH`、`INVALID_RELATION`、`INVALID_PAGE`、`INVALID_STATUS`、`NOTION_CLIENT_MISSING`、`DELIVERY_NOT_VISIBLE`（8回未確認）。認証/権限等のHTTP400/401/403も読取失敗として保留する。対象DB・Notion IDと固定原因コードを保存し、当該作業の自動再試行を止める。他の配送義務は引き続き消化する。
- 状態確認：Taskの `lastError/errorDbKey/errorNotionId/evaluationHeld`、Pair/Deliveryの `state='held'` と `lastError` を確認する。例外本文・認証情報は保存しない。
- 再開：原因を修正した運用担当が対象案件IDを特定し、`acquire_record_sync_lock(store, 'project', project_id)` 内で `ProjectProductLinkQueue().resume(project_id)` を呼ぶ。保留だけを再開し、済ペア・未配送の義務を捨てない。再開後も最新案件の状態から再評価する。保留を消すためにキューを直接DELETEしない。

恒久保留を管理画面に通知して処理する機能は別の残件であり、本変更では未実装。現状の運用確認は上記テーブル・固定原因ログで行う。大量ペアは1案件でも複数回のcronを必要とし、即時完了は保証しない。

通常同期と同じく、人がNotion画面で同時編集する場合のAPI側の条件付き書込は利用できない。システム内部の同時更新は共通ロックで防ぐ。
