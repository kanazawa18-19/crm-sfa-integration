## 送信根拠（オプトイン）— 2026-09-03 実装

### なぜ足したか

```
   足す前                              足した後
   ─────────────────────────────      ─────────────────────────────
   配信停止の名簿に載っていない        根拠がある   ──▶ 送る
   ＝ 送ってよい                       根拠が無い   ──▶ 送らない（既定）
   ＝ 名刺交換もしていない相手にも
     送れてしまう
```

特定電子メール法は、広告・宣伝のメールを**あらかじめ同意を得た相手**に送ることを
原則にしている。名刺交換などでアドレスを通知された相手・取引関係にある相手・
公表されている事業用アドレスは例外として認められているが、いずれにしても
**「停止の申し出が無いこと」は送ってよい理由にならない。**

Notionに連絡先が3,782件あることも「送ってよい」の証明にはならない。

### 根拠の4種類

| コード | 画面での表示 | 何を指すか |
|---|---|---|
| `opt_in` | 本人が同意した | 資料請求・セミナー申込・メルマガ登録 |
| `notified` | 本人からアドレスを受け取った | 名刺交換・問い合わせ・メールのやり取り |
| `transaction` | 取引関係にある | 契約・受注・導入支援の実績がある |
| `published` | 公表されているアドレス | 会社サイトに事業用として公開されている |

★ **条文の当てはめは法務の確認が要る。** ここでの分類は運用の目安であって、
法的な判断そのものではない。特に `published` は「営業を営む個人・団体」に
限られ、個人のアドレスは対象外になる点が実務で間違えやすい。

定義の**正本は `src/bulk_email/consent.py` の `BASIS_LABELS`**。
`dashboard/lib/bulkEmailConsent.ts` が同じ4つを持っている（ブラウザから来た値の
検証用）。**片方だけ足すと、画面から登録できるのにバックエンドが
「種類が不明」として送信不可にする**という気づきにくい壊れ方をする。

### 判定

```
   記録が無い        ──▶ 送らない   consent_missing
   取り消されている   ──▶ 送らない   consent_revoked
   種類が不明        ──▶ 送らない   consent_unknown_basis
   証跡が空          ──▶ 送らない   consent_no_evidence
   取得日が無い      ──▶ 送らない   consent_no_date
   取得日が未来      ──▶ 送らない   consent_future_date
   アドレスが違う     ──▶ 送らない   consent_email_mismatch
   取得から3年超     ──▶ 送るが警告  （★止めるかは業務判断。今は止めていない）
```

「3年」は `consent.py` の `STALE_AFTER_YEARS` が唯一の持ち主で、画面の文言
（「3年以上前」）もAPI経由でそこから作る。**ダッシュボード側に年数を書かない。**

**取得日は「暦の日」。** UTCの`datetime`同士で引き算すると、日本時間の午前中に
「今日」を登録した瞬間に「1時間未来の日付」として送信不可になる。判定はJSTの暦日
（`BUSINESS_TIMEZONE`）で行い、DBの列も `DATE` にしてある。

古さで送信を止めていないのは、名刺交換から3年経ったことと、取引関係が切れたことが
別の話だから。**機械が判断できるのは日付だけ**なので、日付だけで止めない。

判定の順番は「配信停止 → アドレス無し／不正 → 重複 → 根拠」。
**配信停止が最優先**で、根拠を登録しても停止の申し出があれば送らない。

### 記録の形

```
   ContactMailConsent（連絡先1件につき1行・Prisma）
     contactPageId   正規化済み32桁hex（DBのCHECK制約つき）
     contactEmail    Notionから取り直した値。★画面から来た値は使わない
     basis           4種類のいずれか
     obtainedAt      取得日（必須。未来日は登録不可）
     evidence        取得元・証跡の自由記述（空は不可。DBのCHECK制約つき）
     recordedBy      登録した社内ユーザーのメールアドレス
     revokedAt/By    取り消し（★行は消さない。取り消したことも記録）
```

書き込みは社内の管理画面だけ。バックエンド（`src/bulk_email/db.py`）は読むだけ。
配信停止と同じで、**書き手を1つに絞る**ための構成。

**登録は必ず `AuditLog` に残る**（`actorSource="dashboard_bulk_email_consent"`）。
送ってよいと誰がいつ判断したかを追えないと、根拠を持つ意味が半分無くなるため。

### 使い方（運用）

```
   ダッシュボード ─▶ 一斉配信 ─▶ 「送信根拠の管理へ」
        │
        ├─ 取引先を選ぶ ──▶ 連絡先が今どの状態かが並ぶ
        └─ 1件ずつ「根拠を登録」（種類・取得日・証跡）
```

**登録を始めるまで、一斉配信の宛先は0件のまま**（それが正しい状態）。
プレビューのブロッカーに「うちN件は根拠が未登録」と件数と行き先が出る。

### 根拠は「その連絡先の、そのアドレス」にだけ効く

```
   送ってはいけない（配信停止）  ──▶ 広く効かせる  ページIDでもアドレスでも止める
   送ってよい（送信根拠）        ──▶ 狭く効かせる  ページIDとアドレスの両方が一致した時だけ
```

**アドレス経由で他の連絡先の根拠を借りることはしない。** 一度は「同じ人が複数の
連絡先レコードに登録されている」救済として入れたが、2026-09-03 の他モデルレビューで
2つの穴が出たため撤去した。

```
   ① 代表アドレスは会社をまたいで使い回される
      取引先Aの sales@agency.jp と 取引先Bの sales@agency.jp は別人。
      Bにだけ根拠があると、Aにも送れてしまう

   ② 元の連絡先がNotionから消えても、根拠の行はPostgresに残る
      同じアドレスの連絡先が後から作られると、消えた人の根拠で送れてしまう
```

**連絡先のアドレスが書き換わったら、根拠は付いてこない**（`consent_email_mismatch`）。
名刺交換で得たのは「そのとき教えてもらったアドレス」であって、その人が将来使う
どのアドレスでもないため。画面には「登録時のアドレス: ○○」と出るので、登録し直す。

同じ人が2レコードに登録されているなら、**2件とも登録する**（1件ずつ人が判断する、
という原則とも合う。宛先の重複排除があるので、送られるのは1通）。

## 現状：このシステムには「営業メールを送る手段」が無い

```
   今あるもの                        用途                     使えるか
   ────────────────────────────      ──────────────────────   ────────
   lib/email.ts（SMTP・nodemailer）  招待・パスワード再設定・2FA   ✗ 差出人が
                                     ＝社内向けの低頻度な通知      システム用アドレス
   Gmail OAuth（gmail.readonly）     受信箱を読んで EmailLog に   ✗ 読むだけ。
                                     貯める                      送信権限が無い
```

**`gmail.readonly` は読み取り専用のスコープ。** 送るには `gmail.send` を足して、
担当者全員に**もう一度Googleの同意画面を通ってもらう**必要がある。

## 送信経路の選択肢

| | 差出人 | 返信の行き先 | 到達率 | 必要な作業 |
|---|---|---|---|---|
| **A. Gmail API** | 営業担当**本人** | 本人の受信箱 | 高（普段と同じ経路） | OAuth同意画面に `gmail.send` 追加＋全員の再同意 |
| B. SMTP（既存） | システム用アドレス | 誰も見ない箱 | 中 | ほぼ不要 |
| C. 配配メール | 配配の契約アドレス | 配配の管理画面 | 高 | 連携の新規実装。CSVエクスポート要 |
| D. SendGrid等 | 独自ドメイン | 設定次第 | 高 | 新規契約・SPF/DKIM設定 |

**推奨はA。** 理由は返信が本人の受信箱に返ること。返信が`EmailLog`に入るので、
そのまま②③（返信ラグ・返ってきやすい時間帯）の材料にもなり、**送る→返る→測るが
1つの輪になる**。B・C・Dはこの輪が切れる。

★ **Aを選ぶかどうかは業務判断。** Google Cloud Console の同意画面設定と、担当者への
再同意の依頼は本人にしか出せない。ここが決まるまで実装は始めない。

## 法令上、外せない要件（特定電子メール法）

営業目的のメールを一斉に送る以上、以下は機能として必須。「あとで足す」にしない。

```
   ① 配信停止の方法を本文に明示し、実際に停止できること
   ② 送信者（会社名・住所・連絡先）を本文に表示すること
   ③ 停止の申し出を受けたら以後送らないこと（記録が要る）
```

→ 連絡先ごとに**配信停止フラグ**を持ち、宛先の抽出時に必ず除外する。
フラグはNotion連絡先DBではなくPostgres側に置く（Notionは書き込みが重く、
除外漏れが起きたときの被害が大きいため、取得の速さと確実さを優先する）。

## 想定するデータモデル

```
   BulkCampaign          配信1回ぶん（件名・本文テンプレート・差出人・状態）
        │
        └── BulkCampaignRecipient   宛先1件ぶん（連絡先ページID・アドレス・
                                     送信予定時刻・送信済み時刻・結果）

   ContactMailPreference  連絡先ごとの配信停止フラグ（②の解除記録も持つ）
```

- 宛先は**BCC一括ではなく1通ずつ個別送信**。差し込み（会社名・氏名）ができ、
  返信も個別に返り、`EmailLog`にも1件ずつ載る
- 送信は状態機械（`draft → scheduled → sending → done`）にして、
  **途中で落ちても続きから再開できる**ようにする。Vercelの300秒制限があるため
  1回の実行で全部を送り切る作りにはしない（`feedback_vercel_maxduration_300s_batch_pattern`）

## ②③との接続（この機能の肝）

連絡先ごとの「返ってきやすい時間帯」が分かっているので、
**宛先ごとに送信時刻をずらす**ことができる。

```
   全員に 10:00 一斉送信          →  相手の都合は無視。埋もれる
   連絡先ごとの山の時間に送る      →  開封・返信の確率が上がる
```

ただし現状はサンプル数が足りず、ほぼ全員が「参考値」。
**過去分の取り込み（`docs/reply_timing_note.md`）が先。**
それまでは「全員同じ時刻」を既定にして、時間帯最適化は任意のオプションにする。

## 出す順番（段階リリース）

```
   ① プレビューのみ    宛先一覧と差し込み後の本文を画面に出す。1通も送らない
   ② 自分宛だけ        金沢さんのアドレスにだけ実送信
   ③ 少数（5件以内）   実際の顧客へ。結果を見る
   ④ 本番             件数制限を外す
```

**②③④は明示的な指示があるときだけ進める。** 本番でいきなり試さない。
