# 連絡先ごとの返信傾向（返信ラグ・返ってきやすい時間帯）

作成: 2026-09-03（主機CC）

## これは何か

顧客360度ビューの連絡先一覧に、次の2列を足した。

```
   返信の速さ            こちらが送ってから相手が返してくるまでの時間（中央値）
   返ってきやすい時間帯   相手からのメールが実際に届いている時間帯（日本時間）
```

どちらも新しくデータを集めているのではなく、**Gmail連携が既に貯めている
`EmailLog`（送受信ログ）を数え直しているだけ**。

## 着手時点のデータ量（2026-09-03 実測）

```
   EmailLog の中身          309件（2026-08-25〜09-02 の9日分・担当者1名）
     受信                    31件
     送信                   278件
   ログのある連絡先           44件
   返信ペアが作れた連絡先     13件（合計19ペア）
   信頼度                    13件すべて「参考値」（＝4件以下）
```

**この件数では、連絡先ごとの傾向を断定的に出せない。**
日次同期は直近2日・最大100件しか見ないため、連携開始日より前のメールが1通も無い。
そのため過去分の取り込み（後述）とセットで初めて意味を持つ機能になる。

## 数え方（仕様書に定義が無いのでここで決めた）

### 返信ラグ

```
   送信 ──▶ 送信 ──▶ 送信 ──▶ 受信          起点は「直前の送信」
                     └───ラグ───┘            （連続送信は追撃。返信を引き出したのは最後の1通）
```

| 決めごと | 内容 | 理由 |
|---|---|---|
| 範囲 | **同じスレッドの中だけ** | 別件で届いたメールを返信として数えない（下記） |
| 起点 | 直前の outbound | 最初の1通から数えると、追撃するほどラグが長く出る |
| 上限 | 14日 | それを超えた受信は「返信」ではなく別件の新規メールの可能性が高い |
| 二重計上 | しない | 1通の送信に返信が2通来ても1ペア |
| 主指標 | **中央値** | 分布が右に長く裾を引く。平均は数件の長期放置に引っ張られる |

**スレッドを見ないと数字が系統的に短く出る。**

```
   月曜  こちら → 見積書                    スレッドを見ない場合
   火曜  相手  → 別件（請求書について）      月曜→火曜 ＝ 1日 と記録される
   金曜  相手  → 月曜の見積書への返信        本当の4日は消える
```

複数の案件を並行している相手ほどこれが起きる。GmailのスレッドID
（`EmailLog.gmailThreadId`）を保存して、同じスレッド内でだけペアを作る。
2026-09-03より前に記録した行はスレッドIDを持たないので、従来どおり時系列だけで判定する。

平均も返しているが、画面で主に見せるのは中央値。平均・最速・最遅はホバーで見せる。

### 返ってきやすい時間帯

- **inbound 全件**を数える（返信ペアに絞らない）。知りたいのは「相手がメールを触っている
  時間帯」で、返信かどうかは問わないため。絞るとサンプルが一段減る
- 3時間刻み・日本時間（JST）。1時間刻みだと現在の件数ではほぼ全部が0か1になり山が見えない
- 曜日も同時に数える
- **時刻はGmailの`internalDate`を使う。** `Date:`ヘッダーは送信側が作る値で、
  PCの時計ずれ・遅延配送・壊れた書式でズレる。「実際に届いた時間」を数えたいので
  Gmailの記録の方が意味に合う（ChatGPTレビュー指摘）
- **件数が多くても「傾向なし」はある。** 24件が8つの時間帯に3件ずつ散っていたら、
  それは「00-03時によく返ってくる」のではなく偏りが無い。1位と2位が同数のときは
  順位に意味が無いので、画面には**「傾向なし」**と出す

### 信頼度

| 件数 | 表示 |
|---|---|
| 0 | データなし |
| 1〜4 | 参考値 |
| 5〜9 | やや不足 |
| 10以上 | 十分 |

**数字の横に必ず件数を出す。** 1〜2件の偶然を断定として読ませないため。

## どこに何を置いたか

```
   src/analytics/reply_timing.py      数え方そのもの（純粋関数・DBもAPIも触らない）
        ▲
        │
   src/api/reply_timing_service.py    EmailLogを読んで画面向けdictにする
        ▲
        │
   src/api/client_360_service.py      360ペイロードに reply_timing を足す
        ▲
        │
   dashboard/app/(dashboard)/clients/[id]/page.tsx   連絡先テーブルに2列
```

- 集計の単位は**連絡先ページID**（同じ人が2つのアドレスを使っていても1人として数える）
- `contacts` にはこの算出値を混ぜない。`contacts` はNotionの写しのままにして、
  どれがNotionの値でどれが計算結果かを見分けられるようにする
- EmailLog が読めなくても360ビュー全体は落とさない（他セクションは表示できる）

## 過去分の取り込み

### 手順

```bash
cd ~/crm-sfa-integration
set -a; . dashboard/.env.local; set +a
# NOTION_API_KEY / GOOGLE_OAUTH_CLIENT_ID / GOOGLE_OAUTH_CLIENT_SECRET /
# INTERNAL_EMAIL_DOMAINS も環境変数に入れる（Vercelのsensitive変数は読み戻せないため手で）

# ① まず小さく試す（アドレス30件だけ・1通も書き込まない）
#    Gmailの検索構文が想定通り通るかを、3万件を投げる前にここで確かめる
#    打ち切り日（--before）は省略するとEmailLogの最も古い日付が自動で入る
.venv/bin/python scripts/backfill_gmail_history.py --days 365 \
    --limit-addresses 30 --index-cache /tmp/contact_index.json

# ② 全件の試算（まだ書き込まない）
.venv/bin/python scripts/backfill_gmail_history.py --days 365 \
    --index-cache /tmp/contact_index.json

# ③ 実行
.venv/bin/python scripts/backfill_gmail_history.py --days 365 --apply \
    --index-cache /tmp/contact_index.json

# ④ 実件数を数える（「完了」表示を信用しない）
.venv/bin/python scripts/verify_gmail_backfill.py
```

`--limit-addresses` を付けた1回目を飛ばさないこと。`{from:a to:a cc:a …}` の
OR検索が15件ぶんの長さで通るかは**まだ実機で確かめていない**（下の「未検証のこと」参照）。

### ★ 通常同期と同じ期間を取りに行かない

**これを外すと、本番の通知が黙って止まる。**

```
   10:00     顧客から重大なクレームが届く
   10:00:10  取り込みが先に見つけて EmailLog へ（インシデント判定はしない）
   10:01     通常同期が同じメールを処理 → 既に在るので即 return
             → インシデント検知されない
             → Notionの「最終メール日時」も更新されない
             → web-engagement-tool へも通知されない
```

通常同期（`_process_message_ref()`）は冒頭で `email_log_exists()` を見て、
既にあれば何もせず抜ける。取り込みが先回りすると「副作用を起こさない」つもりが
**正常な副作用を打ち消す**（ChatGPTレビューのBLOCKER指摘、2026-09-03）。

対策は `before:` での打ち切り。既定値は `EmailLog` の最も古い日付（＝通常同期が
面倒を見ている期間の始まり）で、そこより前だけを取り込む。`--before` で上書きできるが、
**通常同期と重なる期間を指定しない。**

### 総当たりにしない

```
   ① Notion連絡先DB ──▶ メールアドレス→ページID の索引を1回だけ作る
                        30,824件（2026-09-03実測）・作成に約6分
   ② アドレスを15件ずつまとめてGmail検索（並列8）
        {from:a to:a from:b to:b …} newer_than:365d before:YYYY/M/D -in:spam -in:trash
        ※ cc: は入れない。突合側がFrom/Toしか見ないので、当たっても必ず落ちる
   ③ 当たったメッセージIDだけ messages.get（並列8）
   ④ 突合・direction判定は日次同期と同じ classify_message() を通す
   ⑤ EmailLog へまとめて追記（ON CONFLICT DO NOTHING）
```

メールボックス全体を舐めると対象外のメール（メルマガ・社内・通知）まで1通ずつ
取得することになる。連絡先のアドレスは分かっているので、当たった分だけ取りに行く。

**Notion連絡先DBは30,824件。** スプレッドシートの「連絡先」タブは3,782行だが、
Notion側の実体はこの件数（`query_all_pages`の1万件の壁を越えて数えた値）。

**★ 拾えないもの:** 索引はNotionの「今の」メールアドレスで作るので、
**この1年の間にアドレスが変わった相手の、変更前のやり取りは入らない**
（Geminiレビュー指摘、2026-09-03）。bccだけで送ったメールも同様に拾えない
（Gmailはbccを検索できない）。どちらも1:1の営業メールでは稀なので割り切っている。

### 過去のメールで「今」を騒がせない

取り込みは`EmailLog`への追記だけを行う。以下は**一切行わない**。

| 行わないもの | 行うと何が起きるか |
|---|---|
| インシデント判定・スコア付与 | 数か月前のクレームで管理者にSlack DMが飛ぶ。`incidentPriority='medium'` かつ `digestedAt IS NULL` の日次ダイジェストには日付の絞り込みが無いため、過去分が一斉に載る |
| Notionの「最終メール日時」更新 | 古い日時で上書きされうる。書き込み件数分のAuditLogも積み上がる |
| web-engagement-toolへの通知 | 過去のメールでスコアリングが動く |

併せて**未返信リマインドに14日の上限**を入れた
（`src/email_reminders/reminder_check.py` の `_MAX_REMINDER_AGE_HOURS`）。
これが無いと、それまで`EmailLog`に1行も無かった連絡先の「最新行」が一気に古い受信メールに
なり、取り込み直後に「未返信です」のDMが大量に飛ぶ。
なお管理画面の閾値を336時間より大きく設定した場合、その閾値は事実上効かなくなる
（上限で先に切られる）。現在の選択肢は3〜72時間なので実害は無い。

### 取り込む前にインデックスを張っておく

未返信リマインドは毎時
`SELECT DISTINCT ON ("contactPageId") … ORDER BY "contactPageId", "sentAt" DESC`
を流している。`EmailLog`が大きくなってから張ると重いので、**行が少ないうち**に
`("contactPageId", "sentAt")` の複合インデックスを追加した
（`dashboard/prisma/migrations/20260903000000_add_email_log_contact_sent_index/`）。
本番へは次回のデプロイ時に `prisma migrate deploy` が適用する。

## レビュー（2026-09-03）

動物チーム3体＋他社モデル2つに通し、指摘を反映済み。

| | 結果 | 主な指摘と対応 |
|---|---|---|
| shirokuma-sec | BLOCKER 0 | 実Gmailで未検証 → `--limit-addresses` を新設。リマインドクエリの負荷 → 複合インデックスを追加。エラー件数のスレッド間競合 → 加算をメインスレッドに寄せた |
| obasan-quality | BLOCKER 0 | 「返信の速さ」は大きい数字＝遅いで直感と逆 → 「返信までの時間」に変更。`medium`（やや不足）が`high`と同じ見た目 → 件数の注記に反映。2列の「N件」が別物である説明がホバー頼み → 本文に明記 |
| kuma-qa | **BLOCKER 2** | 取り込み本体（`backfill_rep`/`main`）が未テスト → 23件追加（`--apply`が無ければ1通も書かない、を含む）。`list_messages_page`のページングが未テスト → 5件追加 |
| Gemini Pro | BLOCKER 1 | 大文字小文字の突合漏れ（実際は`_extract_addresses()`が小文字化済みで空振りだったが、依存させないよう`.lower()`を明示）。数万件を1回のINSERTで投げるな → 500件ずつに分割 |
| ChatGPT（推論:高） | **BLOCKER 2** | **取り込みが通常同期と同じ期間のメールを先に入れると、通常同期の副作用（インシデント検知・Notion更新・外部通知）が黙って止まる** → `before:`で打ち切り。1件でも失敗したのに`rc=0`で終わるな → 終了コード2。他に、返信判定にスレッドIDを使う／時刻は`internalDate`／`cc:`検索と突合の食い違い／平らな分布を「傾向」と呼ばない／トークンの期限切れ／古い索引キャッシュが別人の履歴を作る、を反映 |

**ChatGPTのBLOCKER 1件目は、動物チーム3体もGeminiも見つけられなかった。**
「副作用を起こさない」という設計意図の裏返しで、**正常な副作用を打ち消す**という
形になっていた。他社モデルに通す価値がここに出た。

## 未検証のこと

- **返信判定は「同じスレッド」までしか見ていない。** `In-Reply-To` / `References`は
  使っていない。スレッドをまたぐ返信（相手が新規メールで返してきた場合）は拾えない
- **取り込みスクリプトはGmail APIに対して一度も実行していない**（2026-09-03時点）。
  `GOOGLE_OAUTH_CLIENT_ID` / `GOOGLE_OAUTH_CLIENT_SECRET` がローカルに無いため。
  外部I/Oをフェイクに差し替えた単体テストは通っているが、**実機での試算はまだ**
- 360ビューの新しい2列は、実ブラウザでの表示を確認していない
- 複合インデックス・`gmailThreadId`列は本番未適用（次回デプロイの
  `prisma migrate deploy` で入る）
- Gmail APIのクォータがこのプロジェクトで新体系か旧体系かを確認していない
  （`_FETCH_WORKERS = 8` の妥当性がそれで変わる）
