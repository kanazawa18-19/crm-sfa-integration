# データ移行スクリプトに関する申し送り（Phase 4 実装ノート）

`src/migration/migration_pipeline.py`（計画: `plan_migration()` / 実行: `materialize()`）と
`scripts/migrate_data.py`（CLIエントリポイント）は、kintone CSVエクスポートを入力に
Notion 6DBへ一括インポートするスクリプトである（09_開発ロードマップ T-11、04_項目マッピング
末尾の移行手順①〜⑤に対応）。

実際の営業本部の既存データを移行する重大な操作を担うため、04_項目マッピングに明記が無く
実装者判断で補った点・既知の制約をここにまとめる。

## 1. 取引先マスターDBの「営業ステータス」導出ロジック

`src/db_schema/client_master.py` の「営業ステータス」は必須項目（STATUS型）だが、kintone
取引先マスタ側に対応する「契約進捗状況」等の列が存在せず、04_項目マッピングにも導出方法の
明記が無い。

**採用したロジック**（`src/migration/kintone_client_master.py` の
`derive_client_sales_status()`）: 紐づく④案件管理DB側の営業ステータスから導出する。

- 紐づく案件が1件も無ければ「未アプローチ」
- 1件以上あれば、以下の優先順位で最も商談が進んでいるステータスを代表値として採用する
  （1社に複数案件がある場合、営業サマリーとしては「一番良い状態」を見せるのが実用上
  妥当なため）。
  1. 契約済（いずれかの案件が契約済） → 「契約」
  2. 商談中(B) / 商談中(C) → 「商談中」
  3. 初回接触 / 提案中 / 見積提出 → 「アプローチ中」
  4. 失注 / 解約（他のいずれにも該当しない） → 「失注」

`migration_pipeline.plan_migration()` は④案件管理の処理が完了した後、取引先名をキーに
この関数を呼び出して取引先マスターDB側の営業ステータスを補完する（`transform_client_master()`
の時点では案件データを参照できないため）。

**既知の制約**: 取引先名の完全一致でしか案件と紐付けられない（同名だが実際は別法人、
表記ゆれで一致しない等のケースは考慮していない）。案件が1件も無い取引先は一律
「未アプローチ」になるため、実際には失注済み・休眠中の取引先も「未アプローチ」表示に
なりうる。実データ精査後、必要なら手動修正すること。

## 2. リレーションキー列名の推測（案件管理・アクション管理）

kintoneアクション管理が取引先・案件とどのカラムで紐づくかは仕様書に明記が無いため、
案件管理アプリと同じ命名規則（取引先名＝「施設名（会社名）」、案件の一意キー＝「案件番号」
列に案件管理側のレコード番号が入る想定）を前提としている。実データのCSV列名が異なる場合は
要調整。

実データでこの推測が外れていた場合、全件が未解決になっても気づけないリスクがあったため、
`plan_migration()` はリレーションの解決試行回数（`relation_attempts`）と未解決件数を
`(db_key, relation_name)` 単位で集計し、未解決率が30%を超えるものがあれば
`print_summary()` の先頭に目立つ警告を表示する。全件の詳細は
`--report-path` を基準にしたCSV（例: `migration_report_unresolved.csv`）へ出力される。

## 3. USER型プロパティ（担当営業／担当メンバー）は解決しない

「担当営業」（⑥アクション管理DB）「担当メンバー」（④案件管理DB）はいずれもUSER型・必須
プロパティだが、氏名→NotionユーザーIDの対応表がまだ無いため、本移行スクリプトでは
一切解決しない（Notion側でキー自体が欠落した状態でページが作成され、手動割当が必要）。

- アクション管理は kintone「対応者」の氏名を `_担当営業氏名`（`action_mapping.
  transform_kintone_action()`）として抽出済みなので、未設定レコードのCSVレポート
  （`migration_report_unresolved_users.csv`）に手掛かりとして残している。
- 案件管理は「担当メンバー」に相当するkintone側の列が確認できていないため、raw_valueは
  常に空（`None`）で記録される。

対応表が整備でき次第、`materialize()` 呼び出し前に氏名→NotionユーザーIDのマッピングを
適用する処理を追加する必要がある（現状は本スクリプトのスコープ外）。

## 4. 先方担当者の会社またぎフォールバック解決

アクション管理の「先方担当者」は `(氏名, 取引先名)` の組で連絡先を検索し、見つからない
場合は氏名のみでフォールバック検索する。このフォールバックは同姓同名の別会社担当者を
誤って結合するリスクがあるため、発生時は警告ログ（`フォールバック解決しました`）を残す。
名寄せ自体（Q-08）はスコープ外のままだが、実データ移行時はこの警告ログを必ず確認すること。

## 5. サービス・商品DBの「課金形態」代用値

「課金形態」（必須セレクト）はkintone側にソースが無いため、案件管理「サービス（ショット）」・
アクション管理「提案サービス」がいずれもショット（単発）起点であることから、初期値
「イニシャルスポット」で作成する（実データ精査後に手動調整する前提）。

## 6. PIIの取り扱い

IDマッピングDB（SQLite）・各種レポートCSV（名寄せ・未解決リレーション・USER型未設定）には
氏名・部署・役職・携帯番号・メールアドレス等のPIIが含まれる。デフォルト出力先は
リポジトリ直下の `migration_output/`（`.gitignore` 登録済み）とし、誤ってコミットされない
ようにしている。`--id-mapping-db` / `--report-path` でリポジトリ外・共有ドライブ等へ出力先を
変更する場合は、アクセス権限・保存期間に注意すること。

## 7. materialize() が例外で中断した場合の挙動

Notion API呼び出し中に例外が発生した場合でも、`scripts/migrate_data.py` はそこまでの進捗
（`record.notion_key` が設定済みかどうか）からベストエフォートのサマリーを組み立てて表示し、
名寄せ・未解決系レポートCSVを出力してから例外を再送出する。中断後の再実行時は、IDマッピング
ストアに登録済みのレコードは自動的にスキップされる（`materialize()` の冪等性）ため、
そのまま再実行してよい。
