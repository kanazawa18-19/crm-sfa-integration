# SlackからCRM-SFAを更新するモバイル中心の設計案（2026-10-02）

## 結論と現状

Slack公式のSalesforce連携に近い体験を、このCRM-SFAの取引先・案件・アクションで作る。最初の利用者は金沢さん本人。携帯で「今日やることを見る」「案件を直す」「アクションを記録する」をSlack内で完結させる。既存の `/crm 取引先名` は取引先名と画面リンクを返す読み取り専用コードで、Slackアプリへの登録は自動審査で止まり未実施。このコードを完成形や本設計の入口とは扱わない。

確認した現行資産：案件・アクションの正本はNotion、`ProjectMirror` は読み取り専用。案件・アクションのスキーマは `src/db_schema/project.py` / `action.py`。Slack署名検証と本人ボタンでのアクション新規作成は稼働コードにある。案件/アクションを汎用に編集するSlack APIはまだ無い。Zoho/kintone等への反映には既存同期経路を通す。

## 携帯での使い方

```
Slackの「CRM-SFA」ホーム
  ├─ 今日の予定案件 3件   ──▶ 1件を開く ──▶ 次回アクション日等を更新
  ├─ 最近見た案件         ──▶ 1件を開く ──▶ ステータス等を更新
  ├─ 案件を探す           ──▶ 候補を選ぶ ──▶ 更新／アクション追加
  └─ アクションを記録     ──▶ 案件を選ぶ ──▶ 種別・日付・メモを入力
```

### ホーム画面

1画面の先頭に「案件を探す」「アクションを記録」の2ボタン。その下に、担当者対応が確認できた案件の「次回アクション日」が近いものと最近開いた案件を3件ずつ表示する。担当者を特定できない間は予定案件を出さず、検索を入口にする。アクション履歴の「アクション日」は実施日の記録なので、未完了タスクとして扱わない。各行は案件名・現状・日付の短い要約と「開く」ボタンだけ。長い取引先一覧や全項目の表は載せない。最初の版は本人のDM/専用App Homeだけに表示し、共有チャンネルへ顧客情報を投稿しない。

```
┌ CRM-SFA ────────────────────┐
│ [案件を探す] [アクションを記録] │
│ 今日の予定案件                │
│ Aホテル｜商談中｜今日 [開く]  │
│ 最近見た案件                  │
│ B社｜商談中｜10/05   [開く]  │
└──────────────────────────────┘
```

SlackのApp Homeは利用者ごとの私用画面にでき、ボタンから入力用モーダルを開ける。ホームの初回表示には `app_home_opened` イベント、描画には `views.publish` を使う。ホームが使いづらい環境では本人DMの固定メニューを入口にする。公式仕様：[App Home](https://docs.slack.dev/surfaces/app-home/)、[Modals](https://docs.slack.dev/surfaces/modals/)。

### 案件の更新

案件を探す画面は名前入力後に候補を最大10件表示し、取引先名・案件名・現在の営業ステータスを添えて誤選択を防ぐ。選択後は「営業ステータス」「次回アクション日」「確度」のうち変更したいものだけを開く。入力欄には現在値を入れ、保存前に `商談中 → 見積もり提出済み` のように変更前後を1画面で確認する。確定後は「保存済み」または「未反映・再確認が必要」を本人画面へ返し、詳細はCRM画面へリンクする。契約・失注などの集計に影響する状態変更は確認を必須にする。複数項目の編集は1回の操作IDでまとめ、途中失敗時には成功項目と未反映項目を明示する。

### アクションの登録・更新

案件画面の「アクションを記録」から、案件名を引き継いだ状態で「種別（電話/商談/メール等）」「日付」「短いメモ」を入力する。新規登録の初期値は当日。既存アクションの更新では、現在値を表示して必要な欄だけを変える。長い議事録、ファイル、複雑な関連変更はCRM画面で行う。カレンダー予定から届く既存のSlack承認・登録機能は維持し、新しい入口と重複登録しないよう操作IDで守る。

### タップ数と入力負荷

本人の「今日の予定案件」からの更新は原則「開く → 変更 → 確認」の3段階。案件検索を要する場合は「探す → 選ぶ → 変更 → 確認」。1画面に表示する編集項目は最大3つ程度に抑える。日付はSlackの日付選択、状態と種別は選択肢を使い、携帯の文字入力はメモだけにする。画面を閉じても誤って保存しない。公式仕様：[Block Kit](https://docs.slack.dev/block-kit/)、[Date picker](https://docs.slack.dev/reference/block-kit/block-elements/date-picker-element/)。

## 連携の構成

```
Slackホーム／ボタン／入力画面
    ↓ 署名・本人ID・操作権限を確認
既存Vercel API（速やかに受領）
    ↓ 対象ID・旧値・変更項目・操作IDを記録
CRM更新処理 → Notion正本 → 既存同期 → Zoho/kintone等
    ↓
本人のSlack画面へ結果、監査ログへ履歴
```

Slackは操作受領に3秒の制限があるため、外部CRMの同期完了を待ってから応答する設計にしない。受領をすぐ返し、永続化した操作を処理して結果を本人へ返す。選択候補は既存の検索用索引・ミラーを使い、保存直前にNotionの現在値を再取得する。表示時から値が変わっていれば上書きせず差分を見せ直す。同じ操作IDの再送は二重更新しない。公式仕様：[Interactivity](https://docs.slack.dev/interactivity/handling-user-interaction/)、[Modals](https://docs.slack.dev/surfaces/modals/)。

GASも検討したが、既存Vercel APIにはSlack署名検証、監査文脈、Notionクライアント、同期経路がある。Slackの3秒応答と既存の更新処理への接続を優先し、受信と更新はこのAPIへ追加する。GASへの移し替えで独立した認可・台帳・再送経路を増やす利点は現時点で小さい。

## 権限と導入順

1. 本人だけのApp Home/DMで、案件・アクションの閲覧と入力画面を検証する。SlackユーザーIDをCRM利用者へ対応付け、サーバ側で編集可能項目を限定する。Slack画面のボタンを隠すだけで権限を判断しない。
2. 案件の営業ステータス・次回アクション日、アクションの登録・日付・メモを限定して実物検証する。項目ごとの同期結果、変更履歴、競合を確かめる。
3. 成功を見て、担当営業ごとの表示・編集権限、通知からの操作、必要なら案件別チャンネルへ広げる。共有チャンネルの情報公開範囲は別に決める。

Slackアプリ側で必要な設定はHomeタブ、`app_home_opened` イベント、操作用Request URL、必要なBot権限。スコープやBot Userが追加される可能性を含むため、設定画面の保存前に実際の差分を確認する。旧 `/crm` の登録保存は自動審査が拒否済みで、迂回しない。Slack認証交換は対象外。

## 実物検証の合格点

- 携帯のSlackで、本人が案件を特定し、現在値を見て、1項目を更新できる。
- アクションを案件に紐づけて登録し、既存の1件を更新できる。重複送信では1件のまま。
- Notionの正本、Slackの結果、監査ログ、既存同期先の値が同じになる。失敗時は本人へ未反映を知らせる。
- 他人のID、共有チャンネル、古い画面値、期限切れ/再送リクエストからの書込みを拒む。
- 試験は本人だけの場所と専用レコードで行い、作成物を片付ける。斉木別館・千年亭・松涛園の別管理と既修復476件は触らない。

未決定の業務範囲：本人以外の利用者と閲覧範囲、初回で編集可能にする項目、契約/失注などの状態変更の許可、案件別チャンネルを使うか。上記の初期案は本人だけ・限定項目・共有投稿なしを推奨する。

本書は設計案であり、Slackの携帯実機表示・操作感は未検証。実装後に本人の携帯で入力欄の見え方、タップ数、通信待ち、保存結果を確かめて調整する。
