# Webhook受信監視の運用

2026-09-27現在、主機のlaunchdが毎時、読み取り専用の診断APIを呼び、CRM専用Slack botから金沢さん本人のDMへ通知する。Vercelが止まっても主機から通知できる。業務レコード・通知購読は変更しない。GAS版はコードと専用プロジェクトを用意した段階で、認証登録・OAuth同意・トリガー設置は未実施。

```
主機（毎時） → 診断API → 受信記録・実変更・Zoho購読
   └───────────→ 本人のSlack DM
```

## 判定と誤報対策

|観測|判定|
|---|---|
|Zoho購読なし・失効・必要な操作不足・通知先不一致|即時通知|
|Zoho期限まで6時間以内|要確認（自動更新は6時間周期、期限は1日延長）|
|Notion/kintoneに実変更があるが受信が進まない|変更から2時間以上、かつ48分以上あけた再確認で要確認|
|API・認証・受信記録など取得不能|48分以上あけた再確認で監視不能|
|変更がなく受信もない|異常と断定しない|
|シート受信記録なし|未確認として日次報告|

同じ警告の再通知は24時間以上後。受信再開・正常確認は1回だけ通知する。毎日JST日付が変わった後の最初の実行で日次報告する。通知がSlackに受理されなければ状態を確定せず次回再送（2通目だけ失敗した場合は1通目が重複することがある）。

## 通知を受けたら

- **Zoho購読**：`scripts/register_zoho_webhook.py` と購読延長cronの実行状況を調べる。監視は自動修復をしない。
- **Notion受信**：Notion integrationsのWebhook購読画面でpaused・配信失敗を確認。公共APIから購読状態を取得できないため、実変更と受信の比較で補う。
- **kintone受信**：対象アプリのWebhook設定・配信履歴を確認。CSV、一括REST操作、通知対象外のステータス変更でも更新日時は進むため停止とは断定しない。
- **シート未確認**：既存の編集トリガーと配送先を確認。APIによるセル変更は編集トリガーを起動しない。`setupAll`を監視のためだけに実行しない。
- **監視不能**：Vercelの稼働、専用トークン、外部API権限・通信を確認。秘密値やHTTP例外の原文はSlackに貼らない。
- **日次報告が来ない**：主機の電源・スリープ・ログイン状態、launchdログ、Slack認証を確認。主機自体・Slack停止をこの監視単独では通知できない。

## 限界

受信はツール全体の集計。一部のNotion DBやkintoneアプリだけ止まり他が動くケース、同期処理の成否、Zoho/シートの変更後未着は保証しない。Notionの監査ログはNotionへの成功した実変更だけを記録する。システム自身の更新も含む。Notion最新ページ照会は1ページ/DBで、削除イベントだけの欠落は検出できない。kintoneは通知されない操作と障害を機械的に区別できない。

## Notionの登録待ちと配送失敗（2026-10-16）

外部IDがないZoho/kintoneへの通常更新は新規作成せず、項目別の未完了台帳に残す。
主レコードの直接項目について、この登録待ちだけであればWebhookは200で受理する。
500で再送させ続けると、Notionが高エラー率で購読全体を停止するため。
別の配送先の失敗、通信例外、排他競合は従来どおり500で再送対象となる。

200は全配送成功を意味しない。レスポンスの `partial_sync_skipped` に未反映先と
`registration_pending_tools` が残り、管理画面・診断APIでも未完了を確認できる。
ID補完後は新しい編集通知または対象項目の直接配送で復旧し、実値を確認する。
受理済みの同一通知IDを再送しても重複排除される。関連レコードの配送には親のID不足を
適用しない。キュー経路の `needs_attention` は保持する。


## 2026-11-12 Gmail観測の監視SQL修正

観測台帳が蓄積すると、開始イベントIDの文字列連結だけで結合する最新完了検索が5秒の上限を超え、取り込みが継続中でも監視結果がunknownになる事象を確認した。scanIdの既存索引で結合し、max(receivedAt)で最終完了時刻を取得する。対象者・自然走査・正規開始IDを照合する条件を維持し、対象がなければunknownとする。DB索引追加や監視上限の延長、業務データ変更は行わない。

独立したUTF-8の一時PostgreSQLで、別担当者・補完走査・未完了・不正開始IDを除外する回帰試験を含む関連65件が成功。実DBの読取では旧検索は5秒でQueryCanceled、文字列結合を維持したmax版も10秒超。scanId結合の集計は0.638秒で完了した。修正後の診断関数はGmail観測ok・統合待ち0を返した（接続を含む全体時間はSQL単体時間と別）。自然観測の正常とGAS移管の合格判定は区別する。

## 2026-11-13 未対応項目による通知再送の抑制

Notionの直接項目について、書込み前の判定で未対応となり、送り先の項目名対応表も存在しない単純型だけを `configuration_pending_tools` に分類する。例はアクションの議事録・録画リンク→kintone。通知の再送では設定不足は解消しないため、この保留だけなら200を返す。未対応が今回の購読停止の直接原因だったかは未確定。

`skipped_tools` と項目別未完了台帳は残す。200や受信監視okを配送完了と読まない。担当者・関連・選択肢の解決失敗、未接続、未対応判定の例外、他の配送先の一時障害はこの分類で抑止しない。設定を整えた後は、新しい編集通知または最新原本を照合した限定配送で回復し、実保存を確認する。受理済み通知IDの単純再送は重複排除される。

既に配送先と一致する未完了項目を整える場合も、一括完了化しない。原本と配送先のID・項目型・実値、対応表、統合状態を確認し、既存同期と共有するロック内で再取得する。受理時刻を変更せず、確認時点から変化していない行だけ完了時刻を更新し、私有証跡と監査履歴を残す。関連は親のロック・ID・全件取得も必要。kintoneの会社名表示一致と、Zohoの関連ID一致を区別する。
