# 競合失敗の固定診断

2026-09-10 主機CX。着手基準 `aaf5278`。

## 確認した事実と未確定事項

競合5は12子中2成功・10 FailedPrecondition、事後は処理中2・待機10・空き枠1。
既存証跡には例外型しかなく、発生場所・再試行回数・終了条件は復元できない。
36.110秒は準備・初期登録等を含む試験全体であり、再試行時間ではない。

```text
claimの候補検索 ──▶ _atomicの読取り・判断 ──▶ 比較条件付き保存
    │                     │                       │
    └─ 検索RPC            └─ 文書読取りRPC         ├─ ガード版照合
                                                   └─ 保存RPC
```

`small_policy.full_document` の自前の版不一致と、実SDK呼出し/応答列挙の
例外を別の固定値で識別する。ガード内部の追加読取り失敗を版不一致と混同しない。
claimの候補検索は `_atomic` の外なので、その失敗には再試行診断が付かない。

## 診断の意味

発生場所は `guard_version_check` / `rpc_commit` / `rpc_run_query` /
`rpc_batch_get_documents` / `unknown` の許可済み値のみ。RPC分類はSDK境界で
例外を受けた場所を表し、サーバに要求が到達したことの証明ではない。

`classified` は例外型・コードを分類できたという意味で、発生場所・終了理由まで
判明したことを保証しない。`origin` 欠落/unknownは場所未確定。`atomic` 欠落は
未取得または対象外であり、試行0回・期限未到達という意味ではない。

再試行を最終的に打ち切る競合例外には、その_atomic呼出しの総試行回数1～8、経過ミリ秒、
最後に打ち切った試行のoperation/commit段階と次の独立フラグを添える。
以前の各試行の段階・発生場所の履歴は持たない。
同じ版競合でもガード照合で検出すればguard_version_check、
サーバの条件照合で検出すればrpc_commitになる。originだけで根本原因を別物と断定しない。

| フラグ | 意味 |
|---|---|
| non_conflict_chain | cause/context連鎖に確定競合以外があり再送できない |
| attempt_limit | 8回目まで到達した |
| deadline | 競合を捕捉して再試行を判断した時点で3秒以上経過した |

複数フラグが同時にtrueになる場合もそのまま残す。3秒はRPCを中断する強制期限ではない。
経過値はミリ秒未満を切り捨て、最大86,400,000msに制限する。上限値はそれ以上を含む。
例外本文・traceback・要求本文・文書名は診断に含めない。
再試行の条件・回数・待機・例外型/連鎖と成功判定は変えず、診断のための追加RPCは発生しない。

## 実サービス再開の制約

元台帳は1,227/2,000 RPC、文書名77/100、残773 RPC。既存scope1～5は全て使用済み。
台帳の再作成・累計や元期限のリセット・使用済scopeの再実行は禁止。
診断改善だけでは新しい実試験の許可scopeは増えない。

次段階の最小案は、未使用の専用scopeを1個だけ追加し、12子の診断を1回行うこと。
同じ台帳・2,000 RPC上限・100文書名上限・元期限9/24 04:57 JSTを維持する。
合成12件＋scope1件なら文書名は最大90件となるが、必要RPCは実行経路に依存し、
残枠内で完走できる保証はない。上限到達時は失敗停止し、増枠して再開しない。
未使用 `trial-concurrency-6` のみを第2段階・元の作成日時を持つ台帳に限定して追加する。
実適用は未実施。scope許可変更と独立レビュー・他社レビューを終えてから1回実行する。
5回成功・大規模試験・復旧/復元・同期outboxの合格条件は別途残る。

scope6は元作成時刻1788983820.0、同じ作成時刻を持つ第2段階移行履歴、
累計RPC>=1,227/read>=3,887/write>=358/runtime>=5,065/文書名>=77を
CLI・store作成・RPC直前で確認する。これは誤った新台帳や古い台帳からの実行防止であり、
人が台帳をコピー/捏造することを暗号学的に防ぐ仕組みではない。

## 他社レビューの採否（実行前の最終整理）

Claude Opus5中：BLOCKER3/WARN5/INFO4。
参照 https://claude.ai/chat/ef0a84f7-d12d-4e0c-9ee7-9a81873959b5 。

| 指摘 | 採否と根拠 |
|---|---|
| B1:単一子で最大800RPC、残773で完走保証なし | 完走可能性のWARNとして保持。20候補×8回×5は粗い上限で、今回12件・最終競合では即raiseする経路の実測値ではない。共通reserveはRPC前に2000で停止し超過を許さない。完走保証を追加しない。途中枯渇時には観測の残2RPCもなくなる可能性は残る |
| B2:競合2型のorigin未分類 | 採用。FailedPreconditionに加えAborted/AlreadyExistsも固定originを付ける。再試行判定は変更しない |
| B3:不正atomicで基本型もinvalid | 不採用。不正な追加診断を正常分類しない既存方針。境界は独立SECで実機時計と隣接float6282ケースを検証し不整合0。指摘のremaining<=2.2e-16は今回の期限差分から生成できない。deadlineを丸めたmsから再定義すると実際の停止条件の記録を変えるため採らない |
| W1:認可確認のfsync増加 | Geminiと共通。LOCK_SHで最新台帳を読むのみへ修正、予約transactは維持。プロセス内キャッシュは不採用 |
| W2/W3:最後の段階・同じ競合の異なる検出場所 | 上記説明へ追記 |
| W4:small=True経路のテスト不足 | 実試験と同じ小規模ガードで内部read/commit/query/版不一致の診断を追加検証 |
| W5:台帳指紋をテストでも定数参照 | 不採用。固定証跡の値を実装と独立に期待するテストを維持し、恣意的な定数変更まで同時追従させない |

INFOのインデント等だけを理由に往復を続けない。候補検索は_atomic外のため
originあり・atomic欠落も正常な組み合わせ。外部回答はab4b3dcへの評価であり、
