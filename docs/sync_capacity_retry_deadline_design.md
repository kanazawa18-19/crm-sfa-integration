# 初回が3秒を超える競合の再現と修正設計

2026-09-10 主機CX。基準 `931eebe`（製品 `4dc00db`）。製品修正・実サービス試験は未実施。

## ローカルで確認したこと

`tests/sync_capacity/test_capacity.py` の `test_first_slow_conflict_retry_boundary` は、
実SDKのWriteBatchと例外型を使い、通信をモック、経過時間を仮想時計に置換する。
初回commitだけFailedPrecondition、2回目は成功する条件に固定した。

| 初回競合までの仮想経過 | commit呼出し | 再読取り | 結果 |
|---|---:|---:|---|
| 2.999秒 | 2 | 1 | 成功 |
| 3.000秒 | 1 | 0 | 初回例外を送出 |
| 3.181秒 | 1 | 0 | 初回例外を送出 |

`test_success_after_retry_deadline_is_still_returned` は、処理中に時計が30秒まで進んでも
成功を返すことを確認する。実際に30秒待った実験ではない。
既存テストと併せ、結果不明の通信失敗・例外連鎖は再送しないことも確認する。
これは再試行制御の再現であり、Firestoreの遅延原因や実競合の再現ではない。
scope6の3181msがcommit単体時間、scope5も同原因、とは断定しない。

## 現行の時間制約

| 場所 | コード上の設定・挙動 | 設計上の意味 |
|---|---|---|
| `firestore_store.py` `_atomic` | 初回開始から3秒、最大8試行 | 例外後だけ判定。総処理上限ではない |
| 同 `_ComparedBatch.commit` | timeout=10、retry=None | 保存の結果不明をSDKで再送しない |
| 同 `claim` | 最大0.5秒待機、query、候補最大20件 | 前処理は3秒枠外。候補ごとに期限を作り直す |
| `application.py` `drain_one` | claim→業務処理→finish | 共通の残り時間を引き回していない |
| `http.py` `save` | threadpool経由のenqueue | 保存全体の期限を指定していない |
| `scripts/capacity_trial/firestore.py` | 保存10秒・読取り55秒に上書き | 呼出し元でtimeoutを短縮するだけでは効かない |
| `scripts/capacity_trial/__main__.py` | 子プロセス60秒で停止 | 結果不明の枠を自動回収しない |
| `scripts/capacity_trial/concurrency.py` | 競合群45秒 | 子の起動・準備も含む。60秒全てを再試行に使えない |
| `scripts/cloud_run/deploy.sh` | Cloud Run timeout=3600 | リポジトリの配備設定。現在の実配備値は未照合 |

最短の呼出し元制約を守る必要がある。Cloud Run設定を根拠にWebhookや隔離試験の
待ち時間を延長しない。外側の待機を中断してもthreadpool内の保存停止は保証できない。

## 採用する修正方針（次イシューで実装）

「総処理期限」と「競合後の再試行機会」を分ける。

```text
呼出し元の残り時間 ──▶ query・読取り・保存・待機に共有
                               │
                     初回の確定競合
                               │
              ┌────────────────┴──────────────┐
       残予算で再試行可能                 期限不足・結果不明
              ▼                               ▼
       最新値を読み直す                   再送せず停止
```

1. monotonic時計による絶対期限を呼出し元から渡す。claimは候補ごとに期限を
   リセットせず、query・初期待機も含む。drainは業務処理とfinish用の時間を別途確保する。
2. 初回の確定競合に対する再試行は「初回から3秒経過」を理由に拒否しない。
   総期限内で次の試行に必要な時間を確保できる場合に、最低1回の機会を与える。
   無条件の最低回数保証はしない。最大8試行と確定競合のみの制限を維持する。
3. 全RPCと待機の直前で残り時間を検査し、timeoutは既存上限と残り時間の小さい方。
   読取り側のSDK再試行にも総期限を適用する。バックオフ後にも再検査する。
   保存のretry=Noneは維持し、保存結果不明は再送・自動枠返却しない。
   保存の成功応答を受け取った場合は、期限超過していても未保存扱いに変更しない。
4. 試験ガードはtimeoutを拡大しない。追加読取り・台帳ロック待機・予約処理にも
   同じ期限を渡す。期限不足ならRPC前で止め、消費済み予約を巻き戻さない。
5. 再試行では必ず新しい比較更新batchでscope/jobを読み直す。別の処理が満枠にした
   場合は正常な待機として返す。古い書込み内容を再送しない。
6. 診断はV2を追加し、総期限不足・回数上限・不確定連鎖を固定値で区別する。
   `diagnostics.py` のV1は「deadline == elapsed_ms >= 3000」を要求しているため、
   意味を上書きしない。既存scope1～6証跡の読み取り互換を保つ。

秒数の採用は実装時の設定要件として残す。現在の実配備期限、Webhook提供元の
応答制約、query/ガード/業務/finishの所要時間内訳は未検証であり、固定の総秒数を
実測済みのように置かない。実装は期限・試行予算を注入可能にし、仮想時計で評価する。
「次の試行に必要な時間」はRPCごとの上限と処理段階の予算として定義し、
単に残時間が正なら何でも開始する判定にはしない。

## 次の実装の受入条件

- 初回3.181秒の確定競合でも、十分な総予算があれば新しい値で再試行できる。
- 総期限到達・次の試行予算不足・バックオフ中の期限到達では新規RPCを開始しない。
- query、複数候補、ガード追加読取り、台帳待機を含めた予算が再設定されない。
- 結果不明の保存、原因/文脈に結果不明を含む競合は1回で止め、枠を保持する。
- 最大8回、満枠への変化、2試行目も競合、finish期限不足を独立QAが検証する。
- 試験wrapperが短いtimeoutを延長しないこと、V1/V2診断互換を検証する。

## 見送った案と実サービスの制約

独立QAで `test_capacity.py` と `test_trial_diagnostics.py` の100件成功。
既存Starlette/httpx非推奨警告1件。独立SECが時間制約と診断互換の設計を照合した。
製品の現行不具合は未修正であり、設計・再現の完了を不具合解消とは扱わない。

3秒を単純に延ばす案は、総期限と初回再試行機会の不整合を残すため見送り。
期限を無視して必ず2回実行する案は、呼出し元停止と保存結果不明を増やすため見送り。
本設計ではscope追加・再実行・台帳リセット・認証更新を行わない。
前回記録は残517RPC・文書名残10（今回再照会なし）。新scope+12jobは13文書名必要。
実サービスでの合格や追加試験の認可は、本ローカル再現・設計からは導かない。
