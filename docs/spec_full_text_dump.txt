01_システム構成
================================================================================
1. システム構成 / アーキテクチャ |  |  |  | 
ツール同士を直接繋ぐメッシュ型ではなく、自作の同期エンジンを中央に置いたハブ＆スポーク構造を採用する。 |  |  |  | 
構成要素 | ツール / 環境 | 役割・仕様詳細 | 連携プロトコル | 備考
マスターDB | Notion | Single Source of Truth（真のマスターデータ）。6つの核データベースを保持し、競合発生時の正となる。 | Notion API（REST / Webhook） | 常時稼働・必須
閲覧・分析UI | Googleスプレッドシート | リアルタイム同期データの全社閲覧、コンフリクトログの退避先、営業分析ダッシュボード。 | Google Apps Script（onEdit）/ Sheets API | 未作成。本仕様に沿って新規構築
既存業務DB | kintone | 営業本部 案件管理 / 営業本部 アクション管理 / 取引先マスタ。相互双方向同期の対象。 | kintone REST API / Webhook | 当面は現場入力が継続する前提
過渡期CRM | Zoho CRM | 解約までの過渡期のみ同期。アクション / チェーン / 案件 / 取引先 / 連絡先 / サービス・商品を保持。 | Zoho CRM API / Notification Webhook | ENABLE_ZOHO=False で切り離し可能
名刺・キーマン | Eight | 名刺データの定期取得。連絡先DBへの自動登録・名寄せ、人事異動検知アラート。 | Eight API / CSVインポート | 片方向（Eight → Notion）
同期エンジン | AWS Lambda / GCP Cloud Functions | 各ツールの更新イベントを受信し、他3ツールへ即時波及・書き換えを行うハブサーバー。 | Python 3.11 または Node.js | サーバーレスでランニングコストを最小化
ID管理ストア | 同期エンジン付属DB（DynamoDB / Firestore 等） | 各ツールのレコードIDを1対1で保持するマッピングテーブル。last_synced_at も併せて管理。 | 内部API | 同期の正確性を担保する中核
■ 疎結合設計：連携モジュールはツール単位で独立させる（notion_sync / spreadsheet_sync / kintone_sync / zoho_sync）。環境変数の ENABLE_ZOHO を False に変更するだけで、他システムに一切影響を与えずZoho連携を切り離せること。 |  |  |  |

2. Notion データベース構成（全6DB） |  |  |  |  |  | 
既存Notionで確立済みのID体系（CLI- / HC- / MSA-PJ- / SA-AC-）を全ツール共通の主キーとして踏襲する。 |  |  |  |  |  | 
No. | DB名 | Notion主キー | kintone対応キー | Zoho対応キー | 管理内容 | 主なリレーション
① | 取引先マスターDB | CLI-xxx | 取引先マスタ レコード番号 | 取引先 | 企業基本情報、顧客種別、住所・エリア情報、親子会社階層、公的マスデータ | 自DB（親/子）、チェーンDB、連絡先DB、案件管理DB
② | チェーンDB | HC-xxx | 本部名 | チェーン | 飲食・小売・ホテル等のチェーン店舗網／ブランド、運営会社、施設数、アプローチ状況 | 取引先マスターDB
③ | 連絡先DB（新規独立） | CNT-xxx | 担当者名1〜3（分割） | 連絡先（リード） | 個人（キーマン）情報、役職・部署、名刺情報、人事異動履歴 | 取引先マスターDB、アクション管理DB
④ | 案件管理DB | MSA-PJ-xxx | 案件管理 レコード番号 | 案件 | パイプライン、営業ステータス、初期費用／月額費用、粗利、確度、総接触回数、コンディション判定 | 取引先マスターDB、サービス・商品DB、アクション管理DB
⑤ | サービス・商品DB（新規独立） | PRD-xxx | サービス（ショット／ランニング） | サービス・商品 | 自社プロダクトのマスター、課金形態、標準価格、クロスセル判定基準 | 案件管理DB
⑥ | アクション管理DB | SA-AC-xxx | アクション管理 レコード番号 | アクション | 全タッチポイント履歴（テレアポ／訪問商談／オンライン商談／メール／自動メール）、商談回数、履歴メモ | 案件管理DB、取引先マスターDB、連絡先DB
■ 設計方針：①「チェーン」は店舗網・ブランドを指し、親会社／子会社の関係は取引先マスターDB内のセルフリレーションで表現する。②既存Notionに存在しなかった「連絡先」「サービス・商品」は独立DBとして新設する。 |  |  |  |  |  |

05_同期・競合制御
================================================================================
5. Any-to-Any 相互同期 / コンフリクト制御仕様 |  | 
どのツールで編集しても他の全ツールへ即時反映される完全相互同期を実現しつつ、無限ループとデータ消失を確実に防ぐ。 |  | 
機能項目 | 仕様詳細 | 実装ロジック・制御ルール
Any-to-Any 相互同期 | Notion / スプレッドシート / kintone / Zoho のいずれで追加・編集・削除しても、他の全ツールへ即座に追従・反映される。 | 各ツールのWebhookを同期エンジンが受信し、送信元を除く3ツールのAPIを呼び出して書き換える。
変更検知の仕組み | ツールごとに変更イベントを受け取る手段を実装する。 | Notion：Notion API Webhooks ／ スプレッドシート：GAS の onEdit ／ kintone：kintone Webhook ／ Zoho：Notification Webhook
ハイブリッド同期 | 即時性と安定性の両立のため、即時同期と定時バッチを併用する。 | 即時：新規登録・ステージ変更・緊急更新／定時：同期漏れの自己修復、分析指標の再計算、日報週報の生成
送信元の自動除外 | 変更の発生元ツールには書き戻しを行わない。 | Self-Exclusion。イベントの origin を判定し、対象ツールリストから除外する。
無限ループ防止 | 同期エンジン自身の書き込みによって発生したWebhookを再処理しない。 | APIリクエストヘッダーに X-Sync-System-ID: 自社CRM-Engine を付与し、当該IDによる変更通知は処理をスキップする。
レコード特定 | 全ツール間で同一レコードを1対1で特定する。 | IDマッピングテーブル（Notion主キー ⇔ kintoneレコード番号 ⇔ Zoho ID ⇔ スプシ行）を同期エンジン側で保持。
コンフリクト検知 | 各レコードに同期管理用の項目を保持し、競合を判定する。 | updated_at > last_synced_at が複数ツールで成立し、かつ値が異なる場合を「コンフリクト」と判定する。
競合解決①（片方が空欄） | 一方が空欄、他方に値がある場合は、最終更新日時が新しい側の操作を採用する。 | 空欄化が新しい → 他方も空欄化（削除を伝播）／ 値の追記が新しい → 他方へ値を補完（追記を伝播）
競合解決②（双方に異なる値） | 双方に異なる値が入力されている場合は、マスターDBであるNotionの値を正とする。 | Notionの値で他ツールを上書きし、整合性を担保する。移行時の表記揺れもこのルールで一括クレンジングされる。
データ退避 | 上書きにより却下されたデータは消失させず必ず保全する。 | 却下データをスプレッドシート「同期ログ」タブへ自動記録（対象ID・項目名・採用値・却下値・発生日時）。
アラート通知 | 重要項目の競合が自動解決された場合は管理者へ通知する。 | Slack管理チャンネルへ即時通知。通知内容：対象案件 / 変更項目 / 採用データ / 却下データ。
大量データ対策 | 取引先・案件で数万件規模のため、全件同期は行わない。 | 差分更新の徹底。最終更新日時が前回同期より新しいレコードのみを対象とし、Notion APIのページング制限（100件／回）に対応する。
■ 削除の扱い：物理削除ではなく「削除フラグ」による論理削除を推奨。誤操作が4ツールへ即時波及するリスクを回避できる。 |  | 
【コンフリクト判定フロー】 |  | 
  1. 各ツールの値が一致しているか？ |  | 
     ├─ YES ──→ 処理なし（正常） |  | 
     └─ NO  ──→ 2 へ |  | 
  2. 一方が「空欄（NULL）」か？ |  | 
     ├─ YES ──→ updated_at が新しい方の操作を採用 |  | 
     │            ・空欄化した側が新しい ──→ 他方も空欄化（削除処理） |  | 
     │            ・値を追記した側が新しい ──→ 他方に値を同期（補完処理） |  | 
     │ |  | 
     └─ NO  ──→ 双方に異なる値が存在（データ競合） |  | 
                  ──→ Notion（マスターDB）の値を正として他方を自動上書き |  | 
                  ──→ 却下データをスプレッドシート「同期ログ」タブへ退避 |  | 
                  ──→ Slack管理チャンネルへアラート通知 |  |
