# メール照合と営業アクション記録

メールの照合受付・担当者・判断履歴・配送状態をこのシステムに保存する。営業アクションは既存のNotionアクションを作成・訂正し、既存の共通配送処理でZoho・kintone・Sheetsへ渡す。メール内容の判断にAIは使わない。

**アクション履歴の対象は営業担当者の送信メールだけ**（2026-10-16本人訂正）。To/CCから本人と `sales@cnctor.jp` を除き、相手が残らないメールは対象外。取引先宛でsalesをCCしたメールは対象。他の社員宛は社内ドメインだけを理由に除外しない。取得対象と実施者は既存の本人メールボックス・社員対応表で確認する。受信メールは保持するが照合の必須条件にはせず、受付時点で履歴作成の対象外にする。受信メールの手動確定・再開は拒否し、旧版で処理待ちになった受信メールも外部書込み前に停止する。既存本文やGmail原本は削除しない。

## 判定と操作

```text
Gmail取得 → 共通IDで受付 → 宛先メールで既存連絡先を照合
                             ├ 連絡先1件・所属1件 → アクション → 共通配送
                             └ 未登録・重複・所属不明 → 本人が確認
```

- メールアドレスの前後空白と大文字小文字を整えて完全一致させる（2026-10-17本人指示）。名前、宛名、受信署名の一致は必須にしない。同名でも別メールの連絡先は妨げにならない。
- 対象相手が1人ならそのメールを使用する。複数人の場合は対象Toが1人のときだけ主相手とし、CCも手動選択用候補に保持する。複数Toや主相手不明は保留する。
- 一致する連絡先1件・その既存所属1件のとき自動確定する。所属会社を今回の対象とし、案件は自動選択しない。メール重複・所属複数は保留する。所属なし・メール不一致の場合は下記の既存連絡先補完を試す。
- 作成直前にも実物のメール一致・連絡先の一意性・所属を再確認する。登録済みの再受付は本人が選んだ施設・案件を保持し、同じアクションを再配送する。作成結果不明の受付は再作成しない。
- 相手の所属会社、今回の対象施設、今回の案件は別欄。手動確定では別の対象施設を選べる。案件は選択施設との関連を実物で確認する。
- 連絡先未登録も受付に残る。既存CRMで登録してから「再照合」する。新しい人物・取引先の自動作成や重複マスターの統合は含めない。
- 管理画面 `/email-review` とSlackアプリホーム「メールの照合」は共通の受付・変更版を使用。確定、訂正、保留、対象外、再照合、登録結果の照合ができる。Slackは各状態の最新25件、管理画面は30件ごとのページ切替。
- 閲覧・操作は自分のメールに限定。共同受信したメールは受付を共有するが、相手が受信していないメールの根拠は返さない。共同受信も履歴作成の対象外。送信者は取得対象メールボックス本人との一致で判定し、記録時に既存の社員対応表を照合する。別メンバーから届いた社内メールを受信者の実績にはしない。共有メールボックスや送信別名の代理確認は未対応。

## 既存連絡先の補完（2026-10-17本人指示）

- メール一致が1件で所属空欄なら、送信の冒頭宛名に書かれた取引先名と既存マスターを照合する。空白・全半角・大文字小文字を整えた完全一致が1件のときだけ紐付ける。近い名前を順位で推測しない。既存所属の変更はしない。
- メール一致が無い場合、宛名の取引先1件に所属する氏名一致の連絡先が1件なら、その人のメールを変更する。明示された姓だけの宛名も使えるが、同姓・未分割の同姓候補があれば保留。会社が重複しているときも保留する。
- メール変更は、送信日時が現在の連絡先更新日時から1分以上後のときだけ。更新日時不明・過去アドレスとして備考に記録済みの場合は保留し、古いバックログで現在のメールを巻き戻さない。
- 旧メールは既存備考を保持して `過去メールアドレス: …` と追記する。メールと備考は同じNotion更新で保存する。備考に書式やリンクがある場合は保留し、原本を平文化しない。補完済みの再配送では後から追加された備考を保持する。空欄メールの補完では履歴行を作らない。
- 日本語氏名の区切りが明示されていれば姓・名へ空欄補完する。判別不能なら名前全体を姓へ入れ、名は空欄とする。入力済み値は上書きしない。メール処理を通る連絡先で実施する。既存全件へは `scripts/complete_contact_names.py` で私有の計画ファイルを使って適用でき、計画作成と実値照合・更新を区別する。
- 評価時は変更予定だけを保存し、登録担当者と本文の確認後に、ロック内で最新のメール・会社・氏名候補・備考を再確認して更新する。予定の備考等は公開APIへ返さない。更新中に原本が変わった場合は保留する。
- Notionの備考は既存プロパティを利用し、他ツールへの備考同期は追加しない。所属連絡先が多い会社では一意性確認に時間がかかる場合がある。

## 本文の記録

履歴メモには今回の本文と署名を保存し、過去メールの引用を除く（2026-10-16本人訂正）。日本語Gmailの日付＋送信者行、英語のOn ... wrote:、Original/Forwarded Message、複数項目を持つOutlookヘッダーを引用開始として扱う。後続が引用記号 `>` で始まる場合は引用行だけを除き、その間や後の回答・署名は残す。引用記号がない過去本文は見出し以降を除く。通常の改行・署名・本文中の日付や単独のFrom:は保持する。判別できない引用は残すため、全形式の引用除去を保証しない。Gmail原本は変更しない。登録値はNotionの保存形式に合わせ、改行をLF、アクション日時を分精度に揃える。受付に保存した元の本文と日時は変更しない。

2026-10-21のローカル変更では、Python/GASの本文を共通解析し、引用除去後40,000 UTF-16単位（通常の日本語は4万字、絵文字などは2単位）を上限とする。本番未反映。HTMLは実行せず文字へ変換し、非表示要素・引用を除去、http(s)リンク先は保持する。multipart/alternativeはプレーンテキストを優先し、mixedの独立した本文は結合する。本文未取得・引用だけ・上限超は抜粋や途中切断で代用せず保留する。デコード前は部品あたり20万文字、全体はヘッダー込み25万文字、深さ20、総部品100、子部品30を上限とする。本文の外部参照は15万バイト以下を最大4回取得し、添付ファイル・転送メール本体は辿らない。構造/容量超過でも差出人・宛先・件名・Message-IDは原本から保持する。通信失敗は再試行対象とし、本文参照の404をメール自体の消失と扱わない。Notionの履歴メモは2,000文字ずつ分割し、他の保存先へも引用除去後の本文を渡す。既存アクションや保存済み本文を一括変更しない。既存の受付から初めてアクションを作る場合も引用を除く。

返信不可アドレス（no-reply等）かつ認証コード・ワンタイムパスコード通知の件名は照合DBへの保存前に除外する。返信可能な送信元は、確認済みの送信元と通知件名の完全一致に限定する（WILLERの認証コード、高速バスドットコムのパスワード通知、UPSIDERの本人認証）。同じ送信元の予約・問い合わせなどは残す。通常の人からの認証機能に関する相談は除外しない。この判定の変更だけでは既存受付の本文は削除されない。

## 重複と訂正

RFC Message-IDと送信者アドレスを共通IDに使用する。同一メールの再取得、複数メンバーの取得、Slackと管理画面の同時操作でも受付・アクションを増やさない。共通IDが同じでも本文・件名・宛先が違う場合、または本文が未取得の場合は別の所有者へ共有しない。同じowner+Gmail IDの情報補完だけは本文未取得でも許可する。共通ID未取得では作成を保留し、同じGmail IDの再取得で補完する。

作成前の予約と送信予定値をDBへ保存してから一度だけ作成する。応答消失・中断は「登録結果の照合待ち」に隔離し、時間経過だけで再作成しない。「登録済みの記録を探す」で予定値に一致する既存記録が一つだけ見つかったとき、同じIDで配送を再開する。見つからない・編集済み・複数の場合は管理者による原本照合が必要で、自動解除・強制作成ボタンは設けない。

訂正は同じアクションIDへの更新。外部で編集された項目は上書きせず確認待ちに戻す。連絡先の所属は空欄補完、または当該受付で補完した同じ連絡先・同じ会社の訂正だけを許可する。既存所属の一括付替や重複マスターの統合・削除は行わない。統合済みID・統合作業中の記録は既存の別名/保留機構に従って選び直す。

「記録作成済み」と「配送処理完了／一部未反映」は別状態。配送完了は共通処理の結果であり、外部4システムの実値読戻しをこの画面で保証する表示ではない。一部未反映は既存の同期待ちとともに確認し、関連先の再確定で同じ記録を再配送できる。

## 配備と開始条件

機能フラグの既定値はOFF。2026-10-16に本人指示で本番配備・DB3表の適用・Python取得経路の有効化を実施。現在のGmail接続は金沢氏の1件。開始日時を設定し、既存担当者対応に本人メールを追加した。社内除外へcnctor.netを追加。GASコードは更新・保存一致を確認したが、従来の観測運転を維持し、照合フラグと定期実行は追加していない。

1. 承認された配備時に `dashboard/prisma/migrations/20261016090000_email_review` を適用する。`EmailReview`、所有者、判断履歴の3表と検索索引を追加する。通常のdashboard buildはマイグレーションも実行するため、本番DBに接続したまま検証用ビルドを実行しない。
2. 既存CRMユーザー対応表 `CRM_USER_MAPPING_JSON.users` に各担当者の `email` と `notion_id` が一意に設定され、Notionユーザー実物のメールと一致することを確認する。不足は自動補完せず確認待ちになる。
3. backendに `EMAIL_REVIEW_ENABLED=true`、`EMAIL_REVIEW_START_AT` をタイムゾーン付き日時で設定する。開始時刻以前のメールを自動記録しない。対象社内ドメインは既存Gmail設定を引き継ぐ。`EMAIL_REVIEW_INTERNAL_DOMAINS` で照合だけの追加除外ドメインをカンマ区切り指定でき、既存設定を置き換えない。社内通知は本文の照合保存より前に除外する。
4. GAS取得を使う環境は `EMAIL_REVIEW_ENABLED=true` のScript Propertyと更新版 `gas/gmail-ingest/ingest.js` が必要。Python取得はbackendフラグで切替。更新版は引用除去後40,000 UTF-16単位以内のテキスト/HTML本文に対応する。APIを先に配備し、その後GASを更新する（旧APIはbody_mimeを扱わない）。上限超は切り詰めず未取得として扱い、添付本体は解析しない。日本語の主要文字コードを扱う。本文が取得できない場合は確認待ち。
5. Slackは既存の署名検証・Interactivity・App Homeを使用。`SLACK_CRM_ALLOWED_TEAM_ID`、`users.info`で本人メールを取得できる権限（`users:read.email`等）、同じメールの管理画面User登録が必要。`DASHBOARD_BASE_URL` を設定すると全件表示へのリンクを出す。チャネルへの自動通知・DM配信は今回追加しない。
6. 既存 `/api/cron/slack-crm-drain` で1回あたり最大5件ずつ照合・記録する。新しい定期実行は作らない。実行間隔と処理量は有効化後の観測対象。
7. ステージングまたは本人限定の試験で、メール取得→照合→本人確認→各配送先の実物読戻しとSlack応答時間を確認してから対象者を広げる。本番での検証は別途明示指示の範囲で行う。

停止時はbackendとGASのフラグをOFFにする。受付・履歴を消さない。本文はDBに保存し公開APIでは返さない。本文と履歴の自動削除/保存期間設定は未実装なので、対象者展開前に運用を決める。`scripts/report_email_body_retention.py --days N` は読取専用で状態別件数/本文バイト数を試算する。基準は受付の最終更新時刻であり受信時刻ではない。日数指定は比較条件だけで、削除承認や保存期間設定にならない。判断履歴の根拠・候補、snippet、配送済み各システムの本文はこの集計に含まれず、本文バイト数はDB解放量を意味しない。

## 検証範囲

- 純粋な判定、同時確定、共通ID補完、共有受信者の閲覧制限、作成応答消失、訂正、配送再試行を自動テスト。
- 使い捨てローカルPostgreSQLで実マイグレーション・SQL・並行予約・メール2通からの自動確定を検証。外部Notion/配送先はテスト用代替であり、実サービスへの反映検証ではない。
- ローカル管理画面を合成データのAPIで開き、タブ・候補選択・根拠表示・確定受付と幅390pxで横はみ出しがないことを確認。
- 本番Gmailからの自然取込み、定期照合、本人ログイン後の管理画面で確認待ちの表示を確認。届いたメールはセミナー案内と認証通知であり、営業メールによるアクション作成・全配送先の実値読戻し・Slack入口の実物確認は未完了。認証メールはsales-division@cnctor.netから送るよう復旧し、本人が受信・ログインを確認。独立レビューと外部モデルの指摘の採否は `docs/evidence/email-review-20261016/` に記録する。

引用除去導入前の受付を同じ所有者・同じGmail IDで再取得した場合は、今回本文の一致で移行を許可する。別所有者へ旧引用本文が共有されないよう、他所有者の初回取得では本文完全一致を維持するため、旧形式と衝突して保留になる場合がある。
