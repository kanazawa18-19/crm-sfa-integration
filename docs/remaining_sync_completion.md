## 条件付き新規登録

```
Notionの新規ページ      シート「CRM同期 → 選択した新規行を登録」
         └───────────────┬─────────────────┘
              必須項目・同名候補を確認
                   ┌─────┴─────┐
                 確定          不足・曖昧
                   │               └→ メモ・登録状況・週次一覧
           DBへ作成予約を確定
                   │
             POSTは1回だけ
          ┌────────┴────────┐
        ID取得               応答不明
  予約へID保存→対応表登録       再POSTせず保留
```

- `HUB_CREATION_ENABLED_SINCE`（タイムゾーン付きISO日時）を設定した場合のみ有効。Notionはその日時以後に作成された未登録ページに限定する。過去の146,515ページを自動作成しない。
- シートは同期キーを消しただけでは新規登録しない。メニューによる明示操作で `new:UUID` と行の識別情報（DeveloperMetadata）を発行し、`登録状況` 列へ結果を表示する。
- 行移動への追随はDeveloperMetadataを使用。データフィルタで同じ行を読書きし、行番号を使って同期キーを書き換えない。識別情報または同期キーが重複・不一致なら停止する。
- シートではNotionページを先に作成する。Notionで担当者・関連付け・選択肢が確定できない型は新規作成を保留する。
- 外部の必須項目はAPIから読み取り、Zohoはレイアウト上の必須項目も全レイアウト分確認する。値が不足したら作らない。
- 同名候補があれば既存へ自動で結び付けない。名称の表記違いを推測する名寄せはしない。Zohoは検索APIの索引遅延を避け、名前とIDの通常一覧を最大10ページ・2,000件まで読み、最後まで照合する。上限超過・応答不正・取得失敗は作成前に保留する。COQL権限追加は不要。
- 同時登録はDBの一意な予約（送り先・DB・正規化した名前のハッシュ）で排除。応答不明・予約後の異常終了は自動再実行しない。ID取得後に対応表保存だけ失敗した場合は保存から再開する。
- 外部作成によるWebhookが対応表登録より先に来ても、同じ名前の作成予約があれば別のNotionページを作らない。
- `CRM同期確認_` / `CRM同期テスト_` で始まる名前は作成対象外。
- 新規作成に成功したあとも、登録済みの相手への通常更新は継続する。シート起点で外部作成が保留になった場合は、通常のセル編集がNotionへ反映された後に登録履歴から再判定する。Notionへの反映に失敗した間は再判定しない。

実APIの必須レイアウト確認に基づき、Zohoで現在自動作成できるのはチェーンだけ。他の5DBは上表の理由で保留する。送信前に取得した型を検査し、数値文字列は数値へ変換する。単位付き文字列・真偽値・非有限数は数値として受け付けず、未対応の複合型も予約前に保留する。

予約状態の `reserved` は「結果未確認」であり、失敗が確定した意味ではない。人が外部で結果を照合するまで削除・リセットしない。`blocked` はPOST前の条件不足なので、次の本人編集で再判定できる。

## 応答不明・対応表保存失敗の復旧

- 週次の `reserved` は、外部へPOSTが届いたか確定できない状態。予約は消さず、元の登録キー・送り先・作成時刻を基に外部の実レコードを担当者が照合する。同名だけで確定しない。
- 外部IDを確定できた場合だけ、その予約へ確認済みIDを保存して `created` とし、次の元ページ編集から対応表保存を再開する。別IDへの付け替えや新しいPOSTは行わない。対応表保存失敗は別の `mapping:<送り先>` 保留として週次に残り、保存成功時に解消する。
- 外部に存在しないことを確実に確認できた場合だけ、保守作業として当該予約1件を再判定可能な保留へ戻す。確認不能なら `reserved` を維持する。復旧時は元の登録操作との同時実行を止め、対象キーを限定し、処理前後の状態と照合根拠を記録する。
- Prisma schemaだけでは表現していない部分一意インデックス（`reserved` / `created` に限定する送り先・DB・名前ハッシュ）はmigrationが正本。`db push` 等で落とさず、今後のmigrationでも維持する。
- 行の識別情報が消えたり重複したときは、推測した行へ状況を書き込まない。週次の保留理由を見て元の行と識別情報を確認する。

Zohoチェーン通常一覧は実APIで232件（1ページ目200件・継続あり、2ページ目32件・継続なし）を確認済み。同名確認の保証範囲は「一覧照合時点の候補」と「当システムの同時登録・再送の防止」。照合からPOSTまでの間に他者が直接作成する競合は、外部の一意制約がないため原子的には防止できない。

外部起点の初回同期は、Notionと対応表・シート行の作成後にメモを書く。メモだけ失敗した場合は完了時刻を進めず、再送で既存ページのメモを補う。通常シート編集後の新規登録再判定だけが失敗した場合は、編集同期の成功を維持し、固定文ログと週次保留に分けて記録する（DB障害中はログのみ）。
