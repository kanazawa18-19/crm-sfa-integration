# リスト作成マシーン（2026-09-11）

楽天トラベルに掲載されている宿泊施設から、条件に合う営業リストを作る機能。
`src/facility_list/` と `dashboard/app/(dashboard)/facility-list/` が実体。

```
   ① 取り込み（バッチ）        楽天トラベルの公開ページ ──▶ RakutenFacility
        scripts/import_rakuten_facilities.py

   ② 抽出（画面）              条件で絞る ──▶ CRMと突合 ──▶ CSV
        /facility-list  →  POST /api/facility-list/{preview,export}
```

画面から楽天へはアクセスしない。先に溜めた母集団を絞るだけなので即座に結果が出る。

---

## 1. なぜ API ではなく公開ページなのか

楽天ウェブサービス（楽天トラベル施設検索API）を使えば客室数・クチコミ点数・電話番号まで
1リクエスト30件で取れる。**それでも使わない。**

```
   利用規約 第10条(4)  楽天アフィリエイト以外の方法で収入を得ることを禁止
   利用規約 第10条(7)  取得した情報は、会社が指定した目的・方法でのみ利用可能
```

自社商材の営業リスト作成がこれに触れる可能性があり、2026-09-11に本人判断で
**公開ページ方式**を採用した。公開ページの取得は robots.txt が許可している範囲で行う。

| | API方式 | 公開ページ方式（採用） |
|---|---|---|
| 施設一覧 | 1リクエスト30件 | エリア一覧が1リクエスト30件（同じ） |
| 客室数・点数 | 一覧で取れる | 一覧で点数、施設ページで客室数 |
| 電話番号 | `telephoneNo` で取れる | **取れない**（CRM側から補う） |
| 規約 | 第10条(4)(7)に触れうる | robots.txt の範囲で許可 |

将来 API 利用の可否を楽天へ確認して OK が出れば、`rakuten_client.py` を差し替えるだけで
移行できる（パーサとドメインはそのまま使える）。

## 3. チェックイン機の判定（2段構え）

メイリーのQRチェックインは**既存のチェックイン機をそのまま活かす**設計なので、
「チェックイン機があるか」が提案可否をそのまま決める。ところが楽天トラベルの施設ページには
ほとんど書かれていない（**鳥取県40施設で実測して記載ありは0件**）。そこで2段構えにしている。

```
   一次判定  施設ページの記述        無料・全件      services.detect_check_in_machine()
   二次判定  WEB検索で確認           有料・候補のみ   check_in_machine_search.py
```

- 二次判定は `claude-haiku-4-5` ＋ web_search を1コール。軽い定型判定なのでHaiku
- 判定は `yes` / `no` / `unknown` の3値。**「書かれていない」は `no` ではなく `unknown`**
- `yes` / `no` には必ず根拠テキストとURLを残す。**根拠が無い断定は `unknown` に倒す**
- 結果は `FacilityCheckInMachine` テーブルに残り、施設マスタを取り込み直しても消えない
- `ANTHROPIC_API_KEY` が無ければ検索せず「未実行」を返す（例外にはしない）

```bash
# まず対象件数を見る（APIを呼ばない）
python scripts/search_check_in_machines.py --prefecture 鳥取県 --dry-run

# 実際に検索する（1件ごとにClaude APIを呼ぶ。既定の上限は50件）
python scripts/search_check_in_machines.py --prefecture 鳥取県 --limit 20
```

## 4. 構成（DDD）

```
   src/facility_list/
   ├── domain/          何にも依存しない。DBも楽天も起動せずテストできる
   │   ├── models.py    Facility / ListCriteria / RoomCountRange / 各種状態
   │   └── services.py  カテゴリ推定・条件判定・商材適合・チェックイン機の一次判定
   ├── application/
   │   ├── import_facilities.py  取り込み（浅い→深い の2段階）
   │   └── build_list.py         抽出 → CRM突合 → 行を組む
   ├── infrastructure/
   │   ├── rakuten_client.py       HTTP取得・robots・レート制御・サイトマップ
   │   ├── rakuten_page_parser.py  HTML → 事実（HTTPを持たない純粋関数）
   │   ├── crm_matcher.py          ClientNameIndex と Notion で突合
   │   ├── db.py                   RakutenFacility の読み書き（psycopg直接）
   │   └── exporters.py            CSV・スプレッドシート用の2次元配列
   └── presentation/   画面は dashboard 側。ここはCLIのみ
```

判定ロジックは全て Python 側にあり、画面（Next.js）は FastAPI 経由で呼ぶだけ。
TypeScript 側に業務ルールを二重実装しない。

## 8. 運用

```bash
# まず1県・30件で試す（DBに書かない）
python scripts/import_rakuten_facilities.py --prefecture 鳥取県 --max-pages 1 --dry-run

# 1県を丸ごと取り込む
python scripts/import_rakuten_facilities.py --prefecture 鳥取県

# 一覧だけ全県（詳細は後で）
python scripts/import_rakuten_facilities.py --all-prefectures --shallow-only
```

- **全国を一度に回さない。** 1施設あたり2リクエスト・既定1.0秒間隔なので、
  43,753施設の詳細取得は24時間規模になる。都道府県単位で進める
- `--interval` を短くしすぎない。429（レート制限）を踏むと専用の例外で止まる
- 掲載終了した施設は**行を消さず** `isListed=false` にする
  （ProjectMirror全消失インシデントの教訓。母集団は消すより残す方が安い）

### rc=0 を信用しない

取り込み結果は「成功件数」だけでなく次を必ず出す。

```
   詳細取得: 成功N件 / 掲載終了N件 / 失敗N件 / 客室数が読めなかったN件
```

**客室数が読めなかった割合が3割を超えたらエラーログを出す**（`ImportResult.is_healthy`）。
楽天側のHTML変更でパーサが静かに壊れても、件数だけは出てしまうため。
失敗が1件でもあれば終了コードを2にする。

## 10. 他社モデルレビューで直したこと（2026-09-12）

ChatGPT（GPT-5.6 Sol・思考量中）と Gemini（3.1 Pro）に主要4ファイルを渡した。
**両社が独立に同じBLOCKER**を挙げた（CLAUDE.md「複数のレビュアーが独立に同じ指摘を
出したものは、ほぼ本物」）。

| 重要度 | 指摘（出どころ） | 対応 |
|---|---|---|
| BLOCKER | **施設名 ≠ CRMの会社名の既存顧客が「未取引」になる。** CRMには運営会社名で載っていることが多く、名前が違うだけの既存顧客に新規営業をかける（ChatGPT） | `NOT_FOUND` を廃し `NO_NAME_MATCH`（名前照合で当たらなかった）に。CSVは「未取引の可能性（名前照合のみ）」と表示。画面にも注意書き |
| BLOCKER | **弱い名前候補で誤マッチし、別会社の担当者名・メール・電話が別施設の行に出る。** 「ホテルABC 大阪」の「大阪」が1件当たると確定していた（ChatGPT） | 名前候補に強さ（EXACT / STRIPPED / WEAK）を持たせ、WEAK は都道府県の一致を必須に |
| BLOCKER | **「500件までなら300秒に収まる」に根拠が無い。** 全件が既存顧客ならNotionを500回読む（**ChatGPT・Gemini 両方**） | 件数ではなく**時間予算**（既定180秒）で制御。使い切った分は `NOT_CHECKED` として正直に返し、画面にも件数を出す |
| BLOCKER | **CRMミラーが古い・空でも「正常に0件」なので例外にならず、既存顧客が丸ごと新規リストに載る**（ChatGPT） | 書き出し前に `ClientNameIndex` の件数と最終同期を確認し、古ければ 503 |
| BLOCKER | **`user_id` が空でも通り、監査ログ無しで個人情報CSVを出せた**（ChatGPT） | `user_id` を必須化。履歴を残せなければ書き出しごと中止 |
| BLOCKER | **robots.txt の解釈が不十分。** UA行が連続すると `*` を読み落とす／ワイルドカード規則を無視／サイトマップとエリア一覧は未評価（**ChatGPT・Gemini 両方**） | 施設番号ベースを捨て、**URLパスベースの評価器**に置き換え。Allow対応・`*`/`$`対応・ホストごとに取得し、**全リクエストで評価** |
| WARN | 「同時3」が定数だけで保証されていない（ChatGPT） | `Semaphore` を追加 |
| WARN | `time.sleep()` をロックの中で呼んでいる（Gemini） | ロック内では順番を決めるだけにし、待つのは外へ |
| WARN | 429で全ジョブが即失敗。`Retry-After` を無視（ChatGPT） | `RakutenRateLimitedError` に `Retry-After` を持たせた |
| WARN | リダイレクト先を再検証していない（ChatGPT） | 最終URLのホストとrobotsを確認 |
| WARN | **エリア一覧の部分的パース失敗を「最終ページ」と誤認して母集団が静かに欠ける**（ChatGPT） | カード数と読み取れた件数を突き合わせ、打ち切り判定はカード数で行う |
| WARN | 先頭修飾語の除去が1回だけ（Gemini） | 落とせなくなるまで繰り返す |
| WARN | `limit` 指定時も全件を突合していた（Gemini） | CRM条件が無ければ突合前に切る |

テストは 126件 → **158件**（全体 3,318件）。

## 11. 本番へ出す手順（2026-09-12 調査）

**Vercelのプロジェクトは2つあり、順番を間違えると壊れる。**

```
   crm-sfa-integration            ルート。FastAPI(api/index.py)。APIエンドポイント
   crm-sfa-integration-dashboard  dashboard/。Next.jsの画面
                                  ★ build に `prisma migrate deploy` が入っている
                                  ＝ここをデプロイするとマイグレーションが自動で当たる
```

どちらも**Git連携が無い**ので、`git push` だけでは本番は変わらない
（[[feedback_vercel_no_git_integration_manual_deploy]]）。毎回 `vercel --prod` が要る。

```
   ① cd dashboard && vercel --prod
        → マイグレーション 20260911000000_add_facility_list が本番Neonへ当たる
        → RakutenFacility / FacilityCheckInMachine / FacilityListRun が作られる
        → 画面 /facility-list とサイドバーの「リスト作成」も出る
        ※ この時点ではAPIが無いので、画面で操作すると失敗する（数分の不整合）

   ② cd .. && vercel --prod
        → /api/facility-list/{preview,export} が公開される
        → ここで初めて画面が動く

   ③ 母集団を入れる（画面から操作しても何も出ない。先に取り込みが要る）
        DATABASE_URL=<本番> python scripts/import_rakuten_facilities.py --prefecture 鳥取県
```

**①を先にやる。** 逆にすると、APIがまだ存在しないテーブルを触りに行く。
