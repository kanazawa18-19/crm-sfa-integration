本人通知の送信元変更をレビューしました。本文・宛先・送信後の記録順序は、差分上はすべての箇所で維持されています。一方で、Googleの権限と実GASへの移行手順に重大な問題があります。このままの手順で実GASへ適用することは推奨しません。

B1 権限の拡大
GmailAppを使うには https://mail.google.com/ が必要です。この権限では「メールの閲覧・作成・送信・完全削除」まで許可されます。対象のGASにはNotebookLMのCookie、Slackへの受信口、外部への通信を持つものが含まれます。
特に問題になるのは、プロジェクトの編集権限を持つ人です。その人がコードを書き換えると、書き換えたコードは既存トリガーの所有者の権限で、追加の承認なしに実行されます。つまり所有者のメールボックス全体に触れられる状態になります。
対応は次のとおりです。

各プロジェクトについて、スクリプトの編集者を確認する。コンテナに紐づくGASの場合は、親スプレッドシートの編集者も含めて確認する。
本人が承認する際に、同意画面に表示される権限の文言を提示する。
最小権限の代替案として、Gmail拡張サービス（Gmail API）に gmail.send と gmail.settings.basic を付ける方法も比較材料として示す。この方法でもメール本文の読取・削除はできません。ただし日本語件名のMIMEエンコードが必要になり、実装の手間は増えます。

B2 代送なしの保証
試験はモックが例外を投げることを前提にしています。しかし、未登録の from を指定したときに実GASが例外にするのか、既定のアドレスで送ってしまうのかは、ローカル試験では検証できません。送信前に明示的に確認し、使えない場合は例外にしてください。


js
var NOTICE_FROM = 'daizuhakkou0619@gmail.com';
function sendOwnerNotice_(to, subject, body) {
  if (GmailApp.getAliases().indexOf(NOTICE_FROM) < 0) throw new Error('NOTICE_FROM_UNAVAILABLE');
  GmailApp.sendEmail(to, subject, body, {from: NOTICE_FROM});
}

各送信箇所はこの関数の呼び出しに置き換えます。そのうえで、getAliasesが空の場合に送信関数が一度も呼ばれないことを試験で確認してください。
なお、実行者が個人Gmailそのものである場合、自分の主アドレスは getAliases() に含まれません。この構成が存在するかどうかを、実行者の確認時に必ず切り分けてください。

B3 権限変更による停止期間
マニフェストの oauthScopes を変更すると、トリガー所有者が再承認するまで、その後のトリガー実行はすべて権限エラーで失敗します。通知だけでなく、processQueue、pollSalesQa、収集処理なども止まります。再承認は、トリガー所有者本人のアカウントで行う必要があります。
推奨する手順は次のとおりです。

送信権限を残したまま mail.google.com/ を追加し、push後ただちに本人が承認する。
通知コードを切り替える。
最後に script.send_mail を削除する（削除だけなら再承認は不要）。

この順にすると、各段階で旧版に戻せます。

B4 通知単独試験の手段がない
末尾が「_」の関数はエディタの実行メニューに表示されないため、通知関数を単独で実行できません。既存の公開関数は、いずれも業務処理やトリガー操作を伴います（nameJobTick、checkHttpNotebookClock、kstepInsightsHealth など）。
各プロジェクトに公開の試験関数（例：ownerNoticeSelfTest）を追加してください。条件は次の3点です。

本番と同じ方法で宛先を決める（OWNER_EMAIL、HEALTH_EMAIL、実行者、COLLECTOR_NOTIFY_EMAIL、INSIGHTS_NOTIFY_EMAIL）。
「[試験]」と付けた件名で1通だけ送る。
プロパティへの書き込みとトリガー操作を行わない。

この関数は、承認画面を出すための関数も兼ねられます。attachment-syncでは、この関数以外を実行しないことを手順書に明記してください。

B5 実GAS原本への適用方法
clasp pushはプロジェクト全体を上書きし、ローカルにないファイルを削除します。リポジトリからそのままpushすると、CRMで未反映の変更が混入します。手順は次のとおりです。

実GASを別ディレクトリにclasp pullする。
本差分の該当箇所（送信行、マニフェストの権限1行、試験関数）だけを手で適用する。
原本との差分が通知関連だけであることを確認してからpushする。

あわせて、実GAS側のマニフェストがリポジトリと一致しているとは限らないため、その確認も必要です。テストファイル（*.test.js）がpush対象から除外されていることも確認してください。

ID	推奨対応
W1	エイリアスが個人GmailのSMTP経由の場合、送信の成功は配信の成功を意味しません。受信ヘッダで From・Return-Path、DKIM/SPF/DMARCの判定、経由サーバーを確認し、送信者側に不達通知が来ていないかも確認してください。
W2	全リポジトリと実GAS原本で、MailAppを検索してください（getRemainingDailyQuotaなどの通知以外の用途を含む）。1件でも残っていれば、権限を明示しているマニフェストでは実行時エラーになります。
W3	doPostを持つ2プロジェクトは、既存のデプロイを新しい版に更新してください。新規デプロイにするとSlack側の受信URLが変わります。
W4	kstepは実GASのマニフェストに明示の oauthScopes があるか確認してください。追加試験の2件目は、fetchのモックが undefined を返すため、送信前に例外で通過している可能性があります。sendEmailが呼ばれたことと、例外メッセージが「送信元拒否」であることを検証してください。
